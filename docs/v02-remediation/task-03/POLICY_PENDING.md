## 1｜disburse 与新不利信息边界（P-03c）

### 1.1 现有实现（Back/A/src/domain/credit.ts）

- `disburseFinancing` 提交点门序：客户/设施行锁 → 状态门（仅 `committed` 可出账）→ `assertFrUseGates(..., 'disburse')`：
  1. 设施硬状态（暂停/过期/超限/依据失效标记，冷却除外）→ 409 `FACILITY_NOT_ACTIVE|STALE_BASIS`；
  2. 客户级未决阻断性差异 → 409 `REVIEW_REQUIRED`；
  3. **到此为止**：`credit.ts` 中 `if (action === 'disburse') return view;`——**不再复查依据包当前性**（K14c 注释原文："已承诺敞口的执行：不回写历史决定，也不以当前性追溯冻结"）。
- `unknown` 模拟出账：状态 `disbursing_unknown` + `external_state='unknown'`，不产生账目、不动桶、不自动释放；唯一退出路径是 `confirm-external`（人类 + 权限矩阵 + 决策记录）。
- 对照：`reserve`/`commit` 在同门之后**继续**复查依据包当前性（`checkPackageForAction('use_of_funds')`）或 409 `BASIS_PACKAGE_REQUIRED`。

### 1.2 当前有效契约

- CONTRACT §9 A3（v2.2，2026-09-17）："commit/disburse 提交点机械复查：设施硬状态 → 客户级未决差异 → 依据包当前性（**commit 及 reserve**；**disburse 为已承诺敞口的执行，不重复当前性门**——新承诺已在 commit 拦截，后来不利信息不追溯冻结既有负债）"。
- DECISIONS.md（既有记录）："disburse 定位为'已承诺敞口的执行'：不再重复当前性门（K14c/B08 的边界——新承诺在 commit 拦截，后来不利信息不追溯冻结既有负债）"。

### 1.3 历史决定冲突

- 旧 B11 口径曾把"冷却/不利信息"理解为可冻结既有合法用信可用额；后被 §9 A3"冷却口径收窄"显式修订（只硬阻断激活/恢复与客户级向上提额，不冻结既有用信）。**现行 = 收窄后口径**；冲突已由契约修订解决，非待决状态。
- 需要说明的历史张力：Q1（"disburse 跳过当前性门"）作为风险被再次提出 → 本轮反例化确认：该跳过**正是** §9 A3 的契约语义（实现=契约），不是实现缺陷。

### 1.4 可验证不变量（测试已覆盖/可覆盖）

- 仅 `committed` 可出账；重复出账/重复回调被状态门+账本部分唯一索引双层拒绝（`ledger-races-a3` K12–K18 并发覆盖）。
- disburse 仍受设施硬状态与客户级未决差异阻断（不是无门）。
- unknown 出账后：账目不变、占用保持、必须经人类 `confirm-external` 收口；**未知外发结果必须对账，不得盲重发**（`SETTLE_UNKNOWN_RECONCILE_OPENED` 事件 + 唯一合法退出路径）。

### 1.5 需人类裁决的问题

1. 承诺（commit）与出账（disburse）之间出现重大不利事实（如资产灭失级差异）时，是否接受"既有负债不追溯冻结"的边界？还是要求 disburse 增加一个**窄**复查（仅检未决差异已覆盖？还是增加确认机制？）——注意：客户级未决差异在 disburse 已被阻断，若裁决需要更强阻断，需定义新触发条件而非复用当前性门。
2. `disbursing_unknown` 长期未对账的处置（超时升级/人工台账）目前只有事件与读面，无自动机制——是否需要制度性 SLA（本内核不擅自引入）。

## 2｜V0.2 组织层级：最小数据建议与接口缺口（只登记，不建设）

### 2.1 现状事实

- `customers` 表仅有：`customer_id/tenant_id/legal_entity_ref/display_name/status/created_by/created_at/updated_at/version`。**无**大区、省级门店、坐标、业绩指标。
- 目录响应（§11 G1）同样不含上述字段；设施/评估/账目均为客户粒度。
- 结论（任务书口径）：**"有客户额度"不等于"有门店业绩"**；业绩/资产/新客视角的数据源当前不存在于 A 内核。

### 2.2 最小数据建议（V0.2 地图视角需要的最小形态；不建平台/引擎/地图系统）

| 层级 | 最小数据 | 建议来源（全部为缺口，需立项） |
|---|---|---|
| 全国 | 汇总视图 | 由下级聚合推导，不落明细 |
| 可配置大区 | region_id、名称、配置关系表（可调整，客户→大区映射） | 新登记表（组织配置），主数据来自用户方 |
| 省级门店 | store_id、名称、所属大区、（可选）坐标；客户→门店归属 | 新登记表；坐标属地理主数据，A 不生产 |
| 客户 | 现有 `customers` 增可选 `store_id/region_id`（或独立映射表） | 迁移只加列/表 |
| 业绩视角 | 门店/大区业绩指标（放款额、回收、新增） | **不存在**：需从台账 `exposure_entries` 聚合（放款/回收可推导）+ 业务侧真实业绩源（账目仅为受控模拟，不能当真实业绩宣称） |
| 资产视角 | 资产/租赁物台账 | **不存在**：equipment_refs 仅是引用，无资产主数据 |
| 新客视角 | 新增客户按门店/大区/时间分布 | customers.created_at + 门店映射即可推导（最小可先行） |

### 2.3 接口缺口（未来立项时点）

- 客户目录响应未含组织归属（region/store）→ 地图选择器需要（可加可选投影，属 §12.6 P-03d 类似的披露面问题）。
- 无组织配置读面（region/store CRUD+授权）→ 需要谁写、谁审（组织主数据属正式配置，建议人类 admin + 审计）。
- 业绩指标无权威源 → 聚合 API（如门店级账目聚合）只对"模拟台账"如实标注 provider/口径，不得冒充真实经营业绩。

## 3｜客户归属校验与最小权限服务接入（处理链契约，已成立，供任务02/04）

- **新客户归属**：客户创建即绑定 `tenant_id`（createCustomer 事务内）；任何服务身份在客户域写口都经 `lockCustomer(tx, customerId, ctx.tenantId)`——跨租户客户一律 404，**无需逐客 SQL 配置**。
- **最小权限服务接入**：service 身份 = `service_identities` 行（创建时绑定租户），认证后 `customers:'all'`（租户内）且 `roles:['service']`；可执行面被收敛为三口（Gate 回执登记 / 分析运行 start+finish / 材料处理状态）+ 只读。**不能**作出任何正式批准（requireHuman 门）、**不能**代替人类验收/决定。
- **不信任浏览器字段**：v2 全部命令的授权（角色/租户/客户/矩阵动作）来自服务端身份源与登记表；载荷中的权限/操作者/批准声明一律无效（`approvedBy` 等字段不存在于载荷或被 400 拒绝）。
- 若未来要求把 service 身份进一步限到客户子集（客户级最小权限），需在 `service_identities` 上引入 grants 语义——**接口缺口登记，本轮不做**（现状：租户粒度已满足处理链需求且无需逐客配置）。
