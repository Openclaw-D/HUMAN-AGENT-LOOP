# 远程协作与视频辅助｜场景边界

2026-09-12。用户已明确远程协作方向；下述技术分层为建议，未实施。产品代码仍归ZCode，新写面须任务交接。

## 用户明确的体验

业务发起流程并询问关键问题；政策、信审、商务、资产专业人员通过同一项目看板补充。见微辅助整理与说明，模型不替代专业人员或正式审批。六分钟演示先展示传统方式三例，再展示远程方式同三例；不固定模型结论，不把剪辑时长当业务耗时。

## 推荐的最小交互

远程发起 → 提问并记录资料 → 可选画面分析 → 看板显示事实/待确认项/专业反馈 → 业务补充、专业人员确认。可让专业人员异步补充，不要求全部同时进入视频；这是减轻实现与参与负担的建议，不是强制取消同步讨论。

同一看板不等于所有角色看到全部内部信息。业务只看获准摘要、问题和进度；专业人员按授权补充。多人写入需角色归属、版本冲突和更新同步，不能用当前单人演示中的角色文字假冒实际协作。

## 视频能力的投入分层

| 层次 | 做法 | 判断 |
| --- | --- | --- |
| 录制素材辅助 | 获准演示片段，明确标为录制；手选关键帧交视觉模型 | 最轻的能力验证，不冒充真实远程接入 |
| 远程视频 + 按需分析 | 复用获准的视频传输组件，业务主动选取当前画面，带问题交视觉模型 | 推荐首期视频候选；仍需摄像头权限、连接恢复、证据归属及预算，不只是增加API |
| 持续实时多模态 | 连续音视频、转写、画面采样、时间同步、模型实时反馈 | 明显更重，需要延迟/带宽/资源与隐私评估，不作为首期默认 |

Dify承载模型与结果编排，不承担音视频会议传输；视频层不因此要求更换全部后端。若未来自建视频通话，LiveKit/WebRTC是候选而非已选定依赖；公司既有视频工具能否合法提供媒体输入尚未核对。

视觉模型可辅助读清晰铭牌、记录可见设备特征、提示补拍和资料矛盾；画面不能单独证明设备归属、经营真实性、偿付能力或正式可授信。模糊画面返回无法确认，不猜测；不以表情、长相或所谓测谎作为客户评价依据。

图像/片段关联项目、本轮问题、输入版本、时间与来源；先由人确认是否纳入事实，避免模型识别结果覆盖原始资料。仅使用合成、授权且充分去标识演示素材；摄录、对外发送与保存期限需明确，不能默认上传整场客户视频。现有模型和资源包的视觉能力/抵扣未核实，不宣称无需新增成本。

## 已查证与未验证

- 本机Dify 1.13.2 LLM节点entities.py/node.py存在vision配置与图像处理路径，只证明视觉接入设计入口存在，供应商插件/具体模型与端到端尚未验证。
- [LiveKit视频文档](https://docs.livekit.io/agents/multimodality/vision/video/)区分抽帧图片与受支持模型的实时视频输入；抽帧不能等同连续运动理解。
- 多人访问、手机摄像头、音视频传输、视觉模型识别均未实现或验收。此次仅记录产品决定和投入评估，不更改现有运行环境。
