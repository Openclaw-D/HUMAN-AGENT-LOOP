# 见微 V4｜比赛交付与现场约束

状态：`CURRENT CONSTRAINTS / SCRIPT NOT FROZEN`

日期：2026-09-03

## 1. 已确认的交付约束

- 当前距离比赛约两周半；精确比赛日期尚未写入本文件。
- 每组现场总时间约 15 分钟。
- 场地有四块大屏，领导集中就坐，后方为其他观众。当前按四块屏幕镜像复制同一个 canonical 画面设计，不依赖扩展桌面或双屏独立输出。
- 当前设计基线采用约 10 米观看距离、单块主屏约 3 米 × 6 米；用户另口述其中一块宽屏比例约为 `19:6`。比例口述值与物理尺寸估算不完全一致，因此两者都保留为输入，不冒充最终 venue specification；精确分辨率、比例、亮度、网络与投屏方式仍需赛前实测。
- 首期只要求业务短输入、政策/信审/商务/资产四域工作面与桌面大屏 Projection；大屏负责让全场看见同一项目 Context 在四域之间的并行工作、路由、Evidence、Human Gate 与 Receipt。是否每个角色都需要独立 Mobile Web 由平台复用 Gate 决定，不为形式增加页面。
- 比赛不是静态原型交付。Golden Case 必须基于真实前后端、API、状态与失败处理运行；PPT、视频和舞台叙事只能解释已经验证的能力。
- 实施顺序固定为：产品与后端契约 → 后端核心 → 前端 → 前后端联调与部署 → PPT、演示和脚本。

## 2. 现场展示的产品含义

手机小屏不能成为领导理解系统的唯一载体。任一角色在手机上的关键动作，都必须在共享大屏 Projection 中被清楚地观察到：

1. 当前是谁、以什么 Role 操作；
2. 操作针对哪个项目 Context 和哪个专业域；
3. 新增了什么 Evidence 或 Candidate；
4. 哪个 Human Gate 正在等待、通过、退回或否决；
5. 哪些依赖工作被启动、停止或保留；
6. 最终产生了什么可验证 Receipt。

大屏不是把手机画面放大，而是同一权威事件账本的公共 Projection。手机、桌面工作台和大屏必须观察同一状态，不能由三套演示脚本分别伪造。

## 3. 单一 canonical 大屏

- 一个画面同时承担项目 Context、当前 Actor、四域状态、风险、Human Gate、Receipt，以及政策、信审、商务、资产之间的路由与 Evidence 来源。
- 四块现场屏幕默认复制这一画面；任何核心信息都不能依赖某一块屏幕单独存在。
- 如果赛前实测证明能够稳定独立投屏，可增加辅助画面，但 canonical 单屏仍必须独立讲清 Golden Case。

这是已冻结的 Projection topology，不是最终视觉稿。

## 4. 互动网站与二维码边界

通过微信扫码进入 Mobile Web 在技术上可行。当前扫码面不是让观众操作另一条流程，而是舞台 Golden Case 的只读伴随页面：

- 只使用合成、脱敏或明确获准公开的数据；
- 不直连真实内部系统、内网模型、内部材料或正式审批写路径；
- API key、模型凭据和内部 endpoint 只存在于服务器端 secret，不进入浏览器、二维码或前端包；
- 所有观众只订阅舞台受控 session 的只读事件流，不拥有命令、审批、上传或状态修改能力；
- 每名体验者仍具有连接限流、过期和滥用保护，但不创建会污染主演示的业务分支；
- 页面按当前进度自动跟随，并允许查看已经公开的角色动作、Evidence 摘要和 Receipt；
- 伴随页面失败不能影响舞台主 Golden Case，舞台也不能依赖观众页面回传。

公开免登录站点是比赛体验面，不是生产权限方案。真实业务系统仍需认证、组织目录、RBAC、事项隔离和审计。

## 5. Golden Case 当前方向

- 新客回租是与竞品共享的业务场景，不作为差异化口号。竞品在租赁物确存、确权、排重上已有明确表达；见微不在缺少同口径 Evidence 时宣称单点能力更强，也不为竞争重复造排重引擎。
- 见微的主差异是“风险接续”：排重或其他检测只产生一条 Evidence；系统继续证明这条 Evidence 由谁承接、如何影响政策/信审 Human Gate、怎样转成商务与起租条件、变化后如何重开、资产结果如何反馈。
- 内部工作案例固定为一个完全合成的小微新客回租项目，但舞台从“业务提交既有十问/材料包形成的待核验 Context”直接开始，不表演商机、客户或尽调流程，也不在入口展开直租/回租。
- Context 封存不等于事实已核验；主演示应让观众看到系统如何把已披露、待核验、矛盾、缺失和过期信息分开，并在访厂前把问题送到正确 Human Role。
- 交易供应商不进入首期案例；回租租赁物只作为资产 Evidence 与交易条件出现，不扩成供应商或采购流程。
- 如果对外直接使用真实企业名称，必须明确标注“基于公开信息构造的虚拟演示案例，不代表真实客户关系、授信结论或合作关系”；若无法通过品牌与合规 Gate，则改用仿真企业名。
- Golden Case 的目标不是把全部功能演一遍，而是证明：新客回租的关键风险可以在访厂前更早暴露，政策、信审、商务、资产按依赖穿插并行，正确角色被路由，Agent 不越权，Human Gate 生效，批复后变化可被重新发现，状态与资产 Evidence 可追溯并反馈前序。
- 现场主画面围绕一条 Risk Thread 展开，不把四域做成四个并列功能块。领导必须能连续看见 `风险 → Evidence → 当前 Owner → Human Gate → 商务/起租条件 → 后续复核/资产反馈`。

## 6. 现场脚本状态

已确认：总时长约 15 分钟，纯实机操作段应缩短，避免观众等待手机输入。

当前 Candidate：业务只完成一次短输入或由主持人说明已有 Context，政策、信审、商务、资产各完成一个能够推动同一风险闭环的短动作，大屏同步变化。约 10–13 分钟核心内容中，用约 5 分钟讲清四域闭环，其余用于问题、第一价值、Capability/Authority 双图、复用式落地与必要容错；不再采用六角色接力或 `3.5 + 3.5 + 3.5` 结构。

在 P5 E2E 稳定前，不锁定最终脚本，更不让脚本反向要求后端伪造能力。

## 7. Model/API 运行边界

Codex 是开发、审查与验收工具，不是部署后网站的运行时。正式调用链应为：

```text
Mobile/Web
  → V4 Server API
  → Provider-neutral Model Gateway
  → 经配置的内网或外部模型服务
```

- 模型供应商、endpoint 与 model ID 通过服务器端配置和 adapter 替换；P0 不冻结具体模型。
- 模型输出只能成为 Candidate；正式状态变化仍由确定性规则或 Human Gate 产生。
- 必须覆盖 timeout、rate limit、invalid response、上游不可达、重试、circuit breaker、fallback 和审计。
- 比赛主链路不能把 live 模型成功当作唯一前提。模型不可用时，应明确降级到已验证的规则、缓存或 deterministic Candidate，同时保留“当前为降级状态”的真实标记。
- “接通一次 API”不等于完成联调；必须把真实调用与同一 Case、Context Version、Evidence、Candidate、Decision/Receipt 和大屏 Projection 串成可重放 E2E。

## 8. 远距展示验收 Gate

- 在约 10 米位置，主状态、当前 Actor、风险级别、Gate 结果和下一步无需放大即可辨认；
- 任何关键结论不只靠小字号、颜色或手机屏幕表达；
- 角色动作后，大屏在可接受时延内显示同一服务端状态；
- 网络或模型失败时，主持人能看见真实故障状态并沿受控 fallback 继续，而不是空白或假成功；
- 最终赛前必须在实际屏幕比例、分辨率、浏览器、网络和投屏链路上完成一次 full rehearsal。

## 9. 尚不阻塞 P0 的后续事实

- 精确比赛日期与上下场规则；
- 四块屏幕的分辨率、比例、输入源与能否分别投屏；
- 会场公网、微信内置浏览器、二维码域名与并发人数；
- 演示客户名称的品牌/合规许可；
- 部署数据库、对象存储、身份与 session 方案；
- 最终模型供应商、凭据、额度、并发、时延与 fallback 顺序；
- 四域是否全部需要真人上台及最终分钟脚本。
- Dify、One/IMAX、其他成熟平台与最小自研控制面分别承担什么。

这些事项分别进入 P3–P6，不新增 P0 产品方向阻塞。
