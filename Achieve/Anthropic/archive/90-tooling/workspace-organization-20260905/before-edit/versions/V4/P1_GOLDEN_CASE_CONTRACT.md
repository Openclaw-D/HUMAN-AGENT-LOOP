# 见微 V4｜P1 新客回租 Golden Case 内容契约

状态：`SCENARIO FROZEN / CONTENT CANDIDATE / USER ACCEPTANCE OPEN`

日期：2026-09-04

2026-09-05 权威边界澄清：本文件承接已冻结的产品主干和新客回租场景，用来探索、验证一个具体案例。正文引用既有明确决定的约束继续生效；案例问题、具体岗位映射、材料、触发条件、页面和效果指标在被明确接受前保持 Candidate。案例选择不反向改写 `NORTH_STAR.md`，也不作为进入 V4-RISK 的前置条件。

## 1. Root Authority

- 当前唯一比赛 Golden Case 固定为“小微新客回租”。它是当前小微资源最关注、业务价值优先级最高的首要锚点，但不是产品排他性边界。
- 产品与技术 contract 仍覆盖融资租赁，不锁死为仅回租；工作面不增加直租/回租选择页。
- “利润最高、价值最大”当前是场景优先级判断，不直接对外写成已证明的财务收益；最终 ROI 必须由可复算基线支持。

## 1.1 多方价值约束

| 相关方 | 应获得的增益 | 不允许的代价转移 |
| --- | --- | --- |
| 客户 | 更早知道真实缺口、减少反复补件和无效等待 | 以更广泛、无目的的数据采集换效率 |
| 业务 | 更早判断可操作性、减少无效访厂和重复整理 | 隐瞒、弱化或把核验责任整体推给后道 |
| 政策 | 口径一致、规则有来源、灰区进入正确路径 | 让模型把模糊事项伪装成硬规则 |
| 信审 | 获得完整可追溯 Evidence，把时间用于专业判断 | 承担业务未披露、系统漏检后的无限补录和兜底 |
| 商务 | 风险要求能够准确落到合同、担保和起租条件 | 成为前序风险遗漏的最后补洞环节 |
| 资产 | 权属、价值、存续和变化更早可见 | 用贷后处置承担贷前本可发现的风险 |
| 公司整体 | 风险收益、客户体验、人员产能与资本安全共同改善 | 只看审批速度、通过率或单部门成本下降 |

每项 Candidate 功能都要形成一张“多方影响账”：谁少做了什么、谁新增了什么、风险提前了多少、成本是否只是跨角色迁移。整体净价值不为正时，不因新回优先级高而强推。

## 1.2 竞争定位：新回是场景，接续才是差异

- 新客回租不是见微独占场景；已知竞品也以新回为对象，并在租赁物确存、确权、排重等单点能力上形成更直接的表达。该判断来自当前比赛材料观察，不冒充完整产品审计。
- 见微未经同口径测试，不声称排重准确率、速度或资产识别优于竞品；如果成熟排重服务可复用，它应作为产生 Evidence 的原子能力接入，而不是重新开发一套。
- 见微要证明的是单点能力之后的工作：同一个风险由谁承接、如何跨域解释、影响什么 Human Gate、怎样固化为商务/起租条件、后续变化如何触发重审、资产结果如何回到前序。

全局协调接续固定为五种连续性：

1. **Context 连续**：所有角色引用同一 Case、同一版本和同一 Evidence 来源；
2. **责任连续**：每个风险都有当前 Owner、下一 Owner、等待原因和停止条件；
3. **决定连续**：Candidate 只有经过正确 Human Gate 才成为 Receipt，并驱动真实依赖；
4. **条件连续**：已确认风险能够落到合同、担保、付款、起租或巡检条件，不能停在报告里；
5. **时间连续**：访前、批复、起租前和资产存续期的新事件能够重开必要事项，并保留旧版本与贡献。

这里的“全局”只覆盖一个小微 Case 的业务接口与政策、信审、商务、资产四域，不扩成集团治理、全产品线或自研通用流程平台。

## 2. 访谈 Evidence 的使用边界

本文件只保存去标识、抽象后的业务证据。原始访谈中的个人、客户、区域、具体案件和内部系统细节不进入 Golden Case、代码 fixture、Prompt 或比赛材料。专家表述是需求 Evidence，不自动成为制度规则；规则、阈值和角色权力仍需有权人员确认。

访谈目前支持以下高置信问题判断：

1. 新客回租的主要浪费发生在访厂前：材料到达晚、预审时间被压缩、项目临时替换、关键问题后置暴露；
2. 既有“十问 + 材料包”能够作为入口，但其准确性、完整性和披露质量不稳定；
3. 前线、业务主管与信审之间可能存在信息不对称，系统不能假定已提交内容等于已核验事实；
4. 税务、发票、流水、征信/授权、主体关系、公开司法、内部预警与资产信息分散，人工难以逐笔钩稽；
5. 批复至起租可能间隔较长，主体、司法、负债、经营或资产信息可能变化；
6. 大量制式整理和校验可以自动完成，但异常解释、补件取舍、审批和例外仍必须由人负责。

## 3. 本 Golden Case 的问题假设（CANDIDATE）

产品主干继续是四个风控职能及其与业务的协同。本案例拟验证以下问题是否能具体证明跨域协作价值：

> 在不改变现有报批与岗位权力的前提下，把新客回租上游申报中的缺失、矛盾、过期和未核验事实，在高成本访厂及正式批核之前尽可能暴露，并把少量真正需要专业判断的问题送到正确的人；批复后至起租前再对关键变化进行复核。

## 4. 场景入口与结束

入口不是新建商机或尽调模块，而是引用既有系统中的 Case，并接收一批合成的“十问 + 材料包 + 已获授权数据引用”。

首期闭环包含两个时间检查点：

```text
既有材料包提交
  → Context Integrity 解析与核验
  → 四域 Candidate / 补件问题
  → 访前准备 Human Gate
  → 现行尽调与审批继续
  → 批复后关键 InputEvent
  → 起租前差异复核 Human Gate
  → 资产域持续观察与前向反馈
```

两个 Human Gate 都只复用现有角色和流程。本产品不得自行取消访厂、批准、否决、放款或起租。

## 5. Context 与 Evidence 语义校正

`OPEN → STABILIZING → SEALED` 仍然成立，但 `SEALED` 只说明这个版本不可变，不能表达“内容已经正确”。关键 Evidence 至少需要：

- `sourceType`：业务陈述、原始材料、既有系统、获授权外部数据、Human 复核或模型派生；
- `subjectRef`：企业、实控人、配偶、担保人、关联企业、交易对手或租赁物；
- `observedAt / effectiveAt / expiresAt`：观察、适用和过期时间；
- `verificationStatus`：`claimed / unverified / verified / contradicted / stale`；
- `evidenceRef`：可回到来源的引用；
- `confidence / uncertainty`：仅对派生结果使用，不能替代核验状态。

系统不得用模型常识补齐缺失身份、关系、授权、资产权属或财务事实。

## 6. 四域在同一风险链上的职责 Candidate

| 领域 | 新客回租首期关注 | 结构化产出 |
| --- | --- | --- |
| 政策 | 已知事实是否触发硬管控、灰区、复议或例外候选路径 | 命中项、适用前提、缺失 Evidence、待 Human 解释项 |
| 信审 | 主体与关系是否完整，经营、税票、流水、能耗、负债和偿债逻辑是否相互一致 | 矛盾图、核验问题、风险 Candidate、依据与不确定性 |
| 商务 | 已确认风险如何成为担保、合同、付款、权属文件或起租前置条件 | 条件 Candidate、文件缺口、条件变化影响 |
| 资产 | 回租租赁物是否真实、可识别、权属清楚、价值可解释，并在起租前后保持可观察 | 资产 Evidence、权属/公允性疑点、巡检与变化反馈 |

四域共享 Evidence，但不共享决定权。任何一个领域发现的新事实都可以触发其他领域的低成本重算；正式动作仍等待真实依赖和 Receipt。

## 7. Golden Case 主矛盾候选池

最终主演示只选择 1 个贯穿矛盾，当前候选为：

1. 关键主体、担保人与关联关系披露不完整，外部风险无法正确归集；
2. 税票、流水、能耗、产能或报表之间存在经营一致性异常；
3. 回租设备的采购真实性、权属、可识别性或公允价值存在缺口；
4. 批复后至起租前出现新的司法、负债、经营或资产变化。

不得把全部异常堆成“风险大礼包”。选择标准是：能贯穿四域、Evidence 可合成、规则不泄密、三分钟内能看懂，并能证明系统不仅更早发现，而且让风险从发现、接手、决定、条件落实到后续复核完整接续。

## 8. 工作面调整

业务 Mobile 首屏不做 CRM 或长报告，优先显示：本批材料完整度、待补的最小问题、每个问题的 Evidence 原因、访前准备状态和变化提醒。

四域 Desktop 优先显示：

- 主体/关系与租赁物图谱；
- 已披露、待核验、矛盾、缺失、过期五类 Evidence；
- 跨数据源一致性检查；
- 当前 Context 与批复快照的差异；
- 哪个 Human Gate 等待谁、为什么、影响哪些后续事项。

主画面必须存在一条跨域 Risk Thread，而不是四张互不相干的卡片。每个时点至少能回答：`发生了什么 → Evidence 在哪 → 当前 Owner 是谁 → 等待哪个 Gate → 将影响什么条件 → 下次何时复核`。

Case Chat 只能解释差异、生成核验问题和材料草案，不得把带情绪的线下沟通变成评分、监控或自动处分。

## 9. ROI 与效果证据

首期不以“自动批准率”或单纯通过量证明价值。需要建立以下基线与改进值：

- 访厂前关键风险发现率与提前量；
- 因明显不可操作或关键缺件造成的无效访厂/临时换案次数；
- 每案补件轮次、重复整理时间和专家有效判断时间；
- 关键主体/关系覆盖率、Evidence 完整度和跨源矛盾发现数；
- 批复后至起租前重大变化的发现率；
- 风险从发现到明确 Owner、从 Human Decision 到条件落地的接续时长，以及重复询问/重复取数次数；
- 单案模型、数据、算力和人工成本，以及避免的差旅、返工与风险损失区间。

所有百分比必须来自可复算样本，不能把访谈中的愿景数字直接写成预计收益。

ROI 必须同时呈现总收益和分角色影响；不得只汇报业务端缩短时间，而隐藏政策、信审、商务或资产新增的工作量与风险责任。

## 10. 明确排除

- 不做无人自动批核；
- 不把业务人员历史表现直接转成权限、排单或加急额度；
- 不把复杂 3D 现场重建作为首期核心，先验证现行照片清单、租赁物识别和 Evidence 覆盖；
- 不一次接入所有内部黑名单、税务、征信、司法或第三方数据；
- 不以“击败竞品排重”为首期目标，不在缺乏同口径样本时宣传单点准确率优势；
- 不训练未经审核即可全租赁复用的自动规则；
- 不使用真实客户、真实征信、身份证、内部制度全文或案件细节；
- 不建设新客经营、商机、尽调采集或回租全生命周期平台。

## 11. P1 Acceptance 仍需用户/有权专家确认

1. 主演示选哪 1–2 个贯穿风险矛盾；
2. 合成十问/材料包的最小字段和必需 Evidence；
3. 访前准备 Gate 与起租前差异复核的现有 Human Role；
4. 哪些数据源首期确有合法权限和稳定接口；
5. Evidence 多久视为 stale，哪些变化必须重开 Context；
6. 可获得的历史退回、换案、补件、访厂和风险发现基线。
7. 多方影响账中允许的成本转移边界，以及由谁确认整体净价值为正。

## 12. 候选验证检查点（待案例接受）

`P1-01 访前 Context Integrity + 风险接续垂直切片`：使用一个完全合成的新客回租 Case，从十问/材料包输入开始，证明 Claim 与事实分离、一个跨源矛盾被提前发现、四域形成不同 Candidate、现有 Human Role 完成访前准备确认、已确认风险变成后续条件，并由一个批复后 InputEvent 触发必要复核。所有 Event/Evidence/Owner/Decision/Receipt/Condition 投影到同一 Risk Thread。该检查点被用户接受前，不替换当前代码 seed，不扩展真实数据接入或自研排重。
