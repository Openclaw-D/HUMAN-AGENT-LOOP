## 与 V6 的关系

V7 不是把 V6 已有候选、合成演示或未验收实现追认为生产能力。V6 首页 R1 仍由既有 ZCode owner 在其明确写面内完成，主 Codex 只做独立验收；V7 不抢写 `jianwei-v3/site/`，也不因此绕过 Git baseline、真实凭据、部署或正式审批的硬门。

V7 要验证的是一个更小、更可运行的后端协作单元：同一项目事实可在 mobile/desktop 继续使用；一次模型辅助可被重放、区分失败/未知，并能由人接管。远程尽调视频、现场增强和把行业报告转为审批规则均不在本轮。

## 最新分工（准确理解）

1. **规则负责收敛，不负责代替全部判断。** 规则说明本次看哪些指标、其适用范围、允许使用的数据/工具、必经人工门及输出边界；它应引导模型和人思考，而非把所有风险结论硬编码成 if/else。
2. **模型负责基础理解与量化辅助判断。** 在规则给出的范围内，模型可整理证据、提出假设、调用可验证的计算工具并解释结果；其输出始终是候选意见，`authority=none`。
3. **人负责例外与最终兜底。** 当规则不覆盖、证据不足/相互矛盾、计算口径不完整、调用状态未知，或模型无法稳定回答时，系统必须明确升级人工。正式否决、退回、例外和决定权仍由人保有。

这不把“3D 打印、液冷精密加工、山东印刷”等 01-Report 对话线索直接固化为行业规则或审批结论。报告正文尚未作为本记录的证据输入。

## 第一候选实验：可追溯的“模型 + 计算 + 人工升级”单次回合

这是待用户确认的实验目标，不是派工授权：对一条合成行业异常事实，服务端保存规则版本、输入事实版本、模型请求标识、计算输入/输出/公式版本、模型候选意见、置信/不确定说明及人工动作。相同输入与规则可重放；网络或模型调用结果不确定时不自动重试为成功，而是留下 `unknown` 记录并升级人工。计算工具只返回带单位和假设的确定性结果；模型不得把它转换成正式审批结论。

拟验证的最小问题：**在真实 HTTP 模型通道已明确配置时，系统能否以一次有界调用产生可解释候选；在未配置、超时/中断、工具输入缺失或输出不合格时，是否诚实失败关闭并把工作交回人，同时让另一端刷新后看见同一事实？**

### 暂定验收证据

- 一次成功路径和四类失败/未知路径的 HTTP 或可复跑测试证据；不以模拟成功冒充真实调用。
- 刷新/重启后，项目事实、请求回执和人工接管状态可恢复；重复 request 不重复记账。
- mobile/desktop 同项目读到相同事实版本；模型、计算、人工三类来源在界面/API 中可区分。
- 不含真实客户资料、密钥、部署或自动审批；不提交、不打 tag、不使用 worktree。

### 仍需讨论后冻结的点

- 第一个合成异常的具体输入和人工可接受的计算口径；不能从行业对话自行推定。
- 模型输出的最小结构（指标观察、依据、假设、不确定、建议人工动作）与不合格时的拒绝条件。
- “unknown”后是否允许人工显式重试，以及防重复计费/重复记账的 receipt 语义。
- 真实 HTTP provider 与 Dify workflow 哪个先接：现有代码都只具备候选 transport/mapping 证据，尚未证明已完成真实端到端调用。
