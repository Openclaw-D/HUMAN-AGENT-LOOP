# 见微-人机协同平台 V3 Direction 冻结稿

更新：2026-08-30  
状态：Direction 已冻结；Gate 1 至 Gate 19 已确认；Gate 11 价值口径已按专业意见更新并重新冻结；对应 D1 Control contract delta 已冻结，D2 实现与验收证据待同步

冷启动总纲：`V3_DIRECTION_HANDOFF.md`

## Gate 1：融资租赁唯一业务事项边界

结论：**已确认。**

V3 MVP 收窄并固定在融资租赁比赛场景。系统底层可以采用可复用的技术框架，但产品语义、领域对象、页面命名、流程阶段、证据类型、风险表达和演示内容必须落在融资租赁业务内，不能以“框架通用”为由扩张为通用 OA、通用项目管理、企业战略执行平台或其他金融业态。

### 权威边界

- `FinancingLeasingCase` 继续作为唯一业务事项权威对象。
- 一个项目只有一个 `caseId`、一条权威事件历史和当前 Context Version。
- 领导系统中的甘特图、时间轴和重点事项，只能是融资租赁 Case 关键里程碑的只读 Projection。
- 不新增通用 `KeyItem`、`StrategicInitiative`、`ProjectTask` 或其他第二类业务事项权威对象。
- 组织关系只决定领导可见范围；`PortfolioProjection` / `LeadershipProjection` 负责汇总，不产生第二份业务真相。

### 允许的“框架通用”

仅限领域无关的技术能力，例如 Event、Evidence、Context Version、Human Gate、Action、Receipt、权限、Projection、审计与失败关闭机制。对外呈现及具体领域模型仍使用融资租赁术语和业务约束。

### Gate 影响

后续四个 Role Application、Mobile / Desktop 响应式视图、God View 和演示闭环，都必须从同一个融资租赁 Case Authority 派生。任何需要第二类权威对象的需求，必须作为未来独立架构 Gate 重新评估，不进入 V3 MVP。

## Gate 2：Golden Case 与背景 Case 的演示边界

结论：**已确认。**

V3 MVP 采用 **1 个 Golden Case 完整演示闭环 + 少量背景 Case 支撑领导 God View**。演示重点是一个可追溯、可跨角色验证的融资租赁事项，而不是将多个项目伪装为同一份完整项目数据。

### Case 分层

- Golden Case 必须完整走通：业务采集、外部材料协同、政策、信审、商务、资产，以及领导系统的 KPI 观察、Shadow 推演与有权管理 Action。
- 背景 Case 必须各自拥有独立、最小化的合成 `caseId` 和只读摘要；用于 `PortfolioProjection` 的组合对比、阶段分布与异常排序。
- 背景 Case 不要求逐个准备完整的 Event、Evidence、Context Packet、跨角色动作和 Human Gate 链路；其详情若开放，也只能是与摘要一致的最小只读 Projection。
- 不得让多个背景项目在点击后共用或伪装为同一个权威 Case。每个 `caseId` 的摘要和派生状态必须可区分，保持多项目隔离语义。

### Gate 影响

- Backend 仍按 `caseId` 管理 Case Repository / Aggregate；Golden Case 仅是演示会话的 `focusedCaseId`，不是全局唯一项目。
- God View 只消费稀疏的 `PortfolioProjection`，默认不拉取背景 Case 的完整 Context Packet。
- 后续项目池、分组、检索、排序和详情入口都只能基于后端派生的只读字段，不能产生第二份项目状态。

## Gate 3：四角色的多 Case 面板与角色化 Case 工作台

结论：**已确认。**

领导、业务、风控、外部协同四个 Role Application 都必须同时具备两层产品结构：

1. **Case Panel / Case Directory**：用于查看、分组、检索、筛选和进入多个融资租赁 Case；
2. **Role Case Workbench**：点击某个 Case 后，进入该角色围绕同一 `caseId` 的详情、协同或处理空间。

### 共享权威与角色差异

- 四个 Role Application 共享同一个 Case Repository、同一批 `FinancingLeasingCase` 和同一个 Backend Authority Kernel；不得为不同前端复制后端数据或建立独立业务状态。
- 同一个 `caseId` 只能有一条权威事件历史、一个当前 Context Version，以及由该权威状态派生的多个 Role Projection。
- 四个 Case Panel 不是 identical dashboard。领导、业务、风控、外部协同依据组织范围、角色权限、当前责任和参与关系，看到不同的 Case 集合、摘要、排序、状态与入口动作。
- 点击同一个 `caseId` 后，各角色进入各自的 Role Case Workbench：业务负责采集、补件、回复与协调；风控覆盖政策、信审、商务、资产的判断与 Human Gate；外部协同处理受邀材料、问题与确认；领导进入 KPI 归因、组织反馈、Shadow 推演与有权管理 Action 空间。
- 业务账号可以看到同一 Case 的商机、政策、信审、商务、资产全部五路 Projection，以便承担全项目运营和跨专业协调；可见全路状态不代表业务可以替专业账号作正式判断。
- 风控 Role Application 内部存在政策、信审、商务、资产四类专业账号 / principal。四类账号都可以看到同一 Case 的全部五路状态、摘要与相互影响，但每个账号只能对自己职责对应的 Gate / Action 取得写入权限；其余板块保持只读观察，不得互相代签。
- 外部协同中的客户与供应商只看到自己当前被邀请的 workstep、Case 级起租大进度和与本次协同直接相关的问题 / 待办；不得展示内部五路专业判断、其他外部参与方材料或完整 Case Context。
- Mobile 与 Desktop 仍属于同一 Role Application；只改变布局、信息密度和展开层级，不改变 Case 对象、动作语义、权限或 Receipt。

### Gate 影响

- 领导 God View 是领导系统 Case Panel 的桌面高密度经营驾驶舱形态，负责把组织 KPI、时间下钻、组合偏差与 Case 归因连接起来；它不是唯一拥有多 Case 能力的系统。
- 后续前端信息架构必须同时设计“多 Case 导航层”和“单 Case 角色工作层”，不得把产品锁死为一个项目或一个处理面板。
- 所有 Case Panel 与 Workbench 均消费后端 Projection；前端筛选、分组、搜索和布局偏好不得成为权威业务状态。

## Gate 4：Golden Case 的五阶段 Case 主链

结论：**已确认；一级阶段名“商机”已正式锁定。**

V3 Golden Case 的产品主链固定为且只突出五个阶段：

> **商机 → 政策 → 信审 → 商务 → 资产**

“商机”是政策之前全部业务背景的统一且不可替换的两字阶段名。融资或购机动机、需求来源、初始客户背景、租赁物与交易方案、业务立项、前期尽调和外部材料导入都轻量归入商机阶段，不再拆成多个一级阶段，也不建设重型 CRM、供应链、采购、客户关系图谱或设备主数据系统。

上述箭头只表达宏观业务语义和前端信息组织顺序，不表示五部分必须以同步阻塞方式逐段运行。商机、政策、信审、商务、资产均是并行 Process Thread；商机不是单纯向后四路供数的独立前置框。五路候选分析采用 Gate 5 冻结的共享 Context 异步更新机制。

### 五阶段语义

1. **商机**：说明项目为什么产生、谁提出需求、客户需要购置设备还是利用已有设备获得资金、业务如何建立 Case，以及初始材料和关键假设是否足以进入政策判断；
2. **政策**：判断项目是否符合准入政策、行业边界和硬性规则；
3. **信审**：围绕客户偿债能力、经营事实、证据与风险完成信用判断；
4. **商务**：形成可执行的交易结构、价格条件、合同条件和放款/起租前提；
5. **资产**：覆盖设备交付、验收、权属、起租、租金履约、设备运行、价值变化、风险策略更新、重组与处置。

旧版材料与证据能力主要服务于商机后段和信审判断，是完整五阶段链路中的 Evidence 能力，不代表整个产品范围。

### 商机阶段的轻量边界

- 实控人、企业、厂长、下游、供应商和设备只作为解释购机动机、项目背景或材料来源所需的轻量字段、关系引用与 Evidence，不建设独立工作台、复杂关系网络或新的权威 Aggregate。
- V3 MVP 只保留推动融资租赁 Case 向下一阶段流转所必需的信息；不能因为背景中出现某类主体，就扩张相应的通用业务系统。
- 商机不是通用营销漏斗。它只表示一个融资租赁 Case 在进入政策前的项目导入与背景形成阶段。

### 单一 Case 与自动更新边界

- 五个阶段始终归属于同一个 `FinancingLeasingCase`、同一个 `caseId`、同一条权威事件历史和连续演进的 Context Version。
- 新材料、履约变化、资产状态或外部信号以 Event / Evidence 进入 Case，并触发相应 Projection 与策略候选更新。
- 系统和 AI 可以自动识别偏差、重新计算指标并提出候选，但模型 `authority=none`，不得静默改写权威事实、正式风险结论或处置策略。
- 需要正式生效的事实修正、策略调整、重组或处置动作，必须经过有权人员确认并生成 Human Gate / Receipt。

### Gate 影响

- 后续 Case Panel、Role Workbench、阶段导航、演示脚本和后端 Stage Projection 均以这五个阶段为一级主链，不再增加“客户、供应商、设备、交付、起租、存续”等并列一级阶段。
- 前端可以在某个阶段内部展示子步骤、材料或里程碑，但它们不得改变五阶段信息架构，也不得成为第二套权威状态机。
- 背景 Case 仍只需提供与五阶段、关键里程碑、风险和异常一致的最小只读 Projection，不要求复制 Golden Case 的完整证据链。
- 后续若要引入独立 CRM、采购、供应链或资产管理权威系统，必须另开架构 Gate，不属于 V3 MVP 默认范围。

## Gate 5：Golden Case 合成样本与共享输入异步五路输出

结论：**已确认。**

V3 Golden Case 采用一个固定、版本化且可重复执行的合成场景包，作为产品端到端测试与演示的输入样本。由于真实完整过程数据位于内网且不能提供，场景包只能依据真实业务过程、角色、步骤、控制点和材料类型进行 process-faithful reconstruction（流程忠实的合成重建），不得宣称为真实客户案例、真实历史过程数据、统计验证样本或生产运行证据。

### 前端沉浸与后端数据来源边界

- V3 Demo 的业务前端不显示“模拟数据”“合成数据”等页面水印、徽标、提示条或重复免责声明，保持完整的内网产品沉浸感和演示质量。
- 合成属性必须保留在 Backend Scenario Package、数据清单与审计元数据中，明确记录数据分类、场景版本、来源说明和不包含真实客户数据的事实；不得在后端将其伪装或登记为真实内网数据。
- 前端不标注不等于可以对外宣称已接入真实内网、真实客户数据或生产系统。演示的 prototype / Demo 语境由比赛介绍、演示开场或交付说明承担，不侵入业务页面。
- 后续截图或页面被单独传播时，数据来源说明由页面外的演示材料或交付上下文承担；V3 MVP 不为此增加业务页面内的常驻标识。

### 固定输入与稳定输出

- Golden Case Input Package 应覆盖商机初始背景、分批进入的材料与事实、人工确认脚本、规则版本，以及后续履约或资产变化信号。
- “固定输入”不表示所有材料在演示开始时一次性暴露。完整场景预先版本化，但具体信息按照预定事件时间线分批进入 Case，以真实呈现补件、校验、事实更新与重新判断。
- 场景设计阶段允许依据验证结果持续调整；进入正式演示版本后，任何输入、规则或人工脚本变更都必须生成新版本，不得静默覆盖既有版本。
- “稳定输出”指在相同 Input Package、规则版本与人工确认脚本下，应得到可重复的权威 Event、Context Version、结构化阶段结果、Human Gate / Receipt 与 Role Projection；AI 自然语言表达可以存在非权威差异，但不得改变正式结构化结果。
- 最终输出不是一次性“通过/拒绝”答案，而是由五部分结果、证据依据、未决问题、人工确认和资产后续状态组成的可追踪、可解释、可回放 Case Lifecycle Record。

### 共享确认输入与异步五路运行

- 来自商机、政策、信审、商务、资产任一路或任一有权角色的信息，先在完成相应校验后形成共享 Evidence / Fact Receipt；只有具名人员对一个逻辑批次执行 `ContextCommit`，才写入同一个 `caseId` 的新 Context Version。
- 每次 Case Context Version 更新都必须形成统一 Trigger，驱动商机、政策、信审、商务、资产五个 Process Thread 读取同一份已确认 Context，并分别自动触发或更新各自的 candidate run；不得为五部分复制五份输入真相或建立五条彼此分叉的权威 Context Version。
- 五个 Thread 可以异步并行运行、独立完成并在不同时间返回结果。一个 Thread 尚未完成、需要补件或运行失败时，其他 Thread 的有效结果仍可独立展示；系统不得伪装为五路同时完成。
- 每个输出必须明确绑定 `caseId + contextVersion + processId + runId`，并显示运行状态、结果版本、更新时间、是否需要人工确认及是否已被新 Context Version 取代。
- 新输入形成新 Context Version 后，旧输出保留为审计历史并标记为过期或已取代，不能与新版本结果混合形成正式结论。
- 前端必须实时呈现五路独立状态和已返回结果，使用户看见同一确认输入如何同时触发商机推进与四个专业板块的更新，而不是只显示一个最终汇总答案。

### 五路可逆进度与风险分离

- 每个 Process Thread 都维护基于当前 Context Version 的 readiness（就绪度 / 距离本部分完成条件的程度）。新信息通常可以提高 readiness，但新的高风险事实、证据矛盾或补件要求也可以使某一路 readiness 回退。
- readiness 不是单向任务完成百分比。某一路已经推进后，若新 Evidence 使其需要补充核实或重新判断，前端必须真实显示回退，不能只增不减。
- 风险水平、readiness、Evidence 覆盖度和模型置信度必须分别表达，不得压缩成同一个分数。例如高风险涉诉材料可以同时造成信审风险上升、readiness 下降和新增补件 Action，但三者是不同状态变化。
- 任一路的更新结果必须由相同 Context Version 的 Evidence 与规则解释，并可追溯说明“为什么上升、为什么回退、还缺什么”。

### 权威边界

- 异步自动运行产生的均为商机、政策、信审、商务或资产候选输出，模型 `authority=none`；自动触发不等于自动生效。
- 正式事实修正、阶段结论、业务动作或处置策略仍需对应的有权人员通过 Human Gate 确认并生成 Receipt。
- 本 Gate 只冻结“一个权威 Case Context、异步五路候选输出、可逆进度、前端独立呈现”的运行模型；五路候选如何过期、如何人工确认、何时允许形成正式生效结论，留待 Gate 6 继续确认。

## Gate 6：五路实时协同、可回放版本与分级 Gate

结论：**已确认。**

商机、政策、信审、商务、资产是五个并行且持续更新的 Process Thread。任何真正改变 `FinancingLeasingCase` 权威 Context 的新信息，都必须由 Backend Authority Kernel 形成一次统一 Trigger，驱动五路基于同一版本重新判断；前端实时显示已经返回的部分结果，不等待五路全部完成。

### 基础快照、Diff 与版本分层

- Backend 采用不可变 Base Snapshot + append-only Diff / Event + periodic checkpoint snapshot 的组合保存 Case 历史，不在每次变化时复制一整份 Case。
- `scenarioVersion`（例如 `V0.1`）表示 Golden Case 输入包、规则与演示脚本的人工可读发布版本，只在场景契约变化时更新。
- `contextSeq` 是后端内部单调递增序号，只在具名 `ContextCommit` 成功时推进；单条 Evidence 接受、Human Gate、Management Action、正式起租 Action 与其他 Receipt 均绑定当前 Context，不为了记录动作而制造额外版本号。
- 五路各自的 Process Run / Projection Version 必须绑定同一个 `contextSeq`。新 `contextSeq` 产生后，旧结果保留审计但标记 stale；迟到的旧版本结果不得覆盖当前页面。
- 重复提交、幂等重试、页面刷新、普通聊天、Agent 思考、运行进度和未确认候选结果不得推进 `contextSeq`，避免输出再次触发自身而形成无限循环。
- 系统必须能够从最近的 checkpoint snapshot 加后续 Diff / Event 重建任一历史状态；snapshot 是回放加速与历史检查点，不替代 Event 权威。
- checkpoint 的具体频率留给后续技术契约配置，可按关键里程碑、事件数量或时间周期生成；不得静默覆盖既有 checkpoint。

### 实时部分结果与起租五格状态带

- 五路异步运行时，任何一路完成上传处理、候选分析或人工确认，都应在结果产生的瞬间独立刷新；未完成、处理中、待补件、待确认和已完成可以同时存在。
- 前端不显示精确百分比。Case 级主视图使用一条由五个等宽背景色块构成的 coarse commencement band（粗粒度起租就绪带）：未达到的区块为白色，已达到的区块为黑色。
- 五格属于整个 `FinancingLeasingCase`，不是为商机、政策、信审、商务、资产各自复制五条进度带，也不等同于五个 Process Thread 的完成数量。
- 五格只表达距离交易生效和正式起租的大致就绪层级，不向用户宣称精确的 20%、40%、80% 等数学测量；内部以 `commencementBand = 0..5` 表达即可。
- 五格不与五个 Process Thread 一一映射，也不要求五路线性串行。资产工作可以在其他专业判断尚未完全结束时提前开展；色块由整体起租条件和关键里程碑派生。
- Golden Case 完成交易生效、正式起租并开始产生利息时，整体五格全部变黑，显示“起租完成 / 已起息”。起租后的还款、开票、资产管理与最终结清不再占用或压低该起租状态带。
- 已经发生的起租里程碑不能因后续风险被前端抹除或倒退。某一路的 readiness 回退、补件、逾期或风险上升通过该 Thread 的状态、异常提示和 Collaboration Dock 表达，与 Case 级 commencement band 分离。
- 五路运行中的瞬时处理状态使用文字、活动状态或实时消息呈现，不使用精确百分比。

### 分级 Gate 与最少人工占用

- 每一路候选结果依据动作影响、可逆性、规则确定性、Evidence 充分度、冲突、例外和权限要求，选择相应 Gate Mode；不得仅凭模型置信度决定是否绕过人工。
- `AUTO_PROCESS`：格式与安全校验、提取、计算、去重、规则匹配、Projection 更新、候选补件和其他低风险确定性处理由机器自动完成，不占用人工；这些动作不等于模型获得正式业务决定权。
- `HUMAN_CONFIRM`：系统完成证据整理、分析和推荐后，由有权人员快速核对并明确确认，适用于标准事实或证据充分、无重大冲突的常规专业结论。
- `HUMAN_DECIDE`：高风险负面事实、证据冲突、政策例外、非标准条件、低证据充分度以及否决、重组、处置等高影响动作必须由人作出实质判断。
- 每个需要人工参与的 Gate 至少明确 Gate Mode、触发原因、所需角色、关键 Evidence、拟议 Action 和确认结果；机器负责准备工作量，人只处理权威确认与例外。

### Five-Thread Collaboration Dock 与最小必要 Context

- 右下角聊天框定义为 Five-Thread Collaboration Dock，而不是通用客服 Chatbox。它连续呈现商机、政策、信审、商务、资产五路中“专业人员 + 对应 Agent”的处理、提问、补件、候选结果和人工确认。
- 五路共享同一个 Case Authority，但每个角色只能接收与其职责、权限、当前问题和参与范围匹配的 Role Projection / Context Packet；共享 Context 不等于向所有人暴露完整原始材料。
- 业务角色拥有五路全局可见性和最完整的项目运营 Context，但仍受数据权限和敏感字段边界约束。风控四类专业账号同样可以看到五路状态、摘要和相互影响；进入某个 Evidence、原始材料、对话或待判断任务时，仍只接收完成本次职责所需的最小 Context Packet，不因全局可见性获得跨专业写入权。外部账号只接收当前受邀 workstep 的最小 Context。
- 用户通过 `@` 指向某个人或专业 Agent 时，Backend 必须依据 `caseId + contextSeq + principalRole + targetRole / process + question + permissions` 生成精准的 task-scoped Context Packet，并附带必要 Evidence 引用；不得由前端直接拼接或发送整份 Case。
- 机器可处理的任务由对应 Agent 使用 task-scoped Context 自动完成并返回候选结果；不能因为自动处理方便，就扩大其材料访问范围或业务 Authority。
- 普通聊天、Agent 思考、处理进度和候选讨论属于实时 Collaboration Projection / advisory record，不直接改变权威 Context。

### 明确确认后才允许 Trigger 五路

- 上传材料、确认事实、接受 Action、完成 Human Gate 或执行其他权威写入，必须先以待提交状态展示，并明确询问有权用户是否确认。
- 确认界面必须使用户知道将写入什么、依据什么 Evidence、作用于哪个 Case / Context，以及确认后会触发五路重新判断；不得用普通发送消息动作暗中代替业务确认。
- 只有用户明确执行 `ContextCommit` 且 Backend 完成权限、预期版本、幂等性和数据校验后，才可原子地追加 Context Event / Diff、生成 ContextCommit Receipt、推进唯一 `contextSeq`，并由 Backend 发出五路更新 Trigger；其他 Human Gate / Action 生成各自 Event 与 Receipt，但不自动推进 Context。
- 普通聊天、输入中的草稿、未确认上传、Agent 候选与运行状态不能触发五路权威更新。版本冲突或校验失败必须失败关闭，刷新最新 Context 后重新预览和确认。
- 五路之间不得直接改写彼此结果。补件、核实或冲突处理必须回到共享 Evidence / Fact 和明确确认流程，再通过新 Context 统一触发下一轮。

### Gate 影响与未决边界

- 后续前端必须实现起租五格状态带、实时部分结果和角色化 Collaboration Dock，但具体尺寸、动画、头像和布局留到信息架构与视觉契约阶段。
- 后端必须把聊天 Projection、Agent candidate、权威 Event、Context trigger 和 Human Receipt 分开建模，不能以一份聊天记录代替业务状态。
- 五路独立结果在交易生效、起租和租后存续期间仍可持续更新；不得把一次五路分析完成误写为整个融资租赁 Case 的最终结束。唯一成功终点由 Gate 7 定义。

## Gate 7：起租五格完成与租后独立存续

结论：**已确认，并按用户纠正区分起租完成与全周期关闭。**

领导视角首先关心融资租赁项目是否正式起租并开始产生收益。Golden Case 满足合同生效、向供应商付款、供应商向租赁公司开具相应销项发票以及项目约定的其他起租条件后，即形成正式 Lease Commencement，并在前端显示五格全黑。Case 的后续还款、开票、资产管理和最终结清继续存在，但作为独立的租后存续状态管理，不再干预已经完成的起租五格。

### 起租五格与领导成功节点

- 政策、信审、商务和资产在交易前可以并行形成候选与 Gate 结果；资产相关核验或准备可以提前开始，不能把五路强行画成线性瀑布流程。
- 起租五格全黑表示“交易已经成功形成、正式起租并开始产生利息”，是领导 God View 的核心正向里程碑；它不是精确的 100% 数学测量，也不等于后端 Case 已经关闭。
- 政策与信审可以在起租前形成当时版本的正式判断；商务和资产在起租后仍保持 active，继续承载收款、开票、履约、设备状态、风险策略和存续管理，但这些租后活动不再降低或重新打开起租五格。
- 起租后任何新 Evidence / Fact 仍更新唯一 Case Context，并 Trigger 五路重新判断；已完成的专业板块可以返回“结论不变”，但不得退出共享 Context 更新机制。

### 租后状态与最终关闭

- 起租后使用独立的 lease lifecycle status（租后存续状态）、风险与异常表达还款、开票、资产状态和处置，不再继续计算或展示起租百分比。
- 当本金全部结清、应收利息全部收回、应开票事项完成、全部商务流程收口、资产权属或期末状态完成处理，并且不存在阻断关闭的未结 Action 时，Backend Authority Kernel 根据可验证事实和必要 Receipt 生成正式 Lifecycle Closure Event。
- Lifecycle Closure 是后端融资租赁 Case 的全周期成功关闭状态，但不再承担“点亮第五格”的职责；五格早已在起租时全黑。前端通过“正常在租、还款中、已结清、已关闭”等独立状态表达租后位置。
- 起租完成、租后存续和最终关闭必须分别留有里程碑 Event / Receipt，不能因为领导主要关注起租，就丢失后续全周期历史。

### Gate 影响

- 前端必须分别表达“当前五路运行状态”“Case 起租五格状态”和“租后存续状态”，不得把三者混为一个进度指标。
- 稳定输出需要覆盖至少两个关键 checkpoint：起租成功时的五格全黑与最终结清时的 Lifecycle Closure；前者是领导核心收益节点，后者是后端全周期关闭。
- Golden Case 演示数据和事件时间线必须包含起租后的履约、收款、开票与最终结清事件，否则只能证明交易前闭环，不能宣称完成全周期演示。
- 非正常终止、违约、重组、核销或资产处置不改变已发生的起租五格；它们如何映射租后状态与 Closure，不在本 Gate 中推断，后续只有确需进入 V3 MVP 时再单独确认。

## Gate 8：起租 100% 的商务主线、条件化顺序与资产辅助预判

结论：**已确认；具体五项子流程暂不硬编码。**

V3 主进度的唯一完成目标锁定为正式起租。商务是推动交易生效、付款和起租的主执行线；资产在起租前主要提供设备、查验、未来风险与巡检时点的辅助预判断，不作为压低起租完成度的第二条重型主线。五路仍共享 Context 并并行更新，但其内部步骤可以因项目与供应商条件不同而采用不同顺序。

### 五路产品权重

- 商机、政策、信审、商务、资产都保留各自五个可配置内容槽，但五路在 V3 中不是等权、等密度页面。
- 商机与信审在产品层面同等重要，都是 V3 的重型 Workbench。商机承载项目背景、材料导入、业务协同、事实形成和进入后续判断前的大量问题；信审承载材料、Evidence、专业判断、补件、冲突和 Human Gate。
- 当前演示中信审可以因用户掌握的业务经验更多而做得更真实、更贴切，但这属于内容成熟度差异，不代表信审在产品架构上高于商机。
- 商务是推动付款与正式起租的主执行线，产品权重低于商机 / 信审但高于资产，必须清楚表达交易条件、未满足前提和起租结果。
- 商机中的真实耗时、常见问题和信息密度可在后续获得内网过程数据后继续提炼，本轮先搭建与信审同等级的容器和交互骨架，不凭猜测填满具体流程。
- 政策以规则、准入、例外和影响解释为主；资产在起租前以辅助预判、查验建议和未来风险窗口为主，均不复制信审的重型材料判断页面。
- 产品权重只影响前端默认焦点、信息密度和交互深度，不改变五路共享 Context、独立 Gate、权限与审计要求，也不代表某一路拥有更高业务 Authority。

### 商务完成与 Lease Commencement

- Case 级 `commencementBand` 的五格全黑只由正式 Lease Commencement Event 驱动。前端不得自行根据某个按钮或单一付款字段直接改成完成。
- 在 Golden Case 中，合同正式生效、向供应商付款成功、供应商按项目要求向租赁公司开具相应销项发票，以及其他已配置起租条件共同构成起租依据；具体条件和先后顺序由版本化的 Commencement Condition Set 决定。
- 商务 Thread 的起租前流程以“交易条件落实、付款成功并满足起租条件”为完成目标。付款成功通常是领导最关注的末端商务信号，但是否足以单独触发起租必须由当前项目条件集判断，不能在所有 Case 中硬编码为同一规则。
- 一旦 Backend 验证必要条件并由有权人完成相应 Human Gate / Receipt，即生成 Lease Commencement Event，五格全黑并显示“起租完成 / 已起息”。租后活动不再降低该状态。

### 条件化付款与非线性顺序

- 商务与资产不采用一条全项目通用的固定线性顺序。V3 只冻结一个 mode-aware condition graph（业务模式感知的条件图）能力，用于表达不同融资租赁模式下付款、权属、到货、查验、开票、合同与起租条件之间的关系。
- 直接租赁内部可以存在货到查验后付款、经批准的预付款等不同顺序；新设备售后回租则会出现客户将设备权属转移给租赁公司、租赁公司向客户支付价款并再租回的不同交易关系。上述内容用于证明不能硬编码单一路径，不在 V3 Direction 中继续冻结具体节点与先后。
- 直接租赁与售后回租在当前战略层面均属于一级重要模式，不再把售后回租降为 V4 才考虑的边缘模式。V3 MVP 仍不要求同时制作两条完整 Golden Case 证据链；最终 Golden Case 采用哪种模式或如何安排背景 Case，依据集团导向调研与演示内容真实性另行决定，不得用当前演示样本反向声明业务战略优先级。
- 供应商资质、合作历史、租赁模式和设备权属只作为当前 `FinancingLeasingCase` 的轻量 Evidence / 条件输入，不因此建设重型供应商主数据、采购、供应链或独立权属系统。
- 不同模式和顺序可以变化，但任何正式付款、权属确认与起租仍必须绑定 Evidence、Context Version、Human Gate 和 Receipt，Authority 与审计标准不能降低。

### 资产的起租前辅助预判断

- 资产 Thread 的起租前角色是辅助项：判断租赁物适格性和基础状态，提出是否需要付款前查验，并基于当前信息预测未来更可能暴露风险的时间窗口与重点部位。
- 资产候选输出可以包含风险窗口、触发依据、建议线下巡检时间、巡检重点、待补 Evidence 与建议 Action；它用于帮助商务与资产人员安排验证资源，不是对未来风险的确定性承诺。
- 资产 Agent 可以自动完成规则匹配、时间窗口计算和巡检建议；涉及是否放弃付款前查验、正式安排线下行动或改变付款条件时，仍按 Gate 6 的 Gate Mode 进入相应人工确认。
- 资产起租前流程以“已形成足以支持当前付款与起租条件的资产判断”为末端，不单独控制 Case 五格。若当前 Payment Condition Plan 明确要求资产查验，则相应 Evidence 未完成时可以阻断付款和起租；没有该前置要求时，资产预测本身不阻断商务完成。
- 起租后，资产 Thread 转入独立的租后存续与风险监测，不继续占用起租进度；后续巡检、风险策略和资产状态仍通过共享 Context 触发五路更新。

### 五项子流程的暂缓边界

- 商机、政策、信审、商务、资产各自内部可以保留五个 centrally configurable flow slot（集中可配置流程槽），但具体名称、顺序、必选条件和 Gate 不在本轮凭经验硬编。
- 特别是资产的五项内容，需要结合实际租赁物管理、付款条件、查验、起租与租后工作继续学习和确认；当前只冻结“起租前辅助预判、条件需要时形成阻断、起租后独立存续”的职责边界。
- 后续前端可以先依据已冻结语义设计可配置容器，但方向冻结前不得用占位名称冒充已确认的真实业务流程。

### Gate 影响

- 领导 God View 的项目主进度以正式起租为 100% / 五格全黑，不因资产租后流程尚未结束而停留在四格。
- 商务 Workbench 必须能够容纳不同项目的条件化付款路径；资产 Workbench 必须突出辅助预测、查验建议和风险窗口，而不是复制一套线性审批页面。
- V3 Direction 不再讨论 Golden Case 采用货到付款还是预付款等具体路径；该选择属于后续演示数据和后端条件契约，不改变当前宏观架构。

## Gate 9：共享前端骨架与可插拔 AI-Native 路由

结论：**已确认，并授权开始有限前端实施。**

在 Gate 10 的前后端 Projection / API 契约继续收敛前，V3 先完成一个可运行、可替换且不复制业务真相的前端骨架。该骨架必须证明四个 Role Application、五路 Process Thread、Case 导航、实时协同和现有 Backend Authority 可以被同一套路由连接；它不是只画静态概念，也不在本轮深挖尚未确认的具体流程内容。

### 本轮允许实施

- 复用现有 `jianwei-v3/site` 前端代码库、设计基础、启动方式和已存在的后端能力，不重新初始化项目，不新增第二套前端或第二个业务后端。
- 建立共享 Case Shell：Case Panel / Directory 入口、单 Case Workbench、Case 基本信息、起租五格、五路状态与右下 Five-Thread Collaboration Dock。
- 建立领导、业务、风控、外部协同四个 Role Application 的共享路由与 Role Projection 骨架；同一 `caseId` 在不同角色下进入不同工作中心。
- 业务角色展示全部五路；风控应用提供政策、信审、商务、资产四类账号 Projection，四类账号均展示全部五路但只开放本专业 Gate；外部客户 / 供应商 Projection 只展示当前受邀 workstep、Case 大进度与当前问题。
- 商机与信审按同等重型容器设计；当前信审允许使用更成熟、更贴近实际的示例内容，商机保留同等级结构和未来替换能力。商务作为起租主执行线，资产作为辅助预判，政策作为规则与例外入口。
- 五路各自保留五个 centrally configurable flow slot，但本轮只实现稳定容器、状态、路由和替换接口，不冻结或伪造具体名称、顺序与规则。
- 复用现有后端只读 Projection、Context / Event / Receipt 能力和适配层；只有支持骨架运行所必需的窄小修正才允许进入后端，禁止大规模改写或另建状态源。

### AI-Native 高速公路边界

- 五路 Process Thread 的具体步骤、判断和工具能力最终以可配置 Skill / Agent capability 注入共享框架，而不是把每一种业务路径硬编码进页面组件。
- 前端路由负责把 `caseId + role + process + contextVersion + task` 传递给后端派生的 Context Packet、Agent candidate、Human Gate 与 Receipt；前端不得自行拼装权威 Context 或把聊天内容直接写成正式事实。
- 框架必须能够呈现 shared input -> five-process trigger -> partial result -> targeted @ context -> explicit confirmation -> new Context 的循环，即使本轮暂时复用现有模拟 Adapter，也必须保持接口、状态和 Authority 语义可替换。
- “AI-native”在本轮的验收标准是路由、状态、版本、角色范围和 Human Gate 能实际串联并运行，不以页面文案、Agent 头像或静态聊天气泡冒充技术闭环。

### 本轮明确不做

- 不确定商机、政策、信审、商务、资产各自五项内容的正式名称、顺序、算法和业务规则。
- 不完整实现预付款、货到付款、新设备售后回租等多种交易路径；只保留 mode-aware / configurable 的容器能力。
- 不大改 Backend Authority Kernel，不复制 Case 数据，不削弱 Event、Context Version、权限、Human Gate 和 Receipt。
- 不部署、不提交、不推送，不接入真实内网、真实客户数据或真实产品模型凭据。

### 本轮停止条件

- 首个可运行前端骨架完成本地测试、lint、build 和真实浏览器验收后停止，不继续补写未冻结的深层业务页面。
- 下一步回到 Gate 10，冻结前后端 Role Projection、Process Run、Collaboration 与 Commencement 的共享数据契约，再决定下一轮联调实现。

## Gate 10：比赛 Demo 交付等级与内网产品化停止边界

结论：**已确认。V3 当前只建设可流畅演示的比赛 Demo，不提前建设完整内网生产系统。**

### 当前唯一交付目标

- 当前目标是让领导与比赛观众能够通过一个完整、流畅、可理解的 Golden Case 演示，看清融资租赁 Case 如何从信息输入开始，经商机、政策、信审、商务、资产五路人机协同、明确人工确认和正式起租结果，被同一套 AI-Native 路由串联起来。
- 前端是当前交付重点，必须把 Case Panel、四个 Role Application、角色权限、五路状态、关键材料、当前问题、Agent 候选、Human Gate、Receipt、起租五格和领导 God View 做到高完成度、高一致性与高演示可读性。
- “前端做到极致”指演示路径、信息层级、角色差异、视觉、交互、状态反馈和跨页面连续性足以支撑正式比赛展示；不表示用静态页面伪装后端结果，也不允许出现无法按步骤运行的空壳按钮。

### Demo-grade Backend 边界

- 后端只需提供让固定合成 Golden Case 按演示脚本稳定走完整流程所需的基础逻辑：固定 / 版本化输入、必要 Context、Event、Evidence、Process 状态、Human Gate、Action、Receipt、Projection 和可重复输出。
- 本阶段验收重点是 happy path（主演示路径）能够稳定、流畅、可复现地完成，并具备足以避免演示中断的基础校验、幂等性、错误反馈和状态恢复；不以生产级高并发、高可用、完整安全治理或长期数据运维作为比赛 Demo 的完成条件。
- 当前不建设真实政策规则部署库、信审模型开发平台、商务核心执行系统、资产管理系统、生产数据库、完整 RBAC、集团级集成平台或真实内网接口。专业规则、真实数据与具体接口留待未来进入内网后，由实际系统和专业团队提供。
- V3 可以保留清楚、可替换的 Adapter / interface 形状，保证未来能够接入内网系统；但不得为了假设中的未来接口提前开发重型 Backend、复杂插件生态或完整生产基础设施。
- 比赛 Demo 可以使用固定合成数据和受控模型 / deterministic adapter 形成稳定输出。不得把未执行的动作、失败的调用或静态文案伪装成已经取得 Backend Receipt 的正式结果。

### 三阶段路线

1. **方向收敛与 Demo 建设**：先把产品边界聊清楚，完成前端主体验和能够支撑完整演示的最小后端闭环。
2. **演示修正与决赛打磨**：依据实际试演、用户反馈和比赛表达修正交互、内容、流程与稳定性，形成决赛版本；不在此阶段扩成内网生产系统。
3. **赛后内网产品化决策**：只有决赛演示完成并取得继续推进的明确结果后，才评估真实内网数据、专业规则库、生产系统 Adapter、安全、权限、数据库、运维与组织协作。该阶段必须重新立项和冻结架构，不属于当前 V3 Demo 授权。

### Gate 影响与停止条件

- Gate 10 之后的实现优先级固定为：前端演示质量与角色连续性 → Golden Case 端到端流畅性 → 必要的 Demo 后端稳定性 → 文档与演示脚本。任何生产化扩展必须排在当前范围之外。
- 后续不得再以“未来可能进入内网”为理由扩大当前后端范围；只有当前 Demo 出现真实阻断时，才允许做最小必要后端修正。
- 当前不再讨论完整生产后端、专业系统替代或内网部署方案。下一轮只应冻结并实现决赛 Demo 的页面 / 场景路线、固定输入、稳定输出和验收脚本。

## Gate 11：当期 / 年度净收入主线、全周期利润辅助校验与直租 / 回租同等战略地位

结论：**已确认。领导经营优先服务当期与年度 KPI：以可验证净收入与单位资产产出效率为主；全周期利润作为辅助判断与防止短期透支的约束。短期为主、长期为辅，二者兼顾。随着财务、费用、人力和风险系统逐步接入，再把预测利润持续收敛为可审计结果。直接租赁与售后回租在集团进一步调研前同等重要。**

### 年度经营优先与长期辅助校验

- 当前可验证的经营主指标是当期、当年或全周期净收入。统一基础公式为：`净收入 = 对应期间总收入 - 资金成本 - 渠道成本 - 附加税`；本口径不包含项目人力成本、非人力成本、风险成本或风险拨备。任何展示必须携带时间范围、公式版本、数据来源和实际 / 预测属性。
- 单位资产产出效率使用 `净收入 / 起租金额` 表达，产品名称优先使用“单位起租金额净收入率”或“单位生息资产净收入产出”，不得在尚未扣除全部运营与风险成本时将其包装为完整 ROI 或最终盈利能力。
- 当期已入账数据可以形成 `actual`；当年未结束部分与尚未完成的全周期结果只能形成 `forecast`；固定参数推演只能形成 `scenario`。预计费用只有在真实报销、入账或受控来源确认后才能转为实际成本，系统必须保留预计值、实际值和预实偏差。
- 领导 God View 默认优先回答“本期 / 本年 KPI 到哪里、应达到哪里、差多少、由哪些 Case 贡献或侵蚀、现在组织谁行动”。当期和年度净收入及单位资产产出效率占据主视觉与主下钻路径；这反映年度经营绩效、激励和下一年度稳定发展的真实管理需要。
- 全成本、全风险、全生命周期净利润是辅助校验和防止短期透支的约束，不与当期 / 年度 KPI 争夺主驾驶舱。只有财务引擎、费用 / 报销、薪酬、人力、资产管理和风险等系统逐步接入并完成对账后，预测利润才可以持续收敛为可审计结果；当前外网 Demo 只显示辅助预测、缺失数据和长期影响提示。
- 规模、投放、项目数量、起租速度、风险识别、客户体验、厂商粘性与渠道转化分别属于净收入 driver、风险 / 专业约束或长期利润 driver，不得与不同计量层级混成一张无法解释的最高目标清单。
- AI-Native 技术的战略作用是在商业租赁资金成本不占优势的情况下，通过更快消除不确定性、更一致地判断风险、更低的运营成本和更强的客户 / 渠道协同，先提高可验证净收入与单位资产产出效率，再提高公司获得可持续全周期利润的能力；不得宣称技术可以直接消除资金成本与资产负债表差距。

### 直接租赁与售后回租

- 直接租赁与售后回租当前均为一级重要的融资租赁模式。集团与最高领导层对两者的实际战略排序尚需进一步调研，本阶段不得由产品团队单方面推断直租优先或回租优先。
- 当前对直接租赁的业务理解与可用演示内容更成熟，可以用于提高 Demo 的真实性和完整度；这属于 content fidelity，而不是战略优先级证据。
- 售后回租面向客户利用已有设备获得资金的需求，可能具有更高定价空间，也伴随更高风险和更强管理要求。V3 必须在模式层面平等容纳回租，但在调研与真实流程确认前不凭猜测补写完整回租规则和 Evidence。
- 从客户融资需求看，银行贷款、金融租赁、商业租赁和其他设备融资方案属于直接竞争选择；从交易结构、权利关系和专业管理看又不能混为同一产品。见微保持融资租赁 Case 语义，不把售后回租错误建模为普通抵押贷款。
- 商机来源保持 channel-agnostic（渠道无关）：可以来自厂商推荐、客户直接申请或其他合作渠道。来源不改变唯一 Case Authority，也不决定直租 / 回租的战略等级。

### Gate 影响

- 当前不切换或复制 Golden Case，不因本 Gate 启动前后端修改。Golden Case 最终模式属于后续集团导向调研后的宏观决策。
- V3 架构与叙事必须同时容纳直接租赁和售后回租，但比赛 Demo 仍坚持一个 Golden Case 完整闭环，不为了表现均等重要而制作两套重型演示。
- 后续领导 God View 与 Case 评价必须以当期 / 年度可验证净收入和单位资产产出效率作为主线，以全周期利润作为辅助校验；规模、速度、风险与体验只能解释价值如何形成或被侵蚀，不能替代明确的计量口径。

## Gate 12：设备锚定的小微融资租赁生态位与差异化风险路径

结论：**已确认。V3 服务融资租赁牌照与小微事业部边界内、具有真实设备 / 租赁物基础且可以被专业穿透判断的企业；不泛化为面向所有缺钱企业的通用融资平台。**

### 核心生态位

- 公司的目标客群不是所有融资困难或被银行拒绝的企业，而是银行标准化体系难以高效判断、但能够借助制造业、设备与属地化专业能力降低信息不对称，并能形成可验证净收入与可持续全周期利润潜力的小微企业。
- 设备 / 租赁物是融资租赁 Case 的必要业务锚点。客户必须存在可识别、可形成相应权属或交易 Evidence 的设备基础；没有任何适格设备或租赁物基础的纯服务业融资需求，不进入本系统的目标经营边界。
- V3 不把融资租赁扩写为通用信贷，也不把监管边界或额度放大方式产品化为核心能力。具体适格性、价值、发票、权属、额度与例外如何判断，留给后续真实政策、专业规则和有权 Human Gate，本阶段不硬编码。
- 精准生态位的目的不是追求最大的可服务客群，而是在整体市场中识别融资意愿、设备基础、可穿透性、风险定价、净收入产出和长期利润潜力相匹配的客群，提高有效获客与风险调整后的价值创造能力。

### 小微客群的三类一级经营路径

- 直接租赁、存量客户回租与新客户回租构成小微事业部当前需要平等容纳的三类一级经营路径；它们共享唯一 `FinancingLeasingCase`、五路 Process Thread 和 Authority Kernel，不建立三套后端。
- 存量客户回租指已有合作与履约信息基础上的再次合作，通常具有更低的信息不确定性；新客户回租指缺少既往合作历史的回租项目，通常具有更高价格空间、更高风险和更强的属地化现场尽调要求。
- 标准化、可模型化的产品可以采用更轻、更线上化的判断路径；复杂项目和新客户回租可以采用更强的现场验证路径。二者是同一平台中的 mode-aware risk path，不是两个产品或两套 Case Authority。
- 三类路径的战略存在性在本 Gate 中冻结，但不冻结具体产品名称、准入规则、额度、报价、现场尽调步骤或内部组织分工；这些属于后续 Control 与真实业务校验内容。

### Gate 影响

- 商机入口必须首先回答“是否属于融资租赁可服务边界、是否存在设备锚点、应进入哪一类经营路径”，然后才触发共享 Context 下的五路并行判断。
- Case Panel 与领导 God View 后续需要支持按租赁模式、客户关系、标准化 / 复杂路径及风险收益特征形成只读 Projection，但不得因此新增通用客户、设备或项目管理 Authority。
- V3 的核心竞争叙事锁定为：以融资租赁与设备专业能力识别并服务被标准化金融体系低效覆盖的优质小微融资需求，优先提升当期 / 年度可验证净收入与单位资产产出效率，同时用全周期利润预测校验长期影响；不是以更高风险换取表面高收益。

## Gate 13：领导优先的 KPI 经营驾驶舱与权威管理 Action

结论：**已确认，并正式纠正此前“领导系统纯观察者”的边界。领导端是决定比赛说服力的核心 Role Application，可以在融资租赁生态内形成带 Authority、Human Gate 与 Receipt 的管理 Action。**

### 领导经营视角

- God View 的核心不是单纯查看项目进度或只按预期利润排序，而是呈现集团对租赁公司、租赁公司对事业部逐级传导的量化 KPI，以及目标、按当前时间应达值、实际值、差值、趋势和主要偏差来源。
- God View 默认以本期 / 本年 KPI 为主：突出可验证净收入、单位资产产出效率、目标、应达、实际 / 预测、差值和主要 Case 归因；全周期利润位于辅助校验层，用于提示长期影响、数据缺口和短期行为是否可能透支未来。规模、投放、合规、风险、资产质量、运营效率等作为经营约束和 KPI driver 共同展示，不得把单一规模或速度包装为成功。
- KPI Projection 必须区分当期、当年、全周期，区分 `actual | forecast | scenario`，并暴露公式版本、数据覆盖、截至时间和预实偏差。数据覆盖不足时宁可显示待接入或预测区间，也不得生成无来源的精确利润。
- 领导可以按年、半年、季、月、周、日切换时间颗粒度，并沿集团、租赁公司、事业部、融资租赁 Case 逐级下钻。不同图形只服务于不同关系的清晰表达，不在 Direction 阶段冻结具体图表数量和版式。
- 所有 KPI、组织汇总、差值和趋势保持 `LeadershipProjection` / `PortfolioProjection` 语义；它们由融资租赁 Case、版本化演示目标与受控输入派生，不新增通用企业战略事项作为第二业务 Authority。

### 领导智能协同闭环

- 领导端必须保留完整 Collaboration / Chat Window，用于上传或引用材料、询问偏差、调取下级反馈、与 Leader Agent 讨论并要求进一步推演。
- 系统沿组织层级聚合专业部门与中层管理者反馈，同时区分 shared context 与 role/task-scoped context；领导能够看到完成经营判断所需的汇总与来源，但不因此默认暴露所有专业工作底稿或无关上下文。
- Agent 可以针对关键 KPI 偏差形成解释、多个可行方案与 Shadow System 推演结果，并基于过去状态、当前 Context 和明确假设提供比较与推荐；候选方案本身不自动成为正式命令。
- 领导在有权限的 Human Gate 中确认方案后，可以生成权威 Management Action 并向相关角色下发。Action 必须关联受影响的 `FinancingLeasingCase` 或 Case 集合、Context Version、决策人、依据与 Receipt，不以聊天文本直接改写权威状态。
- 领导是否可以越过或改写政策、信审、商务、资产的专业 Gate 尚未在本 Gate 中确认；该 Authority 边界作为下一项战略 Gate 单独决定。

### Demo 边界与优先级

- 领导端正式提升为 V3 比赛 Demo 的最高展示优先级之一，必须清楚证明系统如何改变领导发现偏差、取得解释、比较方案、完成判断和推动执行的方式。
- V3 只模拟少量与融资租赁生态一致的 KPI、组织层级、反馈与 Shadow 场景，形成一个可重复演示的管理闭环；不建设集团级绩效管理平台、预算系统、通用战略执行平台或生产级仿真引擎。
- 背景 Case 继续只提供稀疏 Projection；完整的分析、推演、确认、Action 与 Receipt 演示集中在 Golden Case 及其组合影响上，避免为所有背景项目制作完整权威链。

## Gate 14：小微唯一演示经营域与直接租赁 Golden Case

结论：**已确认。V3 比赛 Demo 的唯一经营域锁定为小微融资租赁；Golden Case 正式选择直接租赁，售后回租保留为架构可容纳、背景 Case 可表达但不制作第二条完整演示闭环的经营路径。**

### 小微唯一经营域

- V3 的组织、KPI、Case 组合、业务语言、角色职责和演示内容只围绕小微事业部展开。汽车融资租赁、中大客户事业部及其他事业部可能采用不同产品、规则与组织路径，本阶段不推断、不实现，也不用于扩大 Demo 范围。
- “见微”的产品含义同时服务于这一边界：看见小微客户、微小事实、微弱风险信号和被组织传递损耗的信息，再把它们汇总为可验证、可行动的 Case Context。
- 集团、融资租赁公司和总部职能只作为小微目标、约束、资源与专业支持的来源；不在 V3 中建设其他事业部工作台或集团通用经营系统。

### 直接租赁 Golden Case

- Golden Case 固定采用用户最熟悉、能够获得高 fidelity（高贴合度）流程输入的直接租赁场景。其核心外部主体是租赁公司、设备供应商与客户，完整演示商机、外部材料协同、政策、信审、商务、资产预判断与正式起租。
- 直租被选择是因为用户能够持续校验业务事实、角色、材料、条件与判断，提高 Demo 内容真实性和稳定性；它不构成集团战略上“直租高于回租”的证据。
- 存客回租和新客回租继续作为平台能够容纳的 mode-aware 路径，在背景 Case、组合分布或扩展接口中保留轻量表达；当前不制作第二套完整 Evidence、Context、Gate 与跨角色演示链。
- 后续若获得足够准确的回租输入，可以作为新的 Scenario Package 接入同一 Authority Kernel；不得因此复制前端、后端或 Case Authority。

### Gate 影响

- 后续 Golden Case 场景包、页面文案、材料类型、交易结构、角色动作、KPI 归因和验收脚本都以小微直接租赁为主，不再保持交易模式中性。
- Case Panel 可以出现少量存客回租和新客回租背景 Case，以证明组合视角与架构可扩展性；点击后只进入与其摘要一致的最小只读 Projection。
- 后续 Direction 问题不得再扩展至汽车、中大事业部或通用企业融资，除非用户明确开启新的范围 Gate。

## Gate 15：管理层组织权与专业 Gate 不可替代边界

结论：**已确认。管理层负责目标、导向、优先级、资源与组织协同，但不能替政策、信审、商务、资产专业人员作出正式专业判断，也不能以 Management Action 强制覆盖专业 Gate。**

### 管理层允许的 Action

- 询问偏差、事实与依据；
- 要求相关团队补充说明、重新核验或形成方案；
- 确认经营目标、优先级、资源配置和组织协同要求；
- 发起升级、协调和期限要求；
- 对 Leader Agent 的分析、Shadow 方案与管理建议进行确认或退回。

上述 Action 必须关联 Case 或 Case 集合、Context Version、发起人、目标角色、依据、期限与 Receipt。它们可以触发专业团队重新工作，但不能直接把某个项目改成政策通过、信审通过、商务完成或资产判断完成。

### 专业 Gate 边界

- 政策、信审、商务、资产的正式 Gate 只能由对应有权 principal 在其专业权限内确认。
- 管理层不能替专业人员代签、否决或强压结论；如果管理导向要求重新考虑，必须通过新增 Evidence、规则 / 条件版本或正式复核请求进入专业 Thread，由有权专业人员形成新判断和 Receipt。
- Leader Agent、企划、财务、业务和其他组织角色可以提供 Context、解释与候选，但不能把管理意见伪装成专业结论。

### KPI 与派驻职能

- KPI 目标权威以管理层确认为准。企划负责理解上级下达要求、辅助拆解口径、跟踪偏差和形成经营分析，不单独拥有改变最高经营目标的权力。
- 风控、企划、财务等人员可能由总部派驻事业部。该关系通过版本化组织归属、管理范围与专业责任表达，只影响可见范围、反馈链和 Gate principal，不生成额外 Role Application 或第二套业务 Authority。
- KPI 实际值由 Case Events、财务 / 经营受控输入和相应 Projection 派生；Leader Agent 只能解释、比较和提出候选，不能凭聊天改写目标或实际值。

### Gate 影响

- Gate 13 中尚未确认的领导 Authority 边界正式关闭：领导有管理 Action authority，没有专业 Gate override authority。
- 领导 Demo 的高潮应表现为“发现偏差 → 追问依据 → 组织专业反馈 / Shadow 推演 → 下发可追溯管理要求”，而不是领导替信审或政策点击通过。
- 权限测试必须证明领导账号无法调用专业 Gate 写接口，专业账号也不能越权代签其他板块。

## Gate 16：小微融资租赁实例化的企业 AI-Native 转型 Demo

结论：**已确认。见微 V3 的比赛定位升级为一套以小微融资租赁从商机到正式起租为完整实例的 enterprise AI-native transformation architecture（企业 AI 原生转型架构）Demo；它要覆盖评委关注的技术性、可落地性、价值性、客户触达与场景完整度，但不宣称已经建设真实生产系统或包办所有企业业务域。**

### “完整”的准确含义

- 完整指在一个真实、明确、可验证的经营域内，打通目标与 KPI、业务获客与采集、客户 / 供应商协同、政策、信审、商务、资产辅助预判、领导观察与管理 Action，并由同一 Authority Kernel 串联。
- 完整不等于实现集团所有事业部、OA、财务核心、规则开发平台、资产管理系统、通用 CRM、生产数据库或全部内网接口。
- 见微展示的是一套可以通过 Adapter、Skill、Agent capability 和 Role Projection 扩展的架构；比赛中只证明小微直租闭环真实可运行，不用静态页面冒充其他业务已落地。

### 五类比赛得分证据

1. **技术性**：唯一 Case Authority、共享 Context Version、五路异步触发、Event / Evidence / Diff / snapshot、Human Gate、Receipt、role-scoped Projection、失败关闭与可回放；
2. **可落地性**：复用既有系统的 Adapter 形状、一个前端代码库、最小 Demo Backend、固定 Scenario Package、明确权限与确定性验收，不要求推翻现网；
3. **价值性**：以当期 / 年度可验证净收入与单位资产产出效率证明主要经营价值，以全周期利润预测作辅助校验，并解释效率、风险、运营成本、客户体验和厂商粘性如何形成或侵蚀价值；
4. **客户触达**：客户与供应商通过外部协同 Web 直接完成受邀材料、问题与确认；业务通过同一 Case 及时协同，减少重复提交和信息断层；
5. **场景完整度**：领导、业务、风控四专业账号、客户与供应商围绕同一 Golden Case 连续演示，并由背景 Case 支撑组合视角。

### 目标评委与表达重心

- 主要说服对象是融资租赁公司的科技管理层，约占目标受众的一半至三分之二；
- 集团科技管理层是第二重要对象，约占四分之一至三分之一；
- 事业部业务 / 销售管理层构成其余重要受众。

上述比例只用于决定叙事重心，不是比赛组织的统计事实。页面与讲述必须让科技管理层看见架构与可接入性，让业务管理层看见真实流程、客户价值与经营结果。

### Demo 真实性边界

- 当前交付仍是比赛 Demo / validation prototype。前端可以保持内网产品沉浸感，但 Backend Scenario metadata 必须记录合成来源与版本。
- 不宣称已接真实集团系统、真实客户数据、生产规则库、真实模型组合、生产安全体系或已实现经营收益。
- 所有得分必须由可操作页面、可重复流程、后端 Event / Receipt、测试和浏览器证据支撑；没有证据的能力只能标为 extension path，不能作为已完成项计分。

## Gate 17：协同入口、起租主线与项目群聊首屏

结论：**已确认。V3 前端不再以“领导”作为可见一级入口，当前统一显示为“协同”；首屏必须直接说明同一融资租赁 Case 中谁围绕什么目标协作、五路当前状态、正式起租关系与当前 Owner。**

### 一级入口与内部权限标识

- 当前可见一级入口使用两个汉字：`协同 / 业务 / 风控 / 外联`。其中“协同”替代此前所有可见“领导”文案，是本 Gate 的正式产品决定。
- `leadership` 可以继续作为代码、ACL 与 Projection 的内部稳定标识，本 Gate 不授权 backend identifier migration；内部标识不得重新泄露为前端英文副标题或用户术语。
- `外联` 是当前可逆的两字 UI working label，用于满足同一层级命名长度一致；外部 Role Application 的业务边界仍为客户与供应商受邀协同，最终中文名后续可以单独确认，不能借改名扩张权限或业务对象。

### 起租主线

- 正式起租必须作为一条贯穿首屏的共同结果线表达。商机、政策、信审、商务、资产保持五路并行，不得因为横向排布被描述成固定线性瀑布。
- 五路状态用有限档位、色块或节点表达，不向用户显示虚假的精确百分比；正式起租是共同端点，未满足各专业条件时不得显示已经起租或已经产生收益。
- 当前工作区必须回答“目前结论、现在要做、Owner、完成后交给谁”；Event、Context Version、Human Gate 与 Receipt 继续由后端决定，不在首屏堆叠调试术语。

### 项目群聊

- 右侧 Collaboration Dock 的产品形态锁定为围绕当前 Case 的项目群聊，而不是孤立问答框。
- 群聊顶部至少显示当前 Case、协同目标、参与成员、两字角色头像 / 席位、人员与 Agent 的工作状态、当前 Thread 与最近进展；支持按权限 `@` 对应专业人员与 Agent。
- 普通聊天、候选推理、材料接入、事实确认、ContextCommit 和权威 Action 必须在交互上可区分。材料 / 回答先形成 Evidence Receipt；只有具名事实确认完成逻辑批次的 ContextCommit 才推进版本并触发五路，Human Gate 与其他 Action 绑定当前版本并生成各自 Receipt。
- 业务与风控可以看到同一 Case 的五路群聊与全局 Context；风控仍只在本专业账号内确认 Gate。外部客户或供应商只看到其受邀步骤、整体进度和当前问题，不看到内部专业群聊。

### Case Panel 与背景 Case

- 每个 Role Application 同时具有 Case Panel 和所选 Case 的 Role Workbench；不同角色点击同一 `caseId` 进入不同 Role Projection，不创建不同后端数据。
- 背景 Case 只提供独立 `caseId`、只读摘要、阶段、异常、里程碑与有限起租档位；点击背景 Case 不得复用 Golden Case 的目标、人员、群聊、Evidence 或完整工作区内容。
- Golden Case 继续是唯一完整走通五路、外部材料、Human Gate、Receipt 与正式起租演示的 Case。

## Gate 18：God View 进入、三次 Context 转折与正式起租收口

结论：**已确认。比赛主路径从协同 God View 的小微经营偏差进入，下钻唯一直接租赁 Golden Case；通过 T1 商机事实成立、T2 风险事实暴露、T3 外部证据补强三次关键 Context 转折证明五路异步与可回退，专业 Gate 满足后正式起租，最后返回协同 Projection 并以 Event / Diff / Receipt 回放收口。**

### 固定主路径

1. `协同` God View 发现净收入、单位资产产出效率或起租相关 KPI 偏差并定位 Golden Case；
2. 下钻 `FL-DEMO-001`，看到同一 caseId 的协同目标、五路状态、当前阻断与正式起租端点；
3. 业务具名确认初始商机和设备融资事实，形成 T1 并触发五路首轮 partial run；
4. 受邀客户确认一项会改变判断的风险事实，形成 T2；信审必须出现回退或补件，其他路按影响独立更新；
5. 客户和供应商分别补强受邀 Evidence，必要现场查验由内部人员确认，形成 T3 并让五路基于最新 Context 重跑；
6. 政策、信审、商务、资产有权账号只确认本专业 Gate；协同角色可以追问、协调和形成管理要求，但不能代签；
7. 商务核验 Scenario 所需条件后提交正式起租 Action / Receipt，Case 起租五格全黑并进入已起租 / 已起息；
8. 返回协同 God View 展示 Case / Portfolio / KPI Projection 变化，再打开有序 Event、Context Diff、Gate 与 Receipt 证明可回放。

### 三次 Context 转折

- **T1 · 商机事实成立**：初始商机、设备锚点、供应商报价、直租意图由具名业务人员确认；一次 trigger 创建五路 candidate run。
- **T2 · 风险事实暴露**：外联客户确认主要下游订单覆盖期 / 集中度与拟定租金计划存在需要解释的偏差；具体阈值与材料留待业务校准，但信审回退 / 补件是不可变演示结果。
- **T3 · 外部证据补强**：客户补充订单履约、交付与回款依据，供应商确认设备、交付窗口与付款条件；两类 Evidence 先进入同一 pending batch，再由具名事实确认一次性 commit 为新 Context，五路重跑，旧 T1/T2 run 保留并标记 stale / superseded。

普通聊天、候选 Agent 回复和单个未确认文件不得持续制造 Context Version。每个逻辑批次先保留 Evidence Receipt，只有明确 `ContextCommit` 才推进一次版本并 trigger 五路；专业 Gate、Management Action 与正式起租 Action 绑定 T3 并生成独立 Receipt，不需要为了“版本更多”重复改写 Context。

### 正式起租与经营价值边界

- 正式起租是当前 Demo 的业务完成节点，意味着开始计息；它不代表客户已结清本金利息、开票完成或租后全生命周期结束。
- 正式起租 Receipt 必须引用所需上游 Gate / Evidence Receipt，不得由模型、聊天或前端本地状态直接生成。
- 收口优先展示“本期 / 本年 KPI 变化”“本季起租落地”“预计净收入贡献”和单位资产产出；全周期利润只作辅助预测与长期影响提示。所有 Projection 必须保留时间范围、公式版本、数据覆盖、Scenario version 与推导依据，不能把 forecast / scenario 包装为真实已实现利润。
- 技术高潮必须至少表现为：同一 Context trigger 五路、partial completion、一次风险回退、旧 run 可回看、专业 Gate 权限隔离和最终 Receipt。

### Control 产物

- 宏观页面顺序与得分意图记录在 `V3_DEMO_NARRATIVE_CONTRACT.md`；
- 固定 Scenario identity、三次 Context 转折、角色确认与最终输出记录在 `V3_GOLDEN_CASE_SCENARIO_CONTRACT.md`；
- 两份契约不冻结五路内部内容槽、具体专业阈值、完整 API schema 或现场精确分钟数。

## Gate 19：Browser + Backend 双证据与三次连续回放验收

结论：**已确认。V3 Demo 的完成判定必须同时具有评委可见的真实 Browser evidence、后端 Event / Context / Gate / Receipt evidence，以及三次连续 reset/full-run 证据；静态代码、单次截图、worker 自报或局部绿色测试均不能替代。**

### 完成判定

- 每项宣传能力至少同时具有一个可操作页面证据和一个后端 / Receipt / test 证据；纯 UI prototype 不计为技术闭环，纯 API 不计为比赛可见能力。
- Golden Case 必须连续三次完成 `reset → T1 → T2 → T3 → 专业 Gates → 正式起租 → replay`，中间不得改源码、手工改状态或重启到其他服务救场。
- 三次运行的业务结构、Event 类型与顺序、Context transition、run binding 和 Receipt 引用关系必须一致；时间戳 / runtime epoch 只能按契约使用受控差异。
- 最终浏览器验收至少覆盖 1920×1080 Desktop、1366×768 Laptop 与约 390×844 Mobile；四 Role Application、外联客户/供应商、Case/role/process 切换、loading/error/disabled/success 和 fresh console 均须有证据。
- 最终服务必须来自本次验收记录的最新 production build，并记录 PID、command、port 与 build fingerprint；不得用 stale dev server 或旧截图冒充。

### 证据包与失败规则

- 每次正式验收形成独立 `V3_ACCEPTANCE_EVIDENCE/<acceptanceRunId>/`，包含 manifest、commands、HTTP、browser、scenario runs、events、receipts、security 与 limitations。
- manifest 只记录可复验的 build、Scenario、进程与 Gate 信息，不记录 token、cookie、真实客户身份或其他敏感信息。
- 所有 `MUST` 条目必须通过；任何一项失败即停在对应 Gate 修复，不允许用下游成功抵消上游失败。
- 合成 Scenario source/version/seed 在后端 metadata 留痕；业务前端无需常驻模拟水印，但不得把预计收益写成真实已实现利润。
- 用户保留最终视觉、业务 fidelity 与比赛表达验收权；自动化全绿不等于用户已接受产品。

### Direction 完成边界

- Gate 1–19 已完成本轮会导致整体返工的 Direction 冻结；后续不再无限追加宏观讨论。
- 详细验收项与证据标准以 `V3_ACCEPTANCE_MATRIX.md` 为准。
- 下一阶段进入 D1 Control：冻结 Role Projection、API/Event schema，并校验五份契约互相一致；只有 Contract Gate 通过后才允许按明确 ownership 展开大规模实现。

当前没有未决 Direction Gate。后续只有出现会改变产品边界、Authority、核心数据模型、真实数据权限或验收等级的新证据时，才暂停请求用户纠偏。
