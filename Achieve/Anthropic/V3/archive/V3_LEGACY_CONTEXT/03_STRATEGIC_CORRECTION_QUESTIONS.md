# 归档审计宏观问题答复记录

状态：五项均已由用户答复，并写入 `V3_DIRECTION_FREEZE.md` Gate 14 至 Gate 16。

## 1. 领导 God View 的主服务对象到底是哪一级领导？

历史材料同时出现“集团 / 租赁公司 / 小微事业部”三个层级。不同主 persona 会改变 KPI 口径、组织下钻、管理范围和 Demo 故事。

建议：V3 Golden Demo 的主要操作者锁定为“小微事业部负责人或直接管理小微的租赁公司领导”；集团 / 董事会只作为目标与约束来源，租赁公司其他事业部只提供组合背景，不建设完整工作台。

用户结论：产品与 Case 经营域只做小微；God View 的项目和组织内容聚焦小微。比赛说服对象以融资租赁公司科技管理层为主，集团科技管理层次之，事业部业务 / 销售管理层也是重要对象。

## 2. 领导 Management Action 与专业 Gate 的权力边界是什么？

Gate 13 已允许领导形成权威 Action，但尚未决定其能否直接改写政策、信审、商务或资产结论。这是目前最大的 Authority 未决项。

建议：领导可以定目标、改优先级、调资源、要求补充调查、发起升级、确认组合策略；不能单方面替代专业人员签署正式专业 Gate。若必须例外，应走“例外申请 + 专业会签 / 更高权限会签 + Receipt”。

用户结论：不存在直接覆盖。领导只能询问、给出导向、提出请求和组织协同，不能替专业专家作决定，也不能强压专业 Gate。

## 3. 12 个组织角色在 V3 中应达到什么可见程度？

历史 TQ 的 12 角色非常有助于解释公司如何运转，但完整呈现在 V3 前端会把四 Role Application 与五路 Process Thread 再次搞混。

建议：12 角色作为 organization actor / capability source，用于 Context 路由、Owner、反馈来源和领导下钻；V3 顶级导航仍只有四 Role Application，Case 主链仍只有五路。科技部门只在系统能力、接入状态和治理信息中出现，不成为第六路业务流程。

用户结论：12 角色只作为背景，不作为 V3 显性主架构。当前产品只聚焦商机到正式起租链路。

## 4. KPI 的“目标权威”和“实际权威”分别由谁提供？

Case 是业务事项权威，但 KPI 目标、预算、资金成本和组织口径并不天然由单个 Case 产生。若不定义来源，Leader Agent 容易把分析候选误写成经营事实；若另建通用战略对象，又会突破 Gate 1。

建议：V3 Demo 中将目标口径、预算和组织关系放在版本化 Scenario / Management Configuration；企划与财务是有权提供者，Case Events 只贡献实际值，Projection 负责汇总，Leader Agent 无权修改源数据。赛后内网产品化再单独冻结真实 KPI Adapter 与 Authority。

用户结论：KPI 目标权威以管理层为准；企划辅助理解、拆解和跟踪上层下达目标。风控、企划、财务等可能由总部派驻事业部，该关系只作为组织与权限背景。

## 5. Golden Case 的交易模式何时锁定？

V3 已要求直租与售后回租战略上同等重要，但一个 Golden Case 最终只能采用一个具体模式。选择会影响商机、Evidence、付款、权属、商务与资产演示。

建议：现在不依据猜测冻结；先完成集团方向与专业访谈。若调研仍无明确优先级，选择用户最熟悉、最能稳定跑通的直租 Golden Case，并用背景 Case 展示存回与新回的风险收益差异；这不代表战略优先级。

用户结论：接受。Golden Case 固定为直接租赁，以用户可提供和校验的高贴合度输入做完整闭环；回租保留架构与背景 Case 空间，不制作同等重量的演示链，也不表示战略上低于直租。
