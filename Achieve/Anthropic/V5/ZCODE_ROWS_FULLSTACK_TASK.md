# ZCode 任务包：四域横条总览与前后端联动

日期：2026-09-11，Rev2。来源：用户最新明确要求“连续完成一个大任务”“使用多个 sub-agent”。状态：授权下述完整交付范围连续执行，替代 Rev1 首个预览即停止的限制；不是全平台改版、历史 B1 放行或最终产品验收。

## 目标与当前决定

在现有 V5 preview 上连续完成可稳定演示的前后端更新：业务查看新客回租单笔项目四域横条总览，提交合成补充说明、沟通并跟进待复核，后端保存并返回最新待办、四域状态及沟通记录，刷新和服务重启仍可恢复。把实现、响应式体验、真实 HTTP 联调、权限、失败恢复、回归修复和演示交付作为一个完整任务承担。中间检查点自行留证、自查、修复，通过后继续；不得只交静态页面、接口草案、单个按钮或测试计划就结束。

保留全生命周期表达，用明确标注的合成演示情景验证审批推进中、起租后资产管理、结清完成三种总览。情景切换属于隔离演示控制或测试 seed，不放成业务用户可直接批准/放款/结清的按钮。实际写入闭环聚焦材料说明与项目沟通，不凭本任务重建正式金融交易系统。

四个专业域是政策、信审、商务、资产。手机用四个宽横条上下排列，每条含标题、四段域内进度、语义状态灯和一句说明。排列不等于强制串行；无正式依赖的准备工作可以并行。每域四段不强制同名，不机械折算总进度。全生命周期结清才完成，起租大致八成仅为概念，不写死计算公式。红黄绿仅表达判断状态，其余黑白灰；未开始/未知用灰色加文字，不能默认为绿灯。

顶部客户/项目与整体状态，中部四域，下方最重要待办，底部轻量可展开项目沟通。局部轻玻璃，清晰可读优先。业务保留协调责任，只能看授权总览，不能进入专业详情。本轮不重设计四域专业工作台、客户门户或通用编排。

视觉参考（需实际打开图片）：`design/20260911-business-five/06-horizontal-rows.png`。参考图的客户名、材料名、状态、填充与比例为合成示例，不是制度。用户当前要求将横条方向落实为本次候选实现，最终验收仍待反馈。

## 多 sub-agent 执行编组（用户明确授权）

主 Agent 持续负责需求一致性、可恢复快照、共享 schema、派工、集成和最终报告。先冻结接口及精确文件所有权，再同时安排至少两路实际实现；建议以下四路，按自身可用并发容量分批，不假装存在并发能力。

1. Frontend worker：仅拥有 `app/v5-preview/**` 与已有 `test/v5-preview.test.mjs`。完成横条手机页、桌面自适应、加载/空/错误/成功/冲突反馈、沟通与补充说明交互、键盘焦点和 reduced-motion。只能消费主 Agent 固定的 API/schema；不能自建第二份业务事实源。
2. Backend worker：拥有 `lib/v5-preview/**` 中除主 Agent 指定共享类型之外的服务/存储文件，以及 `app/api/v5-preview/**`。完成投影、受控演示身份、输入校验、幂等、版本冲突、隔离持久化与重启恢复；优先复用，不动 v4life 核心。
3. Verification worker：拥有 `test/v5-preview-*.test.mjs` 新增行为/HTTP 测试与 `V5/handoff/ROWS_FULLSTACK/verification/**`。先按冻结接口独立设计有意义的异常与权限测试，服务可用后运行真实 HTTP；不改前后端实现。失败以复现证据交给对应 owner 修复。
4. UX/review worker：只读代码，拥有 `V5/handoff/ROWS_FULLSTACK/ux/**`。检查语义、手机/桌面可读性、状态与进度分离、越权入口与假联动，产出实际浏览器截图和问题清单；不覆盖前端 worker 文件。共享浏览器与演示数据按预约串行验证，避免操作相互干扰。

每个子任务都必须包含完整输入、允许写面、禁止项、验收和停止条件，并明确告知“你不是唯一执行者，不要回滚或覆盖其他人的修改”。主 Agent 维护 OWNERSHIP.md 和 CHECKPOINTS.md，单文件单 writer；共享类型只由主 Agent 修改，接口变更先通知所有消费者。子 Agent 完成不等于总任务完成，主 Agent 必须整合、运行、复验。能力不足以启动多个子 Agent 时如实报告，不静默声称已委派。

## 连续交付顺序

- C0：核对现状/快照，明确增量复用与 API/schema、持久化路径和文件 ownership。既有修改完整保留。
- C1：前端和后端并行实现，测试与只读审查同步开展；接通后留下第一版运行截图，主 Agent 自查后继续，不等用户逐步批准。
- C2：完成补充说明与沟通往返、刷新/重启/第二客户端一致性、权限和幂等冲突；修复 worker 与审查发现的问题。不得用固定延时动画或前端假状态代替后端。
- C3：完成三种生命周期合成情景、双端体验和所有相称 Gate；对本轮引入的问题持续定位修复到通过。无关既有失败记录来源与影响，不越界大修。
- C4：交付可运行版本、真实截图、演示步骤、测试证据及最终报告，然后停止扩展，等用户/Codex 最终验收。

持续执行按依赖推进，不以额度消耗、工时或代码量作为目标。不在普通实现选择和阶段结束时反复请求确认；只在越出授权范围、重大核心改版基线要求、不可逆操作、必要资源缺失等真正阻塞处停下。尚未确定的专业规则保持合成标识，不由 worker 自行冻结制度。

## 联动契约要求

复用现有路由优先；确需新路由时限定 GET 项目总览、POST 合成补充说明/沟通两个最小能力。精确 URL 在 IMPLEMENTATION.md 中固定并让前后端共用类型。

总览至少有 projectId、version、整体里程碑、四域 domainId、四段状态及说明、独立 judgmentStatus、业务可见摘要、当前待办、业务可见消息及更新时间。阶段含义按各域配置，不继续强行套用“材料合规—模型校验—人工复核—正式通过”到资产全周期。没有已确认阶段名时使用演示阶段标记并如实说明，不发明专业规则。

写请求带 requestId 和 expectedVersion，服务端校验角色、项目范围、长度与输入；同请求重试不重复记账/追加，相冲突版本明确拒绝并要求重新获取。客户端不直接把提交动作改成审批通过。演示身份须服务端受控；若缺真实登录，明确仅本地合成角色演示，不能宣称生产权限。业务 GET 不返回专业细节，直接访问专业路由也不得绕过限制。

共享状态由后端保存，前端 localStorage 不再是业务事实源；可复用现有持久机制，或对本任务隔离的单进程合成存储做有界实现。持久数据与源码分开，文件损坏明确报错，不能静默清空。报告准确说明持久化等级。无真实模型/API，合成后续判断明确标识；补件后可以变成待复核，不能自动变绿或生成正式 Decision/Receipt。

一个完整验收动作：初始黄灯补件 → 业务提交合成说明 → 服务端记录新版本与消息 → 待办和状态一致更新为待复核 → 刷新/另一视口读取同一状态。保留红线与正式依赖；红线不能靠聊天解除。无关域不被无差别清零。
