## 2. 政策五色与信审六维：两种不同组织轴

### 政策：五色风险语义

用户本轮明确采用顺序：**紫、红、黄、蓝、绿**。早期JW原始指令对应：

| 色度 | 历史代码 | 承接语义 |
| --- | --- | --- |
| 紫 | forbid | 禁止类 |
| 红 | risk | 风险类 |
| 黄 | confirm | 核实类 |
| 蓝 | attention | 关注类 |
| 绿 | support | 支持类 |

主分类按风险语义组织；规则来源、专业方向、适用模式等可以是辅助标签。不得把颜色当作未经校准的风险概率，也不凭色度自动审批或否决：正式动作仍受授权规则、Human Gate与例外路径控制。绿色不等于零风险或自动通过；材料缺失、证据可信度、模型confidence与最终审批结果分别记录，不能直接换算成色度。

五色是业务语义，不是本轮UI配色任务；现阶段不制作彩色界面。

### 信审：六维事实结构

固定顺序：**合规 → 交易 → 生产 → 营收 → 负债 → 流水**。“风险”是独立汇总，不是第七维。

历史映射供承接：合规含主体及公开司法等依据；交易含结构、方案和关系；生产含设备、工序、现场及能耗等；营收含收入、订单、票据和经营表现；负债含借款、登记、担保及其他义务；流水关注真实性、经营匹配和异常。此为旧映射参考，不直接授权新增数据查询，也不冻结本轮所有字段。

同一六维事实可以关联多条政策规则；不能把六维、五种色度、四个职能设计成互相替代的分类。具体评分、权重、阈值、总风险合成方式均未在本轮接受。

## 3. 商务与资产的接续：具体流程与四域协作分开

用户说明存在货到与预付两种模式，本轮**先按预付梳理**。用户给出的参考顺序：

信审结束 → 电子签约 → 合同审批 → 付款 → 物流查看 → 正式起租 → 还款与巡检 → 结清 → 结清证明。

这是本轮接续参考，不代表已校验的全公司制度，也不表示链上动作都由商务负责。付款不是整个Case结束。签约、合同、付款、起租、还款等交易事实继续归既有业务系统；V4只引用状态、记录协作要求与接续，不能借此扩成合同/支付/物流/还款平台。

**适用性待对齐**：当前主案例仍是已冻结的新客回租；本轮预付与物流链路是否适用于该案例、还是另一交易模式参考，用户尚未明确。两者分开保存，不擅自替换主案例，也不将全部节点塞入同一个演示。

局部正式流程可以有先后，但四域整体不串行化：前置分析、资产观察准备和低成本核验能否并行，要按具体依赖判断，而非等整个前域“全部结束”。

## 4. 资产：周期巡视与事件触发共同存在

已明确的需求：高风险场景需有计划的现场巡视与后续跟进；用户列明**两个月、三个月、半年**的巡视周期/时间节点，并以新客回租举例。不能只做事件提醒而遗漏制度化巡视。

尚未确认：三档时间是不同客群/风险档位的周期，还是同一项目不同阶段的节点；以何时起算、谁确认计划与调整、具体适用范围。本轮不写成所有客户固定第2/3/6个月到访的制度。

补充机制候选：结合负债与偿付现金流之间的压力、经营变化、资产变化等信号，提示是否需要提前巡视、补充观察或复核。不能把“现金流高”本身当高风险，也不伪造预测概率；调整正式安排仍由现有负责人确认。模型提醒不能自动取消既定巡视。

## 5. 每个工作项的协作关系

用户认可的三类必须明确分开：

1. **共享**：允许谁看什么依据；知悉不等于取得审批权。
2. **提前准备**：低成本、可撤回且无硬前置依赖的分析/草案，不产生正式结果。
3. **必须等待**：指定证据、人工确认或前序正式结果不到位，不执行相应动作。

同一能力的准备动作与正式动作可以分属不同类别，不能给整个职能贴一个“并行/等待”标签。前后端读同一依赖状态；前端用于说明能做什么、为何等待，后端负责强制检查。具体按钮与布局不在本轮设计。

## 6. 小团队建设与专业评审

用户强调能力可模块化逐项迭代，少数熟悉Agent框架的人也能推进多项功能；不把人数或并发数作为价值指标。本轮“scale化”的工程承接暂称**可复用能力单元**，不擅自选定Skill/MCP/Workflow的具体封装。

每项能力要有明确专家评审责任与跟进人，并明确哪部分由AI、业务人员、专业人员或既有系统承接。沿用已有能力登记原则，记录版本、输入输出、权限和失败边界。

专家评审会的要求已记录；评审发生于上线/规则变更/重大异常中的哪些节点、谁召集及如何通过，留待确认。不默认每一次能力运行都召开评审会，也不因一个人能开发而允许其代替四域正式责任。
