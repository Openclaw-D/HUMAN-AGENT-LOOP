## D-01（高）每次成功的远端写都留下"结果未知"幽灵条目（requestId 体系错位）

- **复现**：3469 隔离实例（qa/runtime/app，代码=预览副本@01:40，remote-session 页与 site 基线一致）→ DD 页空状态 → 点「开始访谈会话」→ 成功进入会话；或发起任何写操作。单次点击，无并发。
- **期望**：写成功 → 注册表条目清除，无"请求结果未知"条。
- **实际**：条目永久残留 unknown 状态（跨刷新存活，sessionStorage）；页面持续显示「有一条请求结果未知（op，发送于…）」+ 原样重试/放弃。多次操作累积多条（容量16）。
- **代码版本**：`app/v5-preview/remote-session/page.tsx` 基线 e7d65a16…（A 尚未改此文件；远程尽调页属 A CP3 范围）。
- **根因**：`runWrite` L263 `const requestId = retryEntry !== null ? retryEntry.requestId : newRequestId()` ——新请求时 `requestId` = 页面函数 `newRequestId()`（**crypto.randomUUID，payload 内 ID**）；而注册表条目键 = `registry.begin` 的 idFactory（**`req-` 前缀**）。L276 `registry.resolve(requestId, 'confirmed')` 用 UUID 匹配 `req-` 键 → 永不命中，条目不删。原样重试路径反而正常（此时 requestId=条目键）。
- **风险**：演示中每次操作后都出现"结果未知"警示条，用户误以为失败；堆积至16条后触发背压拒绝新写入（「存在 N 条未确认请求已达演示上限」）→ **演示中断**。
- **证据**：qa/evidence/d01-registry-dump.txt（注册表 dump：entry.requestId=req-mu04pt51… vs body.requestId=a8069517…；两条 unknown 而服务端 store 两笔写入均 200 落库）；3469 服务端日志 `POST remote-session 200` / `POST evidence 200`。
- **建议方向**（供A，不改代码）：`begin` 成功后用 `began.entry.requestId` 作为 resolve 键（retryEntry 分支已是正确键）。
- **owner**：A。**状态**：**已修复，D 复测通过（03:30，3469 隔离实例，A 修复版代码 source-sync-0322）**。A 的修复：runWrite 新增 registryKey（retry=条目键；新请求=began.entry.requestId）。复测：建会话/发起问题（含首次点击）/提交访谈记录 三种写后幽灵条=0。
