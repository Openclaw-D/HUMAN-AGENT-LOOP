# EXPLORATIONS｜Dify 适配 vs 薄代码候选（选型比较，仅协议层验证）

探索问题：六角色"证据→追问→人工复核"的模型步骤编排，走 Dify 工作流还是薄代码候选？

## 现状与约束

- Dify 配置/管理员归 Codex，前序 DIFY 本地引导未完成——**不能接管其写面或取旧凭证**；本轮只做源码/协议层比较。
- 团队已有 Dify 经验（性能接近时优先）；新视频需求不要求 Dify 负责媒体。
- 本轮实现恰好落在两者之间：`simulateFollowUps` 是确定性 stub，其输入/输出契约（见 READY_FOR_INTEGRATION.md §1）即为两种方案的共同接口。

## 比较（围绕同一用例：标注 → 生成 2 条角色化追问）

| 维度 | Dify 适配 | 薄代码候选（当前 stub 形态的延伸） |
| --- | --- | --- |
| 接口契约 | 共同：输入/输出 JSON 同形；适配层把 provider 响应映射为 `AnnotationReply` | 共同 |
| 权限/审计 | Dify 编排侧记录；需导出到 METRICS | 直接在服务层记录 tokens/延迟 |
| 失败路径 | 依赖 Dify 重试/超时配置 + 本侧映射错误兜底 | 本侧直接实现（try/catch → error 标记回复），可控性高 |
| 可迁移性 | 编排 DSL 绑定 Dify 版本 | 逻辑在自家测试覆盖下 |
| 部署面 | 多一套外部依赖与配置漂移风险 | 零新增依赖（本轮约束） |
| 团队经验 | 优势项 | 需要团队后续熟悉 |
| 本轮可验证性 | 无凭证/未完成引导 → 仅协议草案 | **已实现并以 11/11 回归验证失败路径** |

## 结论（建议，不自行晋升主干）

1. 契约已统一：两种方案都落在 `simulateFollowUps` 的 I/O 形状上——切换成本被隔离在单个函数内。
2. 建议：真实模型首链路用**薄代码候选**验证（失败路径/用量核算可控、零新增依赖）；Dify 作为编排增强在模型链路稳定后由用户/Control 决定是否引入；两者共享同一契约，切换不改写面。
3. 未解决：Dify 实际性能/运维成本需真实环境数据，本轮无凭证未测。
