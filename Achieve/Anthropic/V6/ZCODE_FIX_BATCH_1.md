## 必须完成

### A. 全部写入的乐观并发门

`postMessage` 在幂等重放判定之后、任何写入之前，必须与 `submitNote` 一样比较 `expectedVersion` 和当前 `overview.version`。版本过期必须返回既有 `VERSION_CONFLICT`（409、含 `serverVersion`），不得追加消息或递增版本。

保持既有幂等语义：同一 `requestId`、同一完整原始载荷重放成功响应且不重复写入；同一 `requestId` 但载荷不同返回 `REQUEST_MISMATCH`。不要用“消息可并发追加”的新语义规避修复。

### B. 持久化文件的完整失败关闭校验

读取既有文件时，对 `ProjectOverview` 与每一项幂等缓存响应递归校验，而非只检查顶层：

- 总览必须含正确类型与可用值的项目字段、场景、版本、时间、整体进展、待办（或 `null`）、消息数组和恰好四个域。
- 四域必须是政策、信审、商务、资产各一次；每域必须有四个合法段状态、四个非空段名、合法判断状态、非空显示文本和摘要。
- 待办、消息及其枚举/文本/时间字段必须可被当前前端安全读取；不能允许 `null` 伪装成有效对象。
- 每一幂等项必须校验其 `requestId`、哈希和完整 `WriteResponse.overview`，包括可选 `replayed` 的合法性。

任一不符都必须通过现有失败关闭路径返回 `STORE_CORRUPT`，不部分修复、不静默重置、不向前端返回畸形数据。可提取纯校验函数，但不引入第三方依赖。

### C. 网络结果未知后的原请求重试

前端对“网络结果未知”保留并重放**完整原请求**，而非只保留 `requestId + text`：至少包括首次发送时的 `expectedVersion`，补充说明还包括 `todoId`，以及原始文本与 `requestId`。随后轮询或刷新获得新版本时，用户以相同内容重试，仍必须使用该原载荷以命中服务端幂等重放。

成功重放返回的旧 `overview` 不得覆盖页面已经获得的更新版本；只在其版本不低于当前页面事实源时才应用，或等价地随后刷新取得不回退的服务端真相。确定性 HTTP 错误仍按现有规则清除待重试请求；409 保留草稿并刷新，不伪造成功。

### D. 情景切换的版本隔离

不得让情景切换复用任何已经发出过的 `overview.version`。可选择内部演示批次标识，或更简单地让所有 seed 与写入版本在同一持久化生命周期全局单调递增；选择后应更新相关测试与说明。

最低验证：审批情景下发出的旧 `expectedVersion=7` 请求，在切换到其他情景再回到审批后必须被 `VERSION_CONFLICT` 拒绝，不能写入新批次。切换时清空幂等表仍可保留，但 UI 必须以简洁中文明确提示“已切换演示情景；此前演示记录已重置”，且不能把它伪装成普通业务状态变化。

### E. 中文体验收口（仅必要修改）

- 用户界面去除 `Decision`、`Receipt`、内部错误码和开发控制类英文。保留一次简洁边界提示，例如“合成演示数据，不执行正式审批”。
- 待办入口统一为“补充说明”；不得用“提交材料”暗示文件上传能力。输入提示不能暗示附件已被支持。
- 补充成功后，项目总体说明必须同步反映“信审待复核”，与黄色判断灯一致。
- 四段名称在手机端须无需鼠标悬停即可轻量查看；可用点击展开/折叠，默认不展示专业详情，保持横条紧凑。
- 压缩手机第一屏顶部说明，使首个待办更早可见；不增加新的业务功能、图表或视觉包装。
