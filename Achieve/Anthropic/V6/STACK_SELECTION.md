# 六角色后端技术选型｜候选比较

2026-09-12。状态：研究初筛，不是框架性能评测或替换授权。

## 用户已明确的技术指导

业务逻辑与用户体验决定技术选型；不因已安装、历史习惯或团队现用平台锁死Dify。开放引入更合适的栈，但不将“开源”直接等同于低迁移成本。比较开发、状态迁移、自动化验收、运维、许可证及接手成本。此原则不覆盖Human authority、安全和当前授权边界。

保持六角色真实协作、一套响应式Web、合成资料、模型无正式审批权。不安装或迁移新平台，不修改产品代码。Dify 1.13.2环境保留；Dify专属实施任务暂缓放行，未代发、未停止ZCode现有工作。

## 当前证据与初步判断

**最新补充覆盖初筛排序**：用户随后明确稳定性第一、轻量、低代码同事可上手；能力接近时选Dify，再看性能与扩展上限。自用必要步骤也可评估。此前先验偏向LangGraph仅基于流程能力，不再作为当前首选结论。综合评估现建议以“Dify 1.13.2 + 薄业务后端”为优先验证组合，LangGraph作为发现明确限制后的替代候选，详见BACKEND_FIT_ASSESSMENT.md。两者均未通过本项目真实模型稳定性对比。

本地site/package.json实际为React/Next、TypeScript及vinext/Vite，Node要求22.13以上。下面的Node框架与现有语言一致，但并未证明可直接运行在现有Cloudflare/边缘部署目标；持久执行应先按独立Node服务验证，不能混淆开发语言与运行时兼容。

| 候选 | 官方可核对能力 | 对本项目的判断与代价 |
| --- | --- | --- |
| LangGraph JS | 固定逻辑与模型步骤混合、状态检查点、人工中断恢复、子图 | 技术控制能力强的替代候选；低代码接手权重补充后不再作为当前首选，仍需自己实现业务API、权限、可靠副作用和运维 |
| Mastra | TypeScript workflow，输入输出schema，暂停恢复、Studio图视图 | 次选，适合代码优先且需要开发期可视观察；持久恢复、内网依赖和升级行为需实测 |
| Dify 1.13.2 | 当前已有隔离环境；该版本源码支持DSL导入导出 | 公司既有平台的兼容候选，适合可视编排与移交；不能把官网最新能力假定为1.13.2具备，复杂业务事实和版本仍由自有后端负责 |
| 薄TypeScript后端直接调用模型 | 项目自行实现有限步骤和协议，不依赖Agent框架 | 必须保留的复杂度基线：若有限流程不需要持久中断，可能更便宜；一旦自行堆叠调度、恢复、检查点，就是隐性自研编排成本 |

不是寻找一个包替代全部后端。建议候选结构为：现有响应式页面 → 自有业务API和持久业务数据 → 单一可替换编排层 → 模型服务。工作流状态与业务事实区分；权限检查不托付给prompt，客户端不能选择更高权限角色。

暂不建议同时安装Dify、LangGraph、Mastra作为三层编排；首期只选择一个主要编排owner。此轮不因框架变化追加微服务、消息集群、知识图谱或管理平台。

## LangGraph为何保留为替代候选

官方将混合确定性与模型步骤、持久状态及人工介入明确作为核心能力，与流程需求匹配；但结合低代码接手要求，当前优先验证Dify与薄业务后端。持久检查点需要实际存储实现，内存saver无法跨重启；检查点也不等于外部模型调用或写库自动exactly-once。

Mastra和Dify都可能胜出：前者若显著减少集成与观察成本；后者若内网只能导入DSL、不能新增后端服务。尚未确认内网对额外Node/Python服务、依赖包及许可证的接受条件，不能把“逻辑适合”说成“可直接带进去”。

## 公平验收用例与停止条件

下一项建议是对主选和Dify兼容基线使用同一小型合成用例，而不是先各写完整产品。该验证实施需后续明确任务和owner。

1. 业务发起，按条件调用两个专业角色，保留分歧，见微形成给人的解释。
2. 用户补充后只更新受影响的结果；旧版本晚回执不得覆盖新事实。
3. 暂停后重启并恢复；重复请求不得重复写入或盲目重复付费调用。
4. 模型返回格式错误、缺依据、超时、一个角色失败都能显式恢复或停止。
5. 切换模型供应商不改前端；打包到干净本机环境重跑，检查外网/遥测依赖。

记录通过/失败、实际改动量、人工维护步骤、冷启动与常驻资源、延迟和token用量；不以主观百分评分冒充基准测试。达不到正确性与安全门的方案不因开发快胜出。若独立服务无法在内网落地，则回到Dify或获准的其他部署形式，不绕过内网限制。
