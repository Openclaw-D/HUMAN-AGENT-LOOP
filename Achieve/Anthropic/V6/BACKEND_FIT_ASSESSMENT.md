# 见微后端适配评估｜稳定、可接手、不过度建设

2026-09-12。评估依据：最新用户优先级、V6契约、rework-1独立验收、现有package.json、本机Dify 1.13.2源码与官方框架文档。属于方案评估，未做框架性能基准，未获得新平台实施授权。

## 结论

**优先验证Dify 1.13.2加薄业务后端，保留一套响应式前端；不先自研通用框架，不先换到代码优先框架。** 这是当前约束下的推荐，不是Dify最稳定或性能最高的事实声明。若同一关键场景证明Dify有明显缺口，再用LangGraph替换编排层。Mastra保持次级候选，不同时安装维护多套平台。

理由不是已花时间安装，而是团队现有Dify经验、低代码接手要求、内网迁移条件与当前有限六角色流程相互匹配。上一轮LangGraph初筛没有计入刚补充的低代码接手权重，故修正排序。非技术同事的可上手程度还须由实际任务证明，不能仅因有画布就宣布成立。

## 基于现有框架的逐项适配结论

以下为设计与源码层评估，不把运行测试当成推迟架构判断的理由。当前没有发现必须自研通用编排或放弃Dify的已证实硬缺口。

| 已知需求 | 本轮建议实现 | 是否属于平台绕行 |
| --- | --- | --- |
| 六角色、不同提示和上下文 | Dify配置角色对应模型步骤与条件；本机源码含LLM、If/Else、Code及并行Iteration配置 | 否，符合模型编排用途；不需要六套服务 |
| 固定校验与模型分析结合 | 后端验证业务输入，编排内做有限数据转换与角色调用 | 否，两者职责不同；不要复制同一正式业务状态机 |
| 人补充、纠偏、再分析 | 保存新资料版本，发起新分析，结果按输入版本接受 | 否，这是必要业务逻辑，不要求每次在旧工作流中断点续跑 |
| 一套手机/桌面页面 | 现有响应式前端调用统一业务API，不嵌入Dify管理画布 | 否，与编排平台相互独立 |
| 低代码同事维护角色参数 | 在受控Dify配置范围维护模型步骤；谁能改哪些内容仍须明确 | 不需先造编辑器；现有平台权限不自动等于项目要求的细粒度权限 |
| 重启、超时、回执丢失 | 后端记录运行关联和未知状态；能取得run ID时查询运行结果，未知时不能盲目重发 | 必要适配与可靠性工作，但付费执行和业务落库不是天然同一事务 |
| 多日暂停、旧工作流任意节点恢复或跨版本迁移 | 当前未确认为首期必需，不主动加入；若成为硬要求需专项核对 | 若因此要复制执行引擎、改Dify内核才属于高成本绕行 |

本机1.13.2的service_api/app/workflow.py实际包含按run ID查询、执行与按task ID停止的入口；这不证明API提供业务requestId级恰好执行一次。收到运行标识前断线仍有未知结果窗口，应如实暴露而非承诺自动恢复。Human Input源码存在，不等于本项目必须采用其内置表单，更不等于外部业务页面恢复已验证。

因此当前可以给出架构选择建议：Dify承载模型编排，自有后端承载业务事实与可靠边界。所谓“薄”按职责聚焦定义，不代表只有几行代码。完整实现和测试不能省略，但不需要先猜测未来复杂需求并据此换框架。

稳定性分三层，不能互相代替：

1. **运行可靠**：服务失败可识别、恢复有据、不会无限卡住或无限重试。
2. **状态正确**：不串项目、不丢草稿、不重复写入，旧分析不覆盖新资料。
3. **分析可信**：引用存在、未知会说明、专业分歧保留、模型不取得审批权。

现有rework-1报告里59项测试通过但仍实际复现草稿丢失，说明测试数量不能证明真实交互稳定；也说明换Dify或LangGraph不会自动修好前端请求归属。rework-2尚未独立验收，不将旧缺陷断言为最新仍存在。

目前没有真实模型闭环证据，不能承诺金融生产适用性。第一版是合成数据的人机协作demo，不是生产信审引擎。专业有效性最终需获授权的规则与专业人员验证。

## 方案对照

| 方案 | 贴近场景的优势 | 主要责任和缺口 | 当前位置 |
| --- | --- | --- | --- |
| Dify + 薄业务后端 | 复用公司平台经验，角色提示与分支可视配置，延续DSL移交 | 部署组件不算最少；画布配置也会出错，业务版本与幂等仍须自己做；旧版能力逐项验收 | 优先验证 |
| LangGraph JS + 业务后端 | 明确混合规则/模型、持久状态与人工介入机制，开发者可细粒度控制 | 代码维护占比高；给低代码同事的管理界面和运维并不会自动具备 | Dify出现明确限制时的强候选 |
| Mastra + 业务后端 | TypeScript流程、schema和Studio便于开发观察 | Studio可视观察不等于非技术人员安全维护；恢复、依赖和迁移需实测 | 保留次选，不额外开工程 |
| 最小自用步骤实现 | 固定有限流程时可少依赖，只实现需要的逻辑 | 调度、崩溃恢复、预算、版本与测试全归团队；要做拖拽和通用插件很快不再轻量 | 作为复杂度基线，不先自研平台 |

Dify本机这版已观察到11个长运行服务，不因此推断一定慢或不稳定。代码式框架不必带相同数量容器，但没有公平基准不能断言资源更省。业务同事使用的是见微页面，不是Dify管理后台；技术/获准配置人员才维护编排。

## 最小合理分工

**一套Web页面 → 业务后端 → 一个主要编排器 → 模型供应商。**

- 页面：展示事实、进度、需补充事项和模型反馈；mobile/desktop共享状态逻辑，仅布局不同。
- 业务后端：身份范围、项目事实、资料版本、请求幂等、任务归属和结果接受。模型失败不撤销已经成功保存的用户资料。
- 编排器：根据事件选角色，组合确定性校验与模型分析，汇总分歧；不是正式审批状态的权威来源。
- 模型：生成建议与依据引用，不直接写业务数据库、不改正式规则或额度。

只保留窄输入输出协议与供应商适配，不为了可替换而写通用插件系统。统一接口能减少前端变化，但不能自动迁移框架内部检查点或Dify应用。低代码配置优先暴露提示模板、已批准参数和适用分支；内部版本、权限和幂等逻辑不交给随意编辑。

## 自研怎样才值得

可以自研“这几个业务步骤”，不建议现在自研“什么流程都能跑的框架”。前者是必要领域代码，后者需要长期维护调度器、执行存储、可视编辑器、插件生命周期和恢复工具。

若有限流程只需一次分析、一次人补充后重算，可用显式步骤实现作对照；若开始需要长时间暂停、多分支恢复、在途任务升级，优先复用成熟持久执行能力。开源降低许可获取和代码复用门槛，并不消除业务验证、版本迁移与值守成本。

## 验收门，而不是稳定性保证书

用同一合成案例、同一模型配置比较，不用主观总分宣称获胜：

1. 发起→两专业角色有分歧→见微解释→用户补充→受影响结果更新；未受影响的事实不被覆写。
2. 请求到达前失败、已执行但回执丢失、重复点击、A→B→A切换、旧请求完成；页面和后台一致。
3. 执行中重启、单角色超时、模型格式错误或越权输出；恢复或明确失败，不能自动重复付费调用。
4. 有限并发下记录端到端与编排开销、排队、内存、失败率和实际用量；模型延迟与框架开销分开。当前尚无足够峰值人数/延迟目标，先记录不虚构SLA。
5. 同一低代码配置任务由拟接手人员完成，观察是否需改代码、是否能检查变更并恢复旧配置；不把可视画布当作可上手证据。
6. 干净环境导入/部署并重跑；重绑定凭证，检查包依赖、无秘密信息和无意外外网调用。

只有前三项正确性门通过，才比较速度和开发便利。使用真实模型的质量用例与本地故障注入分开报告；每批真实调用上限50万tokens，仅在安全提供密钥后执行。测试降低风险但不能保证绝不出错，发布前还需与交付等级相符的配置冻结、恢复方案和运行观察。

## 本轮具体建议

先不重写产品或替换平台。已有Dify环境保留；先把平台无关的最小业务闭环与验收用例定准，再验证Dify能否在薄后端配合下通过。若通过且接手成本低，就用Dify；若核心恢复/扩展场景需要大量绕行代码，再有证据地换LangGraph。当前管理员与密钥仍缺，不能将方案评估写成实际流程已完成。
