# 候选能力矩阵：七项门槛逐格核验

研究截止：2026-08-27。只把一手资料能直接支持的能力记为“有”；“部分”不补写为“有”；“未证实”不等于该能力不存在。`E` 编号见 `EVIDENCE_REGISTRY.md`。

## 判定规则

直接同类必须同时有：

1. **S 共享可恢复工作状态**：不是仅单人聊天记录或单次 run；
2. **M 多角色/多智能体**；
3. **H 显式交接/接续**：具名传递上下文或责任，而非仅汇总；
4. **P 责任/权限边界**；
5. **G 人工 Gate 或等价控制**：关键动作需人/策略明确批准；
6. **A 审计/事件证据**：可追溯事件/日志，而非只 UI 进度；
7. **E 真实企业工作流运行**：不是框架 demo 或单机 coding shell。

标记：`有` = 一手资料直接证实；`部分` = 局部/其他层证实；`未证实` = 本次未获得满足定义的一手证据；`不适用` = 产品定位本就不覆盖。任何一列非“有”，不得标为“直接同类”。

## 机器可检查结论

- 候选数：**22**（超过 15）。
- “直接同类”：**0**；因此不存在“标为直接同类但缺七项证据”的行。
- 中国候选且至少一手官方证据：Trae、Qoder、扣子、通义灵码、百炼、钉钉、CodeBuddy、腾讯云智能体、Comate、千帆、CodeArts、Dify、FastGPT、MaxKB、RAGFlow、OpenManus、MetaGPT、ChatDev、AgentScope（19 项；其中 C 级项目明确标为待补证而非能力声明）。

## 反证与阅读方式

“高度相邻”不代表“可以替换”。本矩阵刻意把「编排」「聊天日志」「企业 RBAC」「审批」「会话恢复」拆开：它们可以分别成立，仍不足以保证同一 Work 在断线/重启/换人/外部回执未知时能从事件重建、按版本审批并对责任负责。
