## 2. 逐项目抽取

### C01｜可信 AI 研发流水线

**原始问题**

- AI 研发输出不可信，模型可能跳步、上下文中断，甚至执行删除文件等高风险动作。
- 单纯换更强模型不能稳定解决流程可信问题。

**项目主张**

- 把一项需求视为一条独立产线，设置约八个研发状态节点。
- 每个节点定义进入条件、必需产物、禁止清单和停止条件；未过 Gate 不进入下一阶段。
- 用全局 `current state` 与每个变更独立 `state` 文件做双层外部持久化，不依赖聊天记忆恢复。
- 主 Agent 只负责编排和状态推进；Review Agent、Test Agent 各自只有受限职责，并禁止修改代码。

**真实优势**

- 技术对象、失败模式和治理机制都很具体，明显强于只展示前端的项目。
- 已经触及见微关注的 State、Gate、Context continuity、职责分离和可恢复性。

**评审风险**

- 更强 Coding Agent、现有研发治理平台是否已经覆盖大部分能力。
- 八阶段、三 Agent 和双层状态会增加 Token、等待与维护成本。
- 当前是研发垂直流水线，能否迁移到企业业务协同仍未证明。

**对见微的约束**

> “Harness、状态机、持久化、Agent 分工”都不能单独构成见微的独特性。见微必须证明具名人员、企业权限、责任接受、跨系统回执和业务事项连续性，而不是复刻研发流水线。

### C02｜商品车金融“找对人、说对话”助手

**原始问题**

- 新客线索分散、难以筛选和触达；销售能力不均；金融产品复杂；外部商机信号没有被有效利用。

**项目主张**

- 读取内部客户信息与外部经营、展会、融资到期等信号。
- 用自然语言描述目标客群，解析为结构化条件并输出客户评分。
- 为客户生成意向判断、产品方案、额度区间、触达话术和后续运营动作。
- 根据意向程度把客户推给客户经理或官方企业触达渠道。

**真实优势**

- 用户、场景和收入路径直观，“知道敲什么门、说什么话”的价值容易被业务领导理解。
- 圈客、评分、方案、话术和触达可以形成强 Demo。

**评审风险**

- 外部信号质量、评分准确率和转化归因未形成可靠证据。
- 动态话术宣称“百分百合规”风险极高。
- 功能面过宽，难以说明哪一段是不可替代的自研核心。

### C03｜虚拟销冠协同萃炼

**原始问题**

- 海量客户与有限销售精力矛盾；临场需求变化快，培训跟不上；少数销冠经验难以覆盖大量普通销售。

**项目主张**

- 从销冠轨迹、纪要、沟通记录和明细数据中萃炼复合知识。
- 结合客户层级、客群信息、合规筛查、销售模型和心理模型进行虚拟客户对抗与评分。
- 内容经亮灯后进入投产，并随客户行为与沟通反馈持续调优。
- 长期串联数据、策略、内容、外呼与协同执行。

**真实优势**

- 有明确的稀缺资源放大逻辑：把少数高绩效人员的经验服务于更多销售。
- 相比单次生成话术，更强调持续反馈和投产机制。

**评审风险**

- 销冠表现包含客户筛选、时机、关系和隐性经验，未必能被文本萃炼完整复制。
- 容易固化幸存者偏差；反馈闭环也可能放大错误经验。
- “协同”主要服务于营销内容生产，尚未形成跨角色责任与权威状态。

### C04｜租赁物审核前置与流程重构

**原始问题**

- 授信、提款合同、全组文件交接和付款串行运行；后段发现清单或发票问题后需要层层退回，流程往复严重。

**项目主张**

- 将租赁物审核从提款合同流程中解耦，前置到授信阶段并与授信并行。
- 由商务整合审核，释放信审处理更高价值的风险判断。
- 用 AI 排重、发票验证和动态规则提前探测风险。
- 审核通过后的租赁物数据由后续流程自动继承，并用版本控制支持新旧模式并行。

**真实优势**

- 核心不是生成内容，而是真实流程再造；用户、流程节点和效率损耗明确。
- 有直接业务量、时效和产能衡量空间。

**评审风险**

- 创新可能被理解为现有流程优化，而非 AI 独特能力。
- 移动端、规则配置、AI 校验、微服务和流程改造叠加后，首期范围并不轻。
- 可迁移机制和真实投入产出仍需证明。

### C05｜AI 外呼作战体系

**原始问题**

- 外呼规模快速增长，但名单转交到客户经理可能延迟数小时或数天。
- 客户经理只收到名单，不知道 AI 或上一位客户经理此前聊过什么。
- 客户在多次触达、跨座席流转时，意向和上下文发生断裂。

**项目主张**

- 外呼前进行名单挖掘、画像分析、成功经验匹配、话术与触达时机配置。
- 支持批量外呼与客户经理即时发起外呼，把部分响应从小时级缩短到秒级。
- 外呼后由大模型挖掘多轮沟通中的意向演化，并将上下文带给下一座席。
- 从成功案例中提炼关键话术和最佳时机反馈给团队。

**真实优势**

- 用户痛点、业务规模、触达动作和上下文断裂都非常具体。
- 已经展示“AI → 人 → 下一位人”的连续性，不只是单个 Agent 输出。

**评审风险**

- 名单质量、触达时机、话术、人工能力同时变化，转化提升难以归因。
- 多轮总结错误可能污染后续营销；成功话术需要人工确认和纠错机制。
- 上下文连续仍局限在外呼场景和客户对象内。

**对见微的约束**

> “跨人上下文连续”和“人机协同”也不是见微独有。见微必须证明可替换 Agent、临时专家、企业权限、具名责任接受和同一权威事件历史能跨场景复用。

### C06｜数据开发人员 AI 分身

**原始问题**

- 取数、报表开发、大数据开发和 SQL 优化高度重复；业务口径不统一；用户在非工作时间也会发起需求。

**项目主张**

- 把个人开发经验蒸馏为 AI 分身，面向非技术用户 7×24 提供取数与报表服务。
- 用语义知识库统一不同部门对“投放、融资”等指标的表达。
- 匹配指标库、表结构知识库和数据模板，自动生成脚本或报表。
- 把 SQL 优化与平台开发经验固化为可复用能力。

**真实优势**

- 高频痛点来自本人真实工作，知识、数据结构和用户入口都较明确。
- 容易用工时、响应时间和错误率做前后对照。

**评审风险**

- 本质容易退化为个人 Agent；原创资产与跨岗位迁移性不足。
- 取数、SQL 和报表错误会直接影响业务，准确率、完整率和拦截机制要求高。
- 首期同时覆盖四类开发工作，范围过宽。

### C07｜AI 汽车销售助手

**原始问题**

- 普通汽车销售缺少对客户偏好、车辆价值和成交方案的深度理解。

**项目主张**

- 设想接入保单、家庭成员、银行流水、体检、车辆评估、产品与维保等多源数据。
- 推断客户意向，匹配车型，评估保值率和换车时机。
- 动态生成金融方案、销售内容，必要时生成视频辅助成交。

**真实优势**

- 故事化表达、销售逆袭和动态方案具有现场感染力。
- 集团多业务数据若能合法使用，可能形成区别于汽车信息平台的资产视角。

**评审风险**

- 高度依赖敏感数据授权，部分设想在现实权限下可能无法成立。
- 懂车帝、汽车之家等平台的车型、价格和市场数据可能更全、更实时。
- 娱乐化叙事可能掩盖产品对象、验证指标和数据边界。

### C08｜AI 细分市场经营决策

**原始问题**

- 企业依赖人工经验设标签和规则，难以发现未知高价值细分市场；策略触达不够及时、精细。

**项目主张**

- 将财务边际贡献模型和业务洞察标准化、标签化为企业数据资产。
- 建立业务知识库并通过在线训练、动态更新形成自我调整机制。
- 引入经营决策 Agent，综合财务、风险和企划策略，推断下一步最佳行动。
- 通过移动端把智能策略送到一线。

**真实优势**

- 直接面向经营资源配置和高价值市场发现，集团价值叙事很大。
- 财务、企划、科技共同参与，天然具备跨部门背景。

**评审风险**

- 数据资产、知识库、Agent、自主决策和移动端同时展开，核心产品不清。
- “自我进化决策大脑”容易超出数据、权限和治理现实。
- 缺少首个具体决策、输入输出、系统接入和可量化 MVP。

### C09｜客户经理拜访助手

**原始问题**

- 客户经理拜访前需要查授信、工商、财务、风险和历史信息，并准备材料与话术，耗时且可能不准。

**项目主张**

- 一键完成企业 360 画像、关联关系、风险扫描和财务分析。
- 生成客户情况看板、拜访材料和话术，并提供融资到期等预警。
- 目标是把约 30 分钟准备压缩到数分钟甚至更短。

**真实优势**

- 使用时刻清楚，操作和前后对比简单，现场容易演示。
- 可以直接测量准备时间、材料覆盖率和客户经理使用率。

**评审风险**

- 客户画像、材料整理和话术生成很容易被通用模型或 CRM 厂商覆盖。
- 多源数据口径冲突、幻觉、错误修正与责任归属未解决。
- “展示材料更快”不自动等于客户转化提升。

### C10｜挂车资产智能运营

**原始问题**

- 挂车资产位置和状态不可见，空挂与闲置率高，货源和资产在地域、季节上不平衡。

**项目主张**

- 与车厂合作在挂车前装 IoT/GPS，使位置、状态和闲置情况可见。
- 基于历史货运数据预测货源需求，提前调拨并降低等待、空驶和闲置。
- 当平台连接足够多资产后，支持不同物流企业之间共享闲置挂车。
- 金融公司以融资资产和客户网络切入运营入口。

**真实优势**

- 连接物理资产、运营效率和金融业务，商业想象力强。
- 若能形成网络，数据和供需匹配可能产生平台效应。

**评审风险**

- 车厂、物流平台可能比金融公司更有入口优势。
- 前装 IoT、客户数据共享、调度算法和跨企业交易均为重投入。
- 没有真实运力和货源数据时，预测与资产共享难以成立。

## 3. 横向抽取：这些项目实际上在做什么

### 3.1 类型分布

按本研究的功能分类，而非赛方官方分类：

- **八组**主要是垂直 Agent、助手或决策应用：C02、C03、C05、C06、C07、C08、C09、C10。
- **一组**主要是业务流程重构：C04。
- **一组**主要是受控 Agent Harness：C01。

这意味着“别人都只是单 Agent”并不准确。竞争场已经出现三种层次：

1. **能力节点**：画像、评分、推荐、话术、取数、预测；
2. **垂直闭环**：把数据、模型、人工动作和反馈串进一个业务场景；
3. **控制机制**：状态、Gate、持久化、Agent 职责与权限收口。

### 3.2 高频公共链路

多数项目可抽象为：

```text
数据 / 业务信号
→ 语义归一、画像或知识库
→ 模型分析、评分或预测
→ 推荐、方案、话术或任务
→ 人或现有渠道执行
→ 业务结果反馈
```

更成熟的项目已经尝试加入：

```text
状态持久化 / 数据继承 / 跨人上下文 / 人工确认 / 规则校验
```

### 3.3 共同优势

- 多数来自真实岗位痛点，第一用户和使用时刻比平台型项目更清楚。
- 很多团队拥有内部数据、现有业务入口或历史流程，可低成本形成 Demo。
- 销售、审核、外呼、取数等场景天然具备工时、转化、时效或规模指标。
- 现场表达通常以一个具体人物、客户或流程开场，容易被业务评委理解。

### 3.4 共同风险

1. **数据可得性被当作前提**：跨系统权限、实时性、口径和责任经常没有闭环。
2. **模型能力被当作壁垒**：画像、总结、评分、话术、SQL 等能力会被基础模型和既有 SaaS 快速商品化。
3. **结果缺少因果归因**：名单、流程、人员、话术和模型一起改变，难以证明收益来自哪一环。
4. **输出可信机制不足**：幻觉、偏差、错误经验放大、动态合规和最终责任仍是薄弱处。
5. **真实系统接入不清**：Demo 能生成结果，不等于能进入企微、CRM、审批、外呼或生产研发流程。
6. **范围容易扩张**：从一个助手迅速延展为全流程、全生命周期或决策大脑，首期资源与 Gate 不清。
7. **复用性多为口头主张**：很多项目声称可迁移，但没有证明哪些数据结构、规则和机制真正跨场景复用。

## 4. 对见微独特性的直接约束

### 4.1 已被竞争场占用、不能单独作为定位的词

- “人机协同”：C05 已经在真实外呼链路中使用。
- “共享/连续上下文”：C05 已提出多轮、跨座席继承。
- “状态机、持久化、Gate”：C01 已经给出具体机制。
- “数据继承与版本控制”：C04 已用于跨流程审核。
- “群体智慧/经验萃炼”：C03、C06 已经在做。
- “企业智能决策中枢”：C08 已经占据相近宏大叙事。
- “Agent Harness”：C01 已经是直接的结构性邻近物。

因此，见微不能只把这些名词排列在一起，就声称完成差异化。

### 4.2 当前仍可能成立的组合差异

原始项目中尚未看到一组同时把以下机制作为通用产品对象：

1. 多个具名人员与多个可替换 Agent；
2. 围绕一个稳定的企业协同事项而非某个垂直任务；
3. 私有上下文与经确认的共享上下文分层；
4. 具名接收后才发生责任转移；
5. 角色和事项级权限决定可见内容与动作；
6. 人、Agent、规则和外部系统动作均进入同一权威事件历史；
7. 换人、换 Agent、换入口后仍从同一状态继续；
8. 同一内核能在语义、责任和风险结构明显不同的场景中复用。

这是**基于本批原始项目的竞争空位假设**，不是已冻结定位，也不是全球市场“无人实现”的证明。

### 4.3 见微面临的答辩压力

见微比垂直项目更容易被追问：

- 谁会每天主动使用，而不是只有架构师觉得重要？
- 第一个具体场景的直接收益是什么？
- 为什么不直接在现有 OA、企微、项目管理或 Agent 平台中加功能？
- 通用性如何避免变成大而全？
- 与 C01 的可信研发 Harness、C05 的跨座席协同相比，新增机制到底是什么？
- 第一版不接大量系统时，如何真实证明跨系统和跨角色价值？

## 5. 对 P2 产品发现的当前影响

### 5.1 可以保留的判断

- 不与垂直 Agent、Skill 或 MCP 抢具体任务是正确边界。
- 轻量入口、稳定协同事项、可替换 Agent 和失败关闭仍有价值。
- 企业身份、权限、责任、回执与事件证据必须成为真实机制，而不是答辩术语。

### 5.2 必须修正的判断

- 不能再笼统地说“其他项目都没有协同”；它们在垂直链路中已经有不同深度的协同、继承和反馈。
- 不能把 `Shared Context + State + Handoff` 本身视为充分差异；至少 C01、C04、C05 已分别覆盖其中的关键部分。
- 平台叙事不能代替第一个高频入口；垂直项目在用户、痛点、Demo 和 ROI 上天然占优。

### 5.3 MVP 需要证明的最小差异

P2 MVP 不应只展示一个 Agent 输出或一个固定工作流，而应让用户亲自验证：

```text
同一协同事项
→ 多名具名人员各有可见边界
→ 多个可替换 Agent 在授权范围内参与
→ 局部信息经确认后进入共享上下文
→ 具名接收完成一次责任接力
→ 人工决定后 Agent 从同一状态继续
→ 外部动作回执回到同一事件历史
```

并至少用第二个异质场景证明：改变的是参与者、规则和 Adapter，而不是重新写一套内核。

## 6. 当前结论与未决项

### 已形成的证据结论

- 决赛场并非只有浅层 Agent；已经存在垂直闭环、流程重构和 Harness 控制三类竞争。
- 见微真正的竞争压力不只来自外部厂商，也来自内部项目对“协同、状态、上下文和企业中枢”等概念的局部占用。
- 见微若只讲宏大愿景，会输给用户更清楚、收益更直接的垂直项目；若只讲状态与接力，又会与 C01、C04、C05 重叠。

### 仍需继续讨论

- 哪类人是见微第一位高频用户，而不是泛化的“企业员工”？
- 第一个协同事项为什么必须同时需要多名具名人员与多个 Agent？
- 见微第一版的直接业务收益，是缩短决策周期、提高专家杠杆、减少重复建设，还是降低接力损耗？
- 哪个可见动作最能让用户在一分钟内理解见微，而不是把它看成聊天室、工作流或 Agent 管理台？
