# 见微-人机协同平台：P0 收尾与 P1 交接

日期：2026-08-27  
状态：P0 已收尾；不代表旧系统达到正式 P1

## 1. P0 实际完成内容

P0 完成的是产品方向重置、历史资产归整和控制边界建立，不是通用平台的正式实现：

- 唯一项目与决赛名称固定为“见微-人机协同平台”。
- 产品定位固定为面向企业的通用人机协同 Harness，不再以 TAG、RelayOS 或单一风控流程作为产品边界。
- TAG 与 RelayOS 代码归入 `sources/legacy`，中国 AI 市场材料归入 `sources/research`，均只作为候选数据源和证据。
- 十场景采用市场反向提炼；十个场景都必须深入研究真实需求、角色、协同断点、责任、Gate、产物和指标。
- 首页前三场景与顺序固定：风控业务协同、需求开发协同、人机交互协同。
- 候选能力采用“跨三场景资格线”，避免把单场景特性误写成通用内核。
- 前端方向固定为极简工作台：顶部紧凑选择与状态、左侧大协同视图、右侧详情看板、低频信息折叠。
- 后端先轻量，但前端不得伪造状态；前后端按最小纵向闭环持续连调。

## 2. 当前证据与限制

- `127.0.0.1:4177` 当前运行的是 RelayOS 历史界面，仅用于参考和交接，不是新 V1 首页。
- 历史实现已有十个场景配置，但只有少量旧 WorkCase 数据，场景顺序、命名和信息架构均不符合新基线。
- 历史测试、Gate 和阶段编号只算候选证据，不能证明新平台已经完成 P1。
- 其余七个场景的正式名称和优先级尚未冻结，必须由真实市场研究产生。
- 新 V1 的前端、轻量后端与真实连调尚未开始正式实现。

## 3. P1 总控职责

P1 只设一个阶段总控任务。总控负责：

- 保留产品目标、架构边界、决策、依赖、状态和 Gate；
- 把市场研究、前端、后端、前后端连调、验证等具体工作分发到独立的用户可见 Codex 任务；
- 为每个执行任务提供完整冷启动上下文、范围、允许路径、禁止边界、交付物、验收命令和停止条件；
- 根据任务自身复杂度选择 model 与 thinking effort，不继承总控的 effort；
- 综合各执行任务证据，识别漂移，作出是否进入下一 Gate 的判断。

P1 总控不得亲自实现前端、后端、连调或市场研究，也不得用控制任务重复执行任务的原始工作。总控可以进行必要的只读状态检查、结果综合和控制文档维护。

## 4. P1 建议分发顺序

1. **市场研究任务**：深入验证十个场景，冻结其余七个名称、需求证据和指标候选。
2. **前端架构任务**：基于已确认布局形成极简响应式页面和真实状态契约，不扩写后端能力。
3. **轻量后端任务**：只实现支撑当前纵向切片所需的通用 Work/Projection/事件与接口。
4. **前后端连调任务**：以前三个锚点场景验证同一内核、真实 Projection、失败与空状态。
5. **独立验收任务**：按照市场证据、产品契约、运行结果和负向路径提交可复核证据。

这些任务存在依赖，不能为了并行而同时修改尚未冻结的接口。每个任务完成后回到 P1 总控做综合和 Gate 决策。

## 5. P1 启动 Gate

P1 总控启动后，第一步只建立控制板、问题清单和待分发任务图，不做具体实现。首个需要共同确认的问题是：十场景市场研究应先冻结到何种证据深度，才能支撑前端信息架构与共享内核选择，同时又不阻塞前三个场景的最小纵向切片。
