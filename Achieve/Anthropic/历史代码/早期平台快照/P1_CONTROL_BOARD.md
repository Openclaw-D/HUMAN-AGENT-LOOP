# 见微-人机协同平台：P1 控制板

日期：2026-08-27  
状态：`P1 REOPENED`；旧技术闭环为候选基线，十场景与 V2 三视图需求重新冻结中

## 1. P1 唯一目标

以真实市场证据为输入，把十个场景全部转化为同一权威状态上的关系、进度、矩阵三种可操作视图与右侧接续台；随后完成全中文前端、十场景轻量后端、项目内模型运行接口、前后端真实连调和独立验收，使责任、交接、循环、补证、冲突、模型失败与外部结果未知均可恢复、重放和审计。

## 2. 已冻结产品决定

- 十个场景名称依次为：风控业务协同、需求开发协同、人机交互协同、内容生产协同、经营增长协同、物理智能协同、知识办公协同、客户服务协同、供应链履约协同、医疗服务协同。
- 物理智能协同与医疗服务协同保留市场证据的有条件边界；这不改变入口名称。
- 1920×1080 为桌面响应式基线：顶部固定 10%，下方左侧协同画布 80%、右侧接续台 20%。背景白色，视觉只使用黑、白与克制灰阶。
- 左侧固定提供关系、进度、矩阵三种视图；P1 不实现自定义视图。
- 右侧是聊天外观的接续台，承载消息、Artifact、Challenge、Handoff、HumanGate、ActionIntent、Receipt 与系统事件；不是纯聊天框。
- 产品前端只显示后端真实 Projection；视觉原型或测试 fixture 必须与产品运行状态隔离且明确标识。
- 十场景的推荐默认视图、默认中心、矩阵维度和场景独有循环由 R1 市场到视图契约提出，经 G1 与用户共同冻结；旧版本的默认映射仅作候选，不再拥有产品权威性。
- 关系视图必须支持节点拖动、画布平移、缩放与 `Ctrl+滚轮` 缩放；坐标只属于本地展示，不得成为业务状态。进度视图必须表达完整阶段、分支、卡点、负责人、输入输出、下一步、版本漂移与循环/返工/补证/重试/暂停恢复/回退。矩阵必须显示参与者与阶段/任务间的责任、权限、状态、交互和异常，并支持单元格下钻。
- 删除旧左下“查看全局/查看全局动态”栏。全局/局部上下文、画布选择和三视图选择都在右侧接续台联动；普通消息不自动运行模型，只有人类显式命令才创建模型运行。
- 右侧接续台同时承载最近对话、输入框、选中对象、责任/权限、待接动作、证据/回执、人工关口、异常、历史上下文和模型运行状态；通过常显摘要、折叠区和临时详情避免拥挤。
- Gate 先以内联卡展示依据、版本、责任人与影响；真实副作用进行二次确认。顶部第二行固定表达目标摘要、owner、阶段、Challenge、Gate、Receipt 和更新时间；无真实指标时显示“暂无真实数据”或 `—`。
- 移动端 P1 只保证可读、可操作与单列堆叠；正式视觉 Gate 仍以 1920×1080 为准。
- 项目最终展示必须全中文：所有用户可见文字不得出现英文字母；代码、接口与内部枚举可以保留英文，但必须在进入页面前映射为中文。完整验收清单见 `P1_CLOSEOUT.md` 第 8 节。

## 3. 单一权威 Projection 硬约束

以下约束不可由执行任务重新讨论或放宽：

1. 同一协同事项只有一个权威 Event 历史和一个权威 `WorkProjection`。
2. 关系、进度、矩阵三种视图必须绑定同一个 `workspaceId`、`workId`、`projectionVersion`、`eventCursor` 与 `generatedAt`。
3. 三种视图是同一 Projection 的不同 selector/renderer，不得拥有各自的后端状态机、数据库、事件流、owner、Gate、Receipt 或指标真相。
4. 切换视图只改变本地展示，不产生业务事件，也不改变 Projection。
5. 若分片读取导致版本或事件游标不一致，前端必须 fail closed：显示刷新/不一致状态，不得拼接成貌似成功的页面。
6. ScenarioPack 只能声明默认视图、显示术语、阶段映射、矩阵维度、字段 Schema、Policy 与 Connector；不得创建第二套权威状态。
7. 普通消息只能追加非权威协同上下文。任何 owner、Goal、Handoff、Gate、Action 或 Receipt 变化必须转换为显式 Command，并遵守权限与具名人工控制。

## 5. GLM-5.3 路由

- GLM-5.3 不负责产品判断、Projection 架构、视觉设计、浏览器检查或最终验收。
- 正常的市场、产品、前端、后端、连调和验收任务全部创建或恢复在“见微-人机协同平台”项目内。独立“GLM”项目只处理 runner、provider、transport、额度、认证或工具链本身的故障。
- B1 由本项目内 Codex/GPT 执行任务负责契约、拆分和验收；契约冻结后，把边界明确、文件所有权精确、可客观测试的实质后端编码检查点通过受控串行 runner 交给 GLM-5.3。
- 优先 GLM 检查点是 V2 状态投影/重放、十场景包装载、模型运行适配器或对应契约测试中的一个内聚模块；不能让 GLM 决定产品需求、视觉或最终 Gate。
- GLM 输出必须由执行任务独立检查文件边界、测试、`turn.completed`、用量、耗时、权限拒绝和残留进程，再提交总控 Gate。
- 若 GLM 明确返回额度或速率限制，立即停止追加调用并保留 JSONL；只有用户明确要求延后续跑时才创建定时任务。续跑前必须确认没有仍在运行的 GLM 调用，且只允许一次有明确价值的串行恢复。

## 6. 任务与上下文控制

- 本任务是唯一 P1 总控，只保留目标、边界、决策、依赖、状态、风险、证据综合和 Gate。
- 中小型以上的前端、后端、连调和验收工作均使用独立用户可见 Codex 任务；每个任务包含完整冷启动上下文、允许路径、禁止边界、交付物、验收命令、证据和停止条件。
- 不为了表面并行提前启动有未满足依赖的任务；已完成任务可归档，避免侧栏和上下文噪声。
