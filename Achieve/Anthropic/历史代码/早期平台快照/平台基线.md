# 见微-人机协同平台：平台基线

日期：2026-08-27  
状态：P0 产品方向已收尾；P1 正式规划基线

## 1. 产品定义

见微-人机协同平台是企业级人机协同运行与治理 Harness。它不替代 CRM、ERP、代码库、工单、文档或风控系统，也不为某个部门预置一套固定状态机；它把这些系统中的事实、企业规则、Agent 能力、人类责任和可执行工具组装成可运行、可监督、可评估的工作闭环。

平台稳定回答五个通用问题：

1. 当前要完成什么工作，目标和成功标准是什么？
2. Agent 此刻能够看到哪些上下文、能够调用哪些能力？
3. 哪些动作可以自动执行，哪些必须由具名人类决定？
4. 运行产生了什么证据、产物、外部影响和责任变化？
5. 这次人机协作是否正确、有效、经济，并且能够重放和追责？

## 2. 与 Codex Harness 的结构类比

| Codex 概念 | 见微通用概念 |
| --- | --- |
| Project / Workspace | `Organization / Workspace` |
| Thread / Task | `Work / Session` |
| User + Agent | `Actor / Participant` |
| AGENTS instructions | `PolicyPack / Playbook` |
| Model selection | `ModelProfile / RoutingPolicy` |
| Tools / connectors | `Capability / Connector` |
| Context window | `ContextSnapshot` |
| Approval | `HumanGate` |
| Tool call | `ActionIntent / ExecutionReceipt` |
| Files / output | `Artifact / Evidence` |
| Test / review | `Evaluation / OutcomeMetric` |
| Conversation history | `BusinessEvent / Projection / Replay` |

这只是结构类比，不意味着产品只面向编码，也不复制 Codex 的具体界面和实现。

## 3. 通用内核对象

### 组织与控制

- `Organization`：企业租户和治理边界。
- `Workspace`：团队、项目或长期业务域的上下文边界。
- `Actor`：人、Agent、服务账号或外部系统身份。
- `RoleBinding`：Actor 在特定范围和时间内承担的角色。
- `AuthorityGrant`：允许发起、批准或执行的明确权力；模型默认没有后果性决定权。
- `PolicyPack`：版本化规则、约束、审批条件和数据使用边界。
- `Capability`：可被运行时发现和调用的模型、工具、知识源或外部动作。

### 工作与运行

- `Work`：需要推进的通用工作单元，不绑定案件、工单或风控语义。
- `GoalVersion`：目标、约束和成功标准的不可变版本。
- `Session`：围绕 Work 的一次人机协作上下文。
- `Run`：某个 Agent 或编排器在明确输入、模型和能力下的一次执行。
- `Task`：Run 内或多参与者之间可分配、可验收的工作节点。
- `Handoff`：责任转交提议；只有具名接收者接受后才改变 owner。

### 上下文与产物

- `ContextItem`：来自企业系统、人员或前序运行的上下文引用。
- `ContextSnapshot`：某次运行实际使用的不可变上下文清单与 hash。
- `Evidence`：支持判断或结果的可定位、可验证材料。
- `Artifact`：人或 Agent 生成的结构化产物。
- `Challenge`：信息缺失、冲突、不可核验或策略不满足时的闭环对象。

### 决策与执行

- `HumanGate`：受保护动作执行前必须满足的人工控制点。
- `DecisionRecord`：具名人类基于特定 ContextSnapshot 作出的决定。
- `ActionIntent`：外部副作用发生前的规范化执行意图。
- `ExecutionReceipt`：执行后的 `succeeded / failed / unknown` 回执和外部引用。

### 评估与历史

- `BusinessEvent`：唯一权威、不可静默改写的状态变化历史。
- `Projection`：从 Event 派生的查询和界面状态。
- `Evaluation`：对 Run、Artifact、Decision 或完整 Work 的质量评估。
- `OutcomeMetric`：时延、成本、质量、风险、人力节省和业务结果。

## 4. 最小运行闭环

```text
Signal / Human Request / System Event
                  ↓
          Work + GoalVersion
                  ↓
     Context Assembly + Policy Check
                  ↓
           Agent / Human Run
                  ↓
 Artifact / Challenge / Proposed Action
                  ↓
       HumanGate（按策略可选）
                  ↓
      ActionIntent → Connector → Receipt
                  ↓
      Evaluation + Outcome + Replay
```

任何业务场景必须通过这条通用链表达。若一个场景需要新增行业专用状态机，优先检查它是否应当是 PolicyPack、Playbook、Capability、表单 Schema、指标或 Connector，而不是修改平台内核。

## 5. 平台与业务包边界

业务包只允许声明：

- 角色与术语显示；
- 表单和 Artifact Schema；
- Playbook、PolicyPack、Gate 和评估 Rubric；
- 所需 Context Source、Capability 和 Connector；
- 目标指标和去标识化示例数据。

业务包不得绕过 AuthorityGrant 或 HumanGate，不得创建第二套身份、事件、任务或审计系统，不得在 Connector 失败时伪造成功，也不得把演示 fixture 描述为真实客户或生产验证。

## 6. P1 验收边界

P1 先证明十场景可以共享一个 Harness 内核，而不是制造十套行业产品。十个场景都需要真实市场研究和深层语义建模；前三个场景是首批工程锚点，不是其余七个场景可以降级为展示卡片的理由：

1. 一个 Workspace 能装载版本化 PolicyPack、Playbook 和 Capability。
2. 同一个通用 Work/Run 内核先运行三个语义明显不同的场景包：风控业务协同、需求开发协同、人机交互协同。
3. Agent 只能基于显式 ContextSnapshot 产出 Artifact 或 Proposed Action。
4. 受保护动作必须经过具名 HumanGate，并产生可核验 Receipt。
5. 失败、未知、拒绝、补证和责任交接均可恢复、可重放、可审计。
6. 前端只显示后端真实 Projection，不存在本地伪成功。
7. 至少有一组质量、成本、时延和业务结果指标。
8. 其余七个场景以真实市场证据完成需求、角色、上下文、协同断点、Gate、产物和指标建模，并接受相同内核适配检验。

共享能力采用“跨三场景资格线”：只有至少三个语义、责任和风险结构明显不同的场景都真实需要，候选能力才有资格进入平台共享内核；仅一至两个场景需要的能力应保留在 ScenarioPack、PolicyPack、表单 Schema、指标或 Connector 中。该资格线是必要条件，不是充分条件，仍需检查安全边界、实现成本与可解释性。

P1 未共同验收前，旧项目的测试数量、阶段标签和历史 Gate 只算候选证据。

前三个锚点场景的对象映射、流程和防漂移验收见 [三场景融合方案.md](三场景融合方案.md)。
