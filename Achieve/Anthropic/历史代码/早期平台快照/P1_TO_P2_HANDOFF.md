## 三、必须迁移到 P2 的冻结决定

1. 项目与展示名称固定为“见微-人机协同平台”，用户界面全部使用简体中文。
2. 十个场景同等重要并全部做深：风控业务协同、需求开发协同、人机交互协同、内容生产协同、经营增长协同、物理智能协同、知识办公协同、客户服务协同、供应链履约协同、医疗服务协同；不得收缩为风控主场景或“三真七假”。
3. 共享内核从十场景横向量化抽取。能力进入内核的必要条件是至少三个在语义、责任和风险结构上明显不同的场景真实需要，并同时满足安全、成本、可解释性和单一事件/投影语义。
4. 同一协同事项只有一套 Event 历史和一个权威 Projection；关系、进度、矩阵是同一 Projection 的三个 selector，不得拥有三套后端状态或版本。
5. 桌面基线保持 1920×1080、顶部约 10%、下方左画布约 80%、右侧接续台约 20%；白底，主要黑白，灰阶仅用于克制强调。
6. 关系视图突出角色、责任、相对位置、交接与权限，并支持拖拽、平移和 `Ctrl+滚轮` 缩放；进度视图表达阶段、分支、循环、卡点、补证、返工、暂停恢复与下一步；矩阵表达参与者×阶段/任务的责任、权限、状态、交互与异常。
7. 右侧是“聊天 + 结构化接续台”，不是纯聊天。普通消息不触发模型；模型运行、目标变化、责任变化、交接、人工关口、动作和回执必须是显式、可审计、失败关闭的操作。
8. 模型无业务权威；模型完成、候选产物通过、外部动作成功是三个不同事实。未知、失败、限流、超时和断连不得伪装成成功。
9. 中国公开市场中尚无被一手公开证据证明同时满足七项完整门槛的直接同类。采用“自研最小 Corporation Harness 控制内核 + 局部复用 Codex CLI 会话/状态流/沙箱审批等思想 + 中国企业连接器与合规适配”。Codex `resume/fork` 不等于业务责任交接。

## 八、归档前已确认决定

### 决定一：P2 作为重新开始的独立阶段

用户确认 P1 存在严重目标漂移：产生了大量 Token、代码和自动化结果，但用户无法清楚理解其中许多实现，也没有完成对应的产品验收。P2 不在 P1 目录中继续堆叠实现，而是重新冻结目标、可验收输出和执行顺序。

P2 使用独立目录：

- `prototype/p2-frontend/`
- `runtime/p2/`
- `integration/p2/`

P1 的 `prototype/p1-frontend/`、`runtime/p1/`、`integration/p1/` 原样保留为候选资产、历史证据和失败案例。P2 不得直接覆盖这些目录，也不得把其中代码默认视为应当继承；任何复用都必须先说明用途、与新冻结目标的对应关系和独立验收方法。

### 决定二：场景推进策略延后到 P2 重新讨论

用户当前对十场景的推进方式仍有犹豫，因此不在 P1 收尾时冻结“十场景最小闭环 + 三个深链”或其他实施顺序。P2控制应先从项目最终解决什么问题、目标用户为什么需要它、首个可亲自验收的结果是什么开始重新定向；在用户明确决定前，不创建场景、前端、后端或连调执行任务。
