## 1. 已明确、暂不回退的产品边界

### 1.1 五个核心点

1. **大型金融机构级**：必须处理身份、权限、责任、审计、失败、内网和组织边界，而不是个人玩具或泛企业概念样机。
2. **Agent Harness**：允许接入、配置和替换多个 Agent，但不与垂直 Agent、Skill 或 MCP 抢具体工作。
3. **人机协同**：重点不是单人使用 Agent，而是人通过 Agent 与其他人协作，同时支持 Agent 与 Agent 接续。
4. **多人上下文连续**：三至五个人同时推进同一件事时，不因换人、换 Agent 或换入口而重新开始。
5. **轻量化**：商业价值可以很大，但第一次部署、第一次理解和第一次使用必须很轻。

### 1.2 暂定一句话

> 见微是一套面向大型金融机构的轻量至中等重量人机协同 Harness，让前中后台的多个人和可替换 Agent 围绕同一协同事项共享必要上下文、可靠接续，并可审计地完成工作。

这句话是本轮工作定义，不是最终品牌文案。

### 1.3 融资租赁“大风控”切入边界

`用户已确认 / 本轮方向收束`：决赛业务范围只使用融资租赁，不再混入银行、保险、信托或“全牌照”叙事。用户以自身风控经验为基础，把“大风控”团队做清楚；当前四个真实业务板块为：

1. **信审**：信用与项目审查、判断和复核；
2. **商务**：交易结构、商务条件、合同/操作与业务落地支持；
3. **资产**：起租后资产、履约、风险监测、处置与续作相关管理；
4. **政策**：行业、准入、风险政策、标准和规则支持。

大风控整体服务于大业务团队。平台可以把客户商机和资金需求作为上游输入，把资产监测、风险预警和续作作为下游反馈，但产品中心仍是业务与大风控中的人、Agent、规则、系统和上下文如何协同。

`Codex 边界修正`：该范围不是退回单一风控 Agent。信审、商务、资产、政策可以装载各自 Agent，见微负责组织能力、受控上下文、责任、人工决定和结果接续。融资租赁以外的金融业态不进入当前页面、术语、场景或验收；未来可迁移性只作为远期假设。

`用户已确认 / 后端 B1 已冻结`：见微 V2 后端唯一一级业务事项锁定为**融资租赁事项**，不以跨业务复用的通用协同事项作为权威业务根对象。主协同关系锁定为**业务 ↔ 大风控**；“业务”指触达供应商、商机和客户的销售及业务人员群体；大风控固定包含信审、政策、商务、资产四板块。决赛重点放在信审，信审与政策高度关联；商务偏合同、物流、资金等执行流程；资产负责起租后的履约、催收、处置和诉讼资源等存续管理。正式冻结见 `P2_BACKEND_PRODUCT_FREEZE.md`。

`用户已确认 / 后端 B2 高层逻辑已冻结`：每个融资租赁事项只有一条总生命周期，不为政策、信审、商务、资产分别建立平级主生命周期。总流程从商机及其来源/获取开始，进入尽调和后续业务推进；大风控四板块按政策、信审、商务、资产的逻辑时序表达，资产承接起租后的履约与风险处置，因此起租不是事项终点。政策是逐事项阶段还是组织级规则基线，仍待下一轮确认。

### 1.4 最高优先级产品 Gate：如何最小化融入现有生态

`用户转述的关键评审问题`：集团 AI 领导明确追问，见微提出一套架构后，如何与现有规则、系统、人员、内网环境和已自研能力最小化融合，而不是新增一个很重的平台。

该问题升级为 V2 最高优先级 Gate。任何候选方案都必须回答：

- 首次接入需要改哪些现有系统，哪些明确不改；
- 如何复用现有身份、权限、规则、数据、Agent 和审批机制；
- 见微保存什么最小状态，哪些事实仍由原系统权威持有；
- 能否先旁路、只读或影子运行，并在失败时安全退出；
- 多久能出现第一个可量化价值，谁亲自验收；
- 若移除见微，原有业务是否仍能继续，如何回退。

`Codex 现实修正`：金融机构里“投入后立刻使用、立刻产生大价值”不能按字面承诺。更可信的目标是**低侵入、可回退、短 Time-to-First-Value、价值可测量**。如果核心价值必须依赖全量数据迁移、组织重构、统一知识图谱或替换现有平台，则 V2 方向失败。

### 1.5 两层产品结构：组织智能全景 + 一个真实深节点

`用户已确认`：见微不能被理解为聊天盒子，也不能只用 `Harness` 描述全部产品价值。上层关注组织智能、组织判断和人/模型/Agent 的整体管理；核心矛盾是组织人数很多，但个体产能和能力协同不足，需要通过 AI-native 生态让多人使用模型，并将多个人与多个 Agent 联合调度。

`Codex 结构化建议 / 待冻结`：决赛可采用“上层看全局、下层跑一处”的结构：

- **全景层**：展示客户/事项从营销、风险判断、合同/起租到存续管理的金融生命周期，以及人、Agent、模型和系统在其中的位置；该层证明平台边界和可扩展性，不宣称每个节点都已真实实现。
- **深节点**：只选一个高价值环节完成真实前后端闭环、状态、权限、模型调用、人工 Gate、回执和失败处理；当前最强候选是风控预审协同。
- **平台内核**：能力注册、受控上下文、AI 推荐、人类确认、Agent 调用、事件与证据、上下行反馈；它不等于某一个风控 Agent。

全生命周期不是“一条工作流已经实现”，而是多个权威系统和决定的关系地图。若把营销、审批、合同、起租、资产管理全部实现，三周范围必然失控。

### 1.6 风控经验蒸馏与现场预审：高价值候选，不是已成立方案

`用户提出的候选机制`：利用风控人员在现有系统中的操作、停留时间、意见撰写、问题回复和历史经验，抽取判断模式，形成可在客户现场辅助业务人员完成材料补全、问题识别和预审的 Agent，最终由风控人员复核。

`Codex 强红队结论`：这个方向有价值，但“采集点击与文本即可蒸馏专家，现场解决全部问题、风控只需复核”目前是过度推断，原因包括：

- 点击、停留和写法只是行为相关性，不等于真实判断因果；
- 风控结论依赖政策版本、风险偏好、授权层级、外部数据、例外和事后表现；
- 历史样本存在选择偏差，缺少违约/收益等结果标签时无法证明建议更好；
- 采集员工操作涉及隐私、劳动关系、监控边界和数据授权；
- 现场输入可能不完整或被策略性包装，高风险决定不能由模型自动完成；
- 预审 Agent 若成为产品中心，会重新落回垂直风控 Agent，与见微平台定位冲突。

更可信的第一版是“风控协同预检”：基于去标识样例、规则版本和明确来源，发现缺失材料、冲突与需追问项，生成带证据的预审建议；业务补全，风控具名复核。专家经验蒸馏先作为离线研究与未来能力，不在三周内声称训练完成。

### 1.7 三周原型与 GLM 边界

`用户已确认`：三周目标是独立 Web 加轻量后端的最小前后端连调原型，不冒充大型金融机构真实部署；真实生产体系可能需要数月到一年以上的专项建设。

`Codex 现实修正`：

- 前端可以快速探索多个低成本草图，但三至五套完整实现会浪费有限时间；冻结信息架构后只实现一套决赛版本。
- 一次 GLM API 成功只证明模型 transport 可用，不证明后端成立。后端至少还需证明状态持久化、身份/权限、幂等、失败关闭、人工 Gate、Action/Receipt 和重放一致性。
- GLM-5.3 coding runner 只用于冻结后的编码检查点，不能作为见微产品凭据。产品模型 adapter 应先用 fake/stub 验证完整语义；若首轮要求 live smoke，必须使用项目独立的脱敏产品凭据并另设人工 Gate。
- 当前集团具备算力和内网 GPU 是有利部署条件，但不自动解决模型质量、数据授权、系统接入、治理、运维或用户采用。

### 1.8 外网原型与内网商业秘密隔离

`用户已确认`：当前开发和决赛演示均在外网环境。用户不拥有、也不应取得集团全部内网代码、数据、规则实现或系统框架；获得这些内容可能触及商业秘密、数据权限和组织政治边界。

因此 V2 必须遵守：

- 不复制、导出、推断或要求用户提供未授权的内网代码、客户数据、制度全文、接口凭据或系统截图；
- 使用合成、去标识或公开数据构造演示案例；
- 用 contract-first adapter、stub 和模拟回执证明可接入语义，不把模拟连接写成已接集团系统；
- 内网身份、业务事实、规则与审批仍由原系统权威持有，见微只定义最小读写契约；
- “符合现实世界逻辑”是设计目标，不等于已经通过集团架构、安全、合规或生产验收。

外网原型的有效证据是：接口边界清楚、失败语义真实、替换 adapter 后内核不变；不是通过私有数据或内部代码制造真实性。

### 1.9 融资租赁生命周期：公开一手资料校准

根据国家金融监督管理总局公开的金融租赁全流程规范，以及平安国际融资租赁公开业务流程，当前可用于决赛全景的术语链为：

> **客户与商机 → 项目准入/立项 → 尽职调查 → 风险评价与审批 → 商务/合同订立与执行 → 放款、交付与起租 → 租后资产/履约监测与风险预警 → 续作、退出或再营销**

校准边界：

- 监管正式主线是尽职调查、风险评价与审批、合同订立与执行、租后管理、风险管理与内部控制；
- 平安国际融资租赁公开表述包含客户营销、项目评价、商务操作和资产管理；
- “起租”是便于业务演示的状态节点，“翻单/再营销”属于经营延伸，不冒充监管正式环节；
- 当前 V2 全部使用融资租赁术语，不再做银行、保险或信托的跨业态映射；
- 当前生命周期只是平台关系地图，不代表每一阶段都由 V2 真实执行。

官方依据：

- 国家金融监督管理总局《金融租赁公司融资租赁业务管理办法》及答记者问：https://www.nfra.gov.cn/cn/view/pages/governmentDetail.html?docId=1236230&generaltype=1&itemId=861
- 平安国际融资租赁“风险控制”：https://pazl.pingan.cn/gongsijianjie/fengxiankongzhi.html

### 1.10 决赛闭环候选：全生命周期跨越，而非单一审批终点

`用户已确认`：风控业务场景需要保留显性篇幅，但不将风控审批或预检设为产品唯一终点。

`Codex 建议 / 待验证`：用一个 `FinancialCase` 穿越若干生命周期状态，形成平台闭环；其中只有少数模型动作做深：

1. 业务端录入合成客户与商机信号；
2. 尽调/材料 Agent 识别缺口并生成现场追问；
3. 风控预检 Agent 给出带规则来源和不确定性的建议；
4. 风控人员具名复核，原权威系统由模拟 Adapter 返回回执；
5. 案例进入起租/存续状态；
6. 资产监测 Agent 产生一个后续风险信号，重新触发人员与 Agent 协同；
7. 平台形成业务进展、风险变化和贡献/责任的不同 Projection。

这比“唯一深节点”更完整，但仍不能将所有步骤都做成复杂 Agent。需要在产品冻结时控制 Agent 数量、模型调用次数和真实状态转换。

## 2. 用户的长期愿景

长期愿景不是再造一个更强的行业 Agent，而是形成一种更灵动的组织智能：

- 人不再只能按固定岗位贡献，可以在权限和责任边界内更自由地发现信息、学习、参与和投入能力；
- Agent、Skill、MCP、规则和既有系统解决“具体工作怎么做”；
- 见微解决“谁应参与、上下文如何共享、如何接力、谁有权决定、结果如何回来、贡献如何被看见”；
- 信息不只被传递，而是能够连接到行动、结果和潜在经济价值；
- 长期可能影响组织的贡献评价和激励方式，但第一版不直接重构薪酬。

### 2.1 本轮进一步确认：长期愿景与第一版分层

`用户已确认`：

- **企业 AI 协同中枢**保留为长期愿景，不要求第一版一次实现完整平台。
- 产品首先服务集团内部的大型企业环境，必须考虑内网部署、异构系统、既有算力与平台能力，而不是照搬面向公网 SaaS 的单一入口。
- 第一版不追求 Claude Tag 式的最轻形态，也不建设 Atlassian、Microsoft 或 ServiceNow 式完整平台；目标是处在两者之间的**中等重量产品**。
- 希望融合全球头部产品中已经被验证的关键机制，但融合的目标是形成适合集团内部的独立产品结构，不复制品牌、界面、闭源实现或整个平台边界。
- 用户认可把第一版收束到“企业协同事项”这一工作单元，并允许在该核心上作适度扩展；具体正式名称仍待后续讨论，暂不因口述中的“机器驱动”等措辞自动冻结。

`Codex 归纳 / 待用户继续校准`：

> 长期做企业 AI 协同中枢，第一版做集团内、异构系统上的中等重量协同事项运行层。

“中等重量”不以页面数量或功能数量定义，而以承担的责任定义：它应比共享 Agent 多保存正式事项、具名责任、权限、人工关口和回执；但不接管 IM、OA、项目管理、Agent 开发平台或全企业数据图谱。

### 2.2 新增长期理念：从固定岗位与 KPI 转向可见的动态贡献

`用户已确认`：长期希望改变人对工作的态度。人在组织中的价值不应只由固定岗位、业务身份或预设 KPI 定义；一句有价值的话、一条信息、一次判断或一段专业投入，都可能改善组织结果，并最终与个人认可、机会乃至收入产生联系。

`用户已确认`：AI-native 与 data-native 不只是提高既有岗位效率，也可能让人围绕信息、能力、兴趣与问题进行更丰富、更流动的贡献，而不是只能执行传统岗位分工。

`Codex 边界修正`：这一理念可以作为见微的长期 Why，但大型协作、工作管理、知识图谱与 Agent 平台同样可以讲“释放贡献、重构工作”的故事，因此它本身不是独特性证明。第一版也不直接计算薪酬或承诺增收，而应先做到：贡献来自什么信息、由谁提出、为何路由给谁、形成了什么结果，以及结果如何被组织确认，均有可追溯证据。

## 3. 当前识别出的核心问题

现有企业软件和 Agent 产品分别解决了局部问题，但缺少一层轻量、连续的协同运行机制：

- 聊天工具保存讨论，却不天然保存权威目标、责任、决定和接力状态；
- 项目管理系统保存任务，却常要求人手工重建上下文；
- Agent 能完成任务，但通常围绕单个用户或单次会话运行；
- 多个 Agent 可以通信，但 Agent 之间的通信不等于人与人的协同；
- 企业系统保存业务事实，却很少记录跨人、跨 Agent 的协作因果链；
- 身份、权限、上下文、责任、回执和贡献往往分散在不同系统。

因此，见微要填补的不是“能力缺口”，而是**组织能力之间的连续协同缺口**。

### 3.1 独特性过滤器

- “减少重复劳动、提高个人效率、让工作更幸福”是重要愿景，但不是见微独有的产品机制。
- 如果一个价值可以由单个 Agent、Skill、MCP、自动化工作流或普通协作软件独立完成，它就不能成为见微的核心定位。
- 见微的方向、MVP、页面和技术内核必须持续回答：**它解决了哪些只有多个人、多种 Agent 与企业责任体系共同运行时才会出现的问题？**
- 当前差异化候选是：多个具名人员和可替换 Agent 围绕同一协同事项，在权限边界内共享必要上下文、可靠接续责任并保留同一权威历史。
- 上述候选仍需用户确认，不能因写入本文件自动视为冻结结论。

### 3.2 新出现的产品中心候选：领导意图与执行反馈循环

`用户已确认`：第一版更偏向领导层使用。领导在 Web 中不仅查看指标，还应当：

- 快速看懂人、Agent、模型能力、当前位置、工作状态和结果；
- 与 AI 澄清自己的想法，并在明确授权后把部分意图向下分发；
- 看到下属人员与 Agent 的实际推进情况；
- 当执行产生新状态与证据时，由 AI 将必要信息压缩并向上汇报；
- 保留领导、执行人员、Agent 之间的上下级关系、权限差异和信息边界。

`用户已确认`：风控与业务形成的既有内核可以弱化。它们是方向来源和候选资产，不应因已有实现而限制新产品。

`Codex 归纳 / 待验证假设`：产品中心可能从泛化的“协同事项接续”进一步收束为：

> **把领导意图编译为受控、可执行的授权上下文并向下传递，再把人的行动、Agent 动作和系统证据压缩为可信的上行反馈。**

候选闭环为：

> 领导意图 → 人工确认与授权 → 分层分发 → 人 / Agent / 系统执行 → 状态与证据入账 → AI 压缩 → 上行汇报与再次决策

这条闭环是否构成独特产品机制仍未验证。指标驾驶舱、自动汇报、任务分派、Agent 可视化任何单点都不是创新证明；需要检验上述组合是否比现有管理软件、协作平台和 AI 助手形成更低损耗的组织反馈回路。

这里的“让人快速看懂”不是把人定义为愚蠢，而是承认人的注意力、工作记忆和上下文切换带宽有限。前端视觉形式可以后定，但“让有限认知带宽迅速掌握模型能力、位置、结果和责任”已经成为产品机制的一部分，不能仅视为装饰。

### 3.3 第一个具体但未冻结的切口：会议后受控上下文接续

`用户已确认`：前述领导场景只是大体系中的一段。见微不需要成为整台机器，而应把自己负责的接续环节做好，并允许决赛项目或集团已有 Agent 作为能力节点串联进来。

`用户已确认`：第一目标用户更偏向中层管理者。中层既要承接上级意图，又要组织下属、人和 Agent 执行，并向上汇报；会议与 PPT 数量多，是用户目前能够真实接触和观察的群体。

`用户场景样本`：

- 上级参加会议后，完整会议上下文不能全部向下披露；
- 模型可辅助筛选大约需要向下传递的部分，但披露内容必须由有权人员确认；
- 中层只需获得与自己责任相关的必要上下文，理解自己在完整事项中的位置；
- 被授权的 Agent 可基于这份有限上下文自动处理或辅助执行；
- 中层补全自己负责的进程与产物，结果再进入受控的上行反馈。

`Codex 归纳 / 待验证假设`：第一个可被亲自验收的闭环候选是：

> **一次会议结束后，将完整上下文编译为经领导批准的最小披露 Context Packet，交给一名中层及一个或多个既有 Agent；中层能够看懂自己的位置、责任、可用能力和预期结果，完成自己的一段后，系统基于真实证据生成受控的上行回执。**

现有 Agent 会受到上下文影响，但这种影响必须被设计为显式、受限、可追溯：Agent 只接收与任务和权限匹配的 Packet 版本；模型筛选只是披露建议，不拥有披露权；Agent 输出不会自动升级为共享事实，必须经过来源、权限和接受检查。

边界修正：会议只是用于说明“目标/信息向下分发、执行证据向上反馈”的样本，不是产品场景冻结。产品不能退化为会议纪要、会后任务或会议 Agent；同一机制必须能够承载来自会议、消息、业务事件、风险信号、客户反馈或个人洞察的输入。

### 3.4 第一体验原则：先回答“为什么找我”

`用户已确认`：当一个人被路由进协同过程时，第一屏最重要的问题不是有哪些 Agent，也不是先展示完整 Dashboard，而是：**为什么找我，我在这里是做什么的。** Agent 与该人的关系属于后续信息。

`Codex 归纳 / 待验证假设`：第一屏至少需要用可解释证据回答：

- 哪条信息、目标或变化触发了这次邀请；
- 为什么系统或发起人认为“我”与它有关；
- 我被期待贡献什么，而不是只收到一个无上下文 KPI；
- 我的权限、可见范围与不能做的事；
- 我的贡献将影响哪一个结果，以及完成后如何被记录；
- 哪些 Agent、人员和系统可以辅助我。

这一原则把产品中心从“展示 Agent 能力”转向“解释人为何进入协同、如何产生被看见的贡献”。

定位边界：`企业智能贡献路由与协同层` 当前只是一种机制归纳，用户担心它再次把产品收得过窄，不能作为正式产品名称或冻结定位。贡献路由、风险感知与提示、受控上下文接续可先作为见微的核心能力候选，而不是要求所有输入都被解释为“贡献”。

## 4. 轻量产品原则：大内核，小入口

本节中的“轻量”不再等同于“最轻”。当前目标修正为：**进入方式轻、协同语义中等深度、底层可扩展**。允许独立 Web 控制面与必要的事项能力，但不能因融合多个标杆而变成新的全功能办公平台。

### 4.1 用户可见形态

- 第一入口可以是独立 Web 应用；后续可嵌入 Slack、Teams、飞书、钉钉或企业微信。
- 用户登录后，账号代表具名身份；角色与权限决定能看到什么、能做什么、能否改变权限。
- 页面不展示一个庞大“组织大脑”，只让用户看见当前协同事项、必要上下文、参与者、下一棒和需要自己的动作。
- 允许在 Web 中注册、查看、配置或编辑 Agent，但 Agent 编辑器不能吞掉协同主线。

### 4.2 系统实际边界

- 不替换 IM、OA、ERP、CRM、项目管理、代码仓库或文档系统。
- 不复制全部业务数据，只保存必要的协同状态、上下文摘要、来源指针和事件证据。
- 普通消息、页面浏览和常规状态读取不触发模型。
- Agent 调用按需、异步、可失败；失败或无回执不得伪装为成功。
- 模型和 Agent 没有业务权威，只能在被授权的范围内建议或执行。
- 通过 Adapter 接入现有 Agent、MCP、A2A、API 或企业系统；核心不绑定单一模型或厂商。

## 5. “五个人的上下文”如何连续：当前架构假设

不能把五个人的完整聊天记录直接拼成一个超长 Prompt。当前更合理的结构是：

### 5.1 同一个协同事项

所有参与者共同指向一个稳定的 `CollaborationCase`。它只有一条权威事件历史，用于记录：

- 当前目标及版本；
- 已确认事实和来源；
- 已作决定与未决问题；
- 当前参与者、角色和权限；
- 当前责任人与下一棒；
- 关键产物及其位置；
- Agent 动作、人工 Gate 和外部回执。

### 5.2 私有工作上下文与共享上下文分离

- 每个人和每个 Agent 保留自己的局部工作上下文。
- 局部发现不会自动污染共享事实。
- 只有明确提交、具备来源并通过权限检查的信息，才进入共享上下文。
- 不同角色可以看到同一协同事项的不同 Projection，但这些视图必须来自同一事件历史。

### 5.3 版本化 Context Packet

每次接续不传全部历史，而是生成一个受控的 Context Packet，至少包含：

- `caseId` 与 `goalVersion`；
- 当前目标；
- 已确认事实与来源；
- 已作决定；
- 未决问题与风险；
- 关键产物引用；
- 当前权限与约束；
- 下一步动作和建议接收人。

### 5.4 接力不是自动改责任人

接力至少经过：`提出 → 查看 → 接受 / 拒绝 / 要求澄清`。只有具名接收人明确接受后，责任才转移。Agent 可以准备接力包，但不能替人接受组织责任。

## 6. 协同微内核：当前最小组成

这是架构假设，不是已冻结技术方案。

1. **Identity & Permission**：Workspace、用户、角色、Agent 身份、资源范围和动作权限。
2. **Collaboration Case**：稳定的协同事项身份、目标版本和生命周期。
3. **Event & Projection**：追加式事件历史，以及面向不同角色的同源视图。
4. **Context Continuity**：局部上下文、共享事实、版本化 Context Packet 和来源指针。
5. **Handoff & Human Gate**：具名接收、责任变化、人工决定和失败关闭。
6. **Agent Adapter**：模型、Agent、MCP、A2A、工具和现有系统的可替换接入层。
7. **Action & Receipt**：动作意图与真实回执分离，不把“已经请求”当作“已经完成”。

这个内核像调度器：不亲自完成具体业务，只维持协作连续性、边界和证据。

## 7. MVP 工作假设 V0

MVP 先证明一个通用机制，不先绑定风控、研发或其他垂直场景。

### 7.1 最小可演示结构

- 一个企业 Workspace；
- 三至五个具名人员；
- 一个或多个可替换 Agent；
- 一个协同事项；
- 一套账号与角色权限；
- 一条从信息进入、多人补充、共享上下文形成、具名接力、Agent 续跑到结果回执的连续历史。

### 7.2 用户应能亲自验证的结果

1. 不同账号登录后看到的页面和可执行动作不同。
2. 五个人各自补充信息，不需要把五份原始对话全部暴露给所有人。
3. 经确认的信息进入同一共享上下文，换人或换 Agent 后仍能继续。
4. 接力提出后责任不自动变化，只有具名接收人接受才改变。
5. Agent 可以被替换，协同事项的历史、目标和责任不丢失。
6. Agent 失败、越权或没有回执时，系统明确显示失败或未知。
7. 所有关系、推进、责任或其他视图都来自同一份权威状态。

### 7.3 当前不进入 MVP

- 通用低代码流程设计器；
- 大型 Agent 市场；
- 全企业知识图谱；
- 自动重构薪酬和绩效；
- 大规模多租户、高可用和生产部署；
- 一开始接入十几个企业系统；
- 用大量模型调用维持“看起来很智能”的界面。

## 8. 全球对标：第一轮短名单

以下均为公开资料初筛，不能把厂商自述当作已独立验证的产品能力或商业结果。

| 产品 / 公司 | 值得研究的部分 | 与见微的差距 | 当前判断 |
| --- | --- | --- | --- |
| Claude Tag / Anthropic | Slack 中的共享 Agent、频道记忆、主动跟进、组织身份、权限与审计 | 仍以 Claude 为中心；没有完整的人际责任、贡献和价值协同 | 轻入口的主要标杆 |
| Slack Code / Salesforce | 临时多人 Code Channel、共同 Prompt、产物、预览和审批 | 以开发为中心；组织级连续性尚窄 | 多人 Agent 交互标杆 |
| Asana AI Teammates | Work Graph、共享计划、多人架构、治理与 handoff | 产品和迁移感较重，容易被理解为完整工作管理平台 | 协同内核的主要标杆 |
| Atlassian Rovo + Teamwork Graph | 人、工作、目标、决定和工具的关系图；可向不同 Agent 开放上下文 | 深度依赖 Atlassian 体系，入口和数据建设较重 | 组织上下文的主要标杆 |
| Codex in Slack / OpenAI | 从 Slack 线程启动独立执行任务并回传可见结果 | 任务级、编码中心；不是持续共享 Agent | 任务执行对照组 |
| Basebase | Slack 上的团队共享上下文与持续积累 | 公开验证和企业治理证据有限 | 早期直接竞品候选 |
| Handoff | 人与 Agent 共用 Workspace、共享记忆和来源归属 | 企业权限、责任 Gate 和成熟度待核验 | 早期直接竞品候选 |
| Patchwork / Syncolab | 共享的人与 Agent 工作空间、可见 Agent 行为 | 规模、治理和真实采用证据待核验 | 早期形态参考 |

初步结论：

- Asana 与 Atlassian 更接近“大内核”，但形态偏重；
- Claude Tag 与 Slack Code 更接近“小入口”，但组织协同语义仍浅；
- 见微若成立，应落在二者交点：**像插件一样进入，像协同内核一样保持连续性。**

第二轮官方资料核验已形成独立文档 `P2_GLOBAL_HUMAN_AGENT_BENCHMARK.md`。最新修正是：

- **Anthropic Claude Tag** 是当前轻量多人共享 Agent 入口的最佳基准；
- **Asana AI Teammates** 是正式工作对象上的 Human–Agent 协作基准；
- **Atlassian Teamwork Graph + Rovo/Jira** 是战略上最接近见微长期叙事的基准，已经连接人、目标、决定、所有权、工作和 Agent；
- **Microsoft Agent 365** 与 **ServiceNow AI Control Tower** 已占据 Agent 身份治理和 AI Control Plane / Control Tower 叙事；
- **Salesforce Agentforce + Slack** 已把聊天入口、CRM 上下文、业务动作、权限和 Human Handoff 连成闭环。

因此，“企业 AI 协同中枢、AI Control Plane、共享上下文、Agent 像同事、Human Handoff”都不能单独作为见微独特性。当前仅保留待验证的窄组合：比 Claude Tag 更正式、比 Asana/Atlassian 更轻、比 Microsoft/ServiceNow 更贴近一线协作、比 Salesforce 更系统中立。

中国生态的进一步核验已形成 `P2_CHINA_HUMAN_AGENT_ECOSYSTEM.md`。必须同步修正：

- 国内企业人机协同大类已经不是空白；钉钉悟空、飞书、腾讯 WorkBuddy 正在争夺企业 AI 工作平台、协作入口和组织级 Agent 底座；
- 华为 CodeArts Agent Team、Qoder、扣子等已经覆盖多 Agent 持续上下文、共享任务、成员通信或企业协同开发的不同部分；
- P1 的“七项完整门槛下没有已证实直接同类”只能保留为严格同构判定，不能继续外推为“国内没有强相邻产品”或“企业 AI 协同中枢是空白品类”；
- 当前国内生态位候选收窄为：面向受监管、异构系统大型企业的轻量协同事项接续层，比平台型产品更中立、更正式地记录具名责任接受、人工决定、外部回执和同一权威历史。

当前证据只验证了问题有价值，尚未验证企业会单独采购这一层；支付意愿、集成成本和平台替代风险仍需客户 discovery。

### 8.1 内部决赛项目竞争场

本轮已从 ChatGPT 对话《24决赛》中用户录入的十组参赛者原始口述转写，单独形成 `P2_FINALIST_PROJECT_COMPETITOR_RESEARCH.md`。该材料是内部竞争场的发现证据，不是外部产品市场证据，也未独立验证参赛者的技术实现和业务数据。

当前最重要的修正是：不能再笼统声称其他项目只有单 Agent、没有协同。原始项目中已经出现：

- 研发 Harness 的状态门禁、双层持久化、Agent 职责分离；
- AI 外呼中的多轮意向、跨座席上下文与人机接续；
- 审核流程中的前置解耦、数据继承与版本控制；
- 销冠萃炼、个人 AI 分身和经营决策中枢等群体知识或宏大叙事。

因此，“协同、共享上下文、状态、Gate、Human-in-the-loop、Harness”任何一个单点都不足以构成见微独特性。当前仍待验证的组合空位是：多个具名人员与多个可替换 Agent 围绕同一企业协同事项，在权限边界内分层共享上下文，通过具名接受完成责任转移，并把人工决定、Agent 动作和外部回执保留在同一权威事件历史中；同时该内核需能跨异质场景复用。

## 9. 十八问产品访谈与量化收敛

访谈总权重为 100 分。分值不是答案优劣，而是该问题对最终产品方向的影响程度。一次只讨论一个问题；每个答案分别标注为 `用户已确认`、`Codex 归纳` 或 `待验证假设`。

### A. 北极星与边界（17 分）

1. **第一因 / 8 分**：长期愿景中，见微最根本要改变什么？
2. **长期终局 / 5 分**：如果十年后成功，企业的组织运行方式会发生什么结构性变化？
3. **绝对非目标 / 4 分**：无论市场怎样变化，见微绝不能变成什么产品？

### B. 用户、买方与价值（16 分）

4. **第一日常用户 / 7 分**：谁会每天主动打开或触发见微？
5. **经济买方 / 5 分**：谁有预算、动机和权力推动首次采购或试点？
6. **价值受益者 / 4 分**：最先得到可量化收益的是个人、团队、管理者还是企业整体？

### C. 协同对象与最小闭环（31 分）

7. **最小协同对象 / 6 分**：一条信息进入后，围绕什么稳定对象持续聚合人、Agent 和状态？
8. **高频入口 / 5 分**：用户最自然、最频繁地从哪里把信息或意图交给见微？
9. **共享确认 / 6 分**：个人信息满足什么条件后，才成为团队可依赖的共享上下文？
10. **隐私与分层 / 5 分**：哪些上下文必须共享，哪些必须留在个人、角色或部门边界内？
11. **责任接力 / 5 分**：什么事件才算真正完成一次人与人或人与 Agent 的 handoff？
12. **闭环完成 / 4 分**：什么证据出现后，一个协同事项才可以被认定完成？

### D. Agent、身份与权限（15 分）

13. **Agent 权威 / 6 分**：Agent 在第一版可以建议、执行、决定到什么程度？
14. **Agent 装载 / 4 分**：用户在框架里编辑 Agent 时，最少需要配置哪些内容？
15. **权限模型 / 5 分**：权限以固定组织角色为主，还是允许围绕单个事项临时变化？

### E. 轻量入口、MVP 与商业证明（21 分）

16. **轻量形态 / 6 分**：第一版怎样进入企业，才能既独立可演示，又不让领导感到部署很重？
17. **亲自验收 / 9 分**：用户亲自操作后，什么最小结果足以证明 MVP 成立？
18. **商业与扩展 / 6 分**：用什么指标证明它产生了大价值，并值得扩展到第二个场景？

### 已回答

#### Q1 第一因（8 分）

- `用户已确认`：宏大目标是**重构人的工作模式**。
- `用户已确认`：在具体效率层，追求人机协同达到尽可能理想的状态，充分释放模型的每一分可用价值。
- `用户已确认`：当前工作中的沟通损耗、重复和繁琐会制造痛苦；理想状态是让人能够发现问题、学习技术、提高自己、得到认可，并感受到自己的价值。
- `用户已确认`：长期希望更多人从工作中获得幸福感和高价值感；在平安的表达中，希望员工能真实看见技术如何改变工作与世界。
- `Codex 归纳`：模型能力不是产品终点；产品要提高模型能力在多人、上下文、权限、接续和结果中的实际兑现率，并把节省出的人的注意力转向发现、学习、创造、判断和连接。
- `用户纠正`：工作幸福、减少重复和个人提效并非见微独有，Agent、Skill、MCP 或其他产品也可以产生这些结果；产品判断必须始终围绕见微的独特性。
- `Codex 修正`：工作幸福与人的价值感属于长期愿景和 Why，不等于产品独特机制；不能用普遍愿景代替竞争定位。
- `产品影响`：见微的中心必须是人的工作如何被重新组织，Agent 是可装载、可替换的能力节点，不能反过来让人迁就某一个 Agent。
- `当前状态`：第一问仍在澄清，尚未关闭；需要确认见微独有的第一因是否是“多人通过同一轻量 Agent Harness 形成连续、可治理的组织协同”，而工作幸福只是长期结果。

当前进度：`0 / 18 已关闭`；正在讨论：`Q1`；已关闭权重：`0 / 100`。

#### Q4 第一日常用户（阶段性答案，尚未关闭）

- `用户已确认`：第一版更偏向领导层，而不是普通执行者或平台管理员。
- `用户已确认`：领导使用独立 Web；Dashboard / 驾驶舱只是最低能力，不能成为产品全部。
- `用户已确认`：领导可以与 AI 澄清意图，经本人允许后向下分发；下层执行状态被 AI 感知后，再形成上行汇报。
- `待澄清`：“领导层”具体是集团高层、部门负责人、项目/事项负责人，还是三者共用但具有不同 Projection。这个差异将直接改变高频任务、数据范围、权限模型和 MVP 验收。

#### Q4 第一日常用户（本轮收敛）

- `用户已确认`：第一目标用户定位在**中层管理者**；高层不是当前可接触、可验证的首要用户。
- `产品原因`：中层处在组织信息与责任的上下行交界处，既承接上级会议、意图和有限披露上下文，也需要协调下属及 Agent 执行并形成上行反馈。
- `当前状态`：用户类型已初步确认；仍需定义中层的具体工作时刻、频率和可量化损耗后，才能关闭 Q4。

#### Q11 / Q13 路由与 Agent 权威（阶段性答案）

- `用户已确认`：AI 应主动给出若干人员候选及其原因，否则无法体现 AI 在能力匹配中的价值。
- `用户已确认`：最终由有权的人选择实际参与者，AI 推荐不直接形成责任分派。
- `Codex 边界`：候选、理由、使用的上下文版本和最终人工选择都应记录；AI 不得据此自动形成绩效、薪酬或负面员工评价。
