# P1 复用路线与十场景抽取冻结

状态：用户与总控于 2026-08-27 冻结。本文覆盖竞品专项中“以风控作为唯一 P1 纵向闭环、延后其余九个完整实现”的研究建议；竞品事实、证据矩阵和许可证地图继续有效。

## 1. 路线结论

- 公开一手证据下，没有已证实可以整套替代见微的中国直接同类产品。
- `openai/codex`、Claude Agent SDK、AgentScope、RAGFlow 以及中国企业 IM/审批/模型平台，只能作为受许可约束的局部实现或 adapter 候选。
- 见微继续自研最小 Corporation Harness 控制内核，但内核不得由风控或任何单一场景主导。
- 风控业务协同只是十个同权场景之一；它不是默认产品锚点，也不拥有更高优先级。

## 2. 十场景抽取原则

以下十个场景必须全部从真实市场需求做深，并共同约束产品：

1. 风控业务协同
2. 需求开发协同
3. 人机交互协同
4. 内容生产协同
5. 经营增长协同
6. 物理智能协同
7. 知识办公协同
8. 客户服务协同
9. 供应链履约协同
10. 医疗服务协同

每个场景必须分别冻结用户、协同对象、目标与版本、参与者、责任与权限、阶段、循环/返工、证据、质疑、人工 Gate、外部动作、回执、失败/未知、指标和接续包。不得用同一模板只替换名称。

共享能力进入内核的必要条件：至少三个语义、责任和风险结构明显不同的场景都真实需要。满足三场景门槛后，仍必须评估安全、成本、可解释性、失败关闭与是否应留在场景包或 adapter；不得机械升格为共享内核。

## 3. 正确的抽取顺序

1. 完成十份真实 ScenarioPack 与市场证据追踪。
2. 建立“候选能力 × 十场景”矩阵，记录每个场景的语义差异、责任主体、风险和负向路径。
3. 识别满足三类异质场景门槛的候选能力。
4. 将候选能力分为：共享控制内核、场景扩展、外部 adapter、纯展示字段、暂不实现。
5. 冻结 Event、Command、Projection 与拒绝语义后，才恢复后端实现。
6. 用十个真实 Projection 验证三视图同源；任何场景不得成为装饰入口。

## 3.1 共享大板块的量化准入

共享内核不依赖主观判断。每个候选大板块先通过硬门槛，再按 100 分量表评分。

硬门槛：

1. 至少三个语义、责任和风险结构明显不同的场景真实需要；
2. 进入共享层后，任何高风险场景仍能保持权限、人工 Gate、外部动作与回执的失败关闭；
3. 场景差异可以通过参数、规则、Schema 扩展或 adapter 表达，不需要在共享内核堆叠场景名称条件分支；
4. 同一权威 Event/Projection 可以支持所有采用该板块的场景，不产生第二套事实来源。

量化评分：

| 指标 | 分值 | 计算关注点 |
| --- | ---: | --- |
| 十场景覆盖度 | 20 | 真实需要该能力的场景数，而不是页面是否出现同名字段 |
| 异质场景覆盖度 | 15 | 覆盖多少种明显不同的责任、风险与组织边界 |
| 核心语义一致性 | 20 | 输入、状态变化、输出和完成条件是否保持同义 |
| 责任与权限稳定性 | 15 | owner、参与者、授权、接收与撤销语义是否可用统一规则表达 |
| 权威状态与审计必要性 | 15 | 是否必须进入 Event、重放、版本、Gate 或回执事实链 |
| 复用收益 | 10 | 进入共享层后能否实质减少重复实现、测试和解释成本 |
| 安全与可解释性 | 5 | 是否容易失败关闭、审计、说明和独立验证 |
| 场景差异成本 | 最高扣 20 | 例外、条件分支、字段空洞化和误导性统一越多，扣分越高 |

归属规则：

- 70 分及以上且全部硬门槛通过：进入共享控制内核；
- 50–69 分：保留公共接口，但实现留在场景扩展或可插拔模块；
- 30–49 分：留在 ScenarioPack 或 adapter；
- 30 分以下：不做共享抽象，必要时仅作为场景展示或暂缓能力；
- 任一硬门槛失败：无论总分多高，都不得进入共享内核。

## 3.2 场景微调边界

进入共享内核的大板块允许各场景微调：角色名称、阶段、证据类型、Gate 规则、循环条件、指标、文案、布局默认值和外部 connector 映射。

不允许微调的权威语义：对象身份与版本、事件顺序、责任转移是否成立、Gate 是否有效、动作幂等、回执成功/失败/未知、模型权限上限、Projection 与 Event 的一致性。

如果某个场景需要修改上述权威语义，必须回到量化矩阵重新评估：它可能是新的场景扩展，或说明原共享板块抽象错误，不能以局部补丁绕过。

## 4. 复用边界

- 可评估复用：session 标识与恢复、受限执行、approval/sandbox 抽象、JSON 状态流、Agent SDK、RAG、企业身份/审批/IM 连接器。
- 必须自研并由十场景抽取：Work/目标版本、Participant/Authority、结构化 Handoff、人工 Gate、Action/Receipt、Event/Projection、失败关闭和三视图统一业务语义。
- 不得复制：Codex App/Web、Claude Code、CodeArts、Qoder、扣子等闭源 UI、服务端实现、商标、未公开协议或内部调度逻辑。
- 外部 Agent、模型、RAG、IM 与审批平台只能产生候选、证据或外部回执，不能直接改写见微的权威责任、目标、Gate 或动作事实。

## 5. 对当前产物的处理

- `research/p1-competitor-pivot/` 的竞品事实、能力矩阵、许可证与本地化缺口继续作为有效研究证据。
- 其中 `P1_PIVOT_RECOMMENDATION.md` 的“风控唯一闭环、其余九个延后”不被产品 Gate 接受，由本文覆盖。
- 前端 V2 保留为候选交互实现，但必须继续证明十个场景都具有真实而不同的关系、进度、矩阵与接续内容。
- 后端 V2 当前分区产物保持候选状态；在十场景抽取矩阵和新内核契约通过前，不继续模型适配器、HTTP 或连调。

## 6. 下一 Gate

下一项不是选择“先做哪个场景”，而是验收十场景横向抽取矩阵。Gate 必须回答：

- 哪些能力被至少三个异质场景共同需要；
- 同名能力在十场景中的责任、权限和失败语义有何差异；
- 哪些属于共享内核，哪些必须留在场景包或 adapter；
- 当前前后端 Schema 是否错误地被风控、研发或人机交互任一场景主导。

该 Gate 未通过前，不恢复产品代码扩展。
