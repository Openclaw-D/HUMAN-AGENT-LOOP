# 见微-人机协同平台：三场景融合方案

日期：2026-08-27  
状态：P0 产品方向已确认；实现尚未开始

## 1. 融合结论

三个首批锚点场景不建立三套流程引擎，而是共同验证一套 Corporation Harness 内核：

1. **风控业务协同**验证证据、质询、规则建议和具名人工决定。
2. **需求开发协同**验证目标版本、需求澄清、任务分配、交付物和人工验收。
3. **人机交互协同**验证人和 Agent、多 Agent 之间的分工、上下文隔离、交叉复核、冲突升级和人类责任。

`Work` 是唯一通用工作聚合根。场景差异只能放在 `ScenarioPack` 的显示词汇、角色绑定、Playbook、Artifact Schema、Policy、Gate、Connector 和 Evaluation Rubric 中。

## 2. 三场景共享内核

| 内核对象 | 平台职责 | 禁止绑定的场景词 |
| --- | --- | --- |
| `Workspace` | 组织、团队或项目的隔离与配置边界 | 风控部、研发部 |
| `Work` | 需要推进并形成结果的通用工作单元 | 案件、需求单、Agent 对话 |
| `GoalVersion` | 目标、约束、验收条件的不可变版本 | 过审条件、PRD 固定字段 |
| `Actor / RoleBinding / AuthorityGrant` | 区分人、Agent、系统以及它们当前的角色和权力 | business、risk、developer 等固定枚举 |
| `Task / Run` | 可分配工作与一次明确输入下的执行 | 固定两个 Agent、固定审查轮次 |
| `ContextSnapshot / Evidence` | 记录一次判断或执行实际使用的上下文与来源 | 只支持财务材料或代码文件 |
| `Artifact / Challenge` | 结构化产物以及缺失、冲突、澄清闭环 | 风控建议书、需求问答的专用对象 |
| `Handoff` | 具名接收后才改变任务承接关系 | 默认部门流转顺序 |
| `HumanGate / DecisionRecord` | 保护高风险动作并记录具名人类决定 | pass/veto、merge/release 固定结果 |
| `ActionIntent / ExecutionReceipt` | 对外部系统副作用进行授权、执行与回执 | 某一个 CRM、Git 或审批系统 |
| `BusinessEvent / Projection / Evaluation` | 权威历史、查询状态、质量与业务结果 | 某场景独立审计表和第二事件流 |

## 3. 场景一：风控业务协同

### 业务包配置

- 角色：业务人员、风控人员、建议 Agent、规则服务。
- Context：申请信息、材料、历史记录、政策规则。
- Artifact：材料摘要、风险提示、缺口清单、判断包。
- Challenge：缺失材料、材料冲突、来源不可核验、规则不满足。
- HumanGate：具名风控人员作出放行、拒绝或退回补充决定。
- Connector：业务系统状态回写；演示阶段使用明确标记的 Mock。
- Evaluation：漏判、误报、补证轮次、处理时长、人工采纳率。

### 共用内核流程

```text
创建 Work / 接受 GoalVersion
→ 固化 ContextSnapshot
→ Agent Run 生成 Artifact
→ Challenge 打开、回答、解决并形成新 Snapshot
→ HumanGate + DecisionRecord
→ ActionIntent 回写业务系统
→ ExecutionReceipt + Evaluation
```

### 只作为场景配置

`business/risk`、`pass/veto`、预审/正审、`3＋2＋1`、金融材料类型和具体规则均不得写入内核对象或通用 Command。

## 4. 场景二：需求开发协同

### 业务包配置

- 角色：需求提出者、产品/需求负责人、开发者、测试/Reviewer、需求分析 Agent、编码 Agent。
- Context：用户反馈、PRD、设计稿、Issue、代码、接口文档、测试和运行日志。
- Artifact：需求摘要、验收标准、技术方案、任务拆解、Patch/PR 引用、测试报告。
- Challenge：需求歧义、目标冲突、依赖缺失、技术不可行、验收条件不明确。
- HumanGate：目标版本接受、范围变化、代码合并、发布或回滚。
- Connector：文档、Issue Tracker、代码库、CI/CD；外部写入必须产生 Receipt。
- Evaluation：需求漂移、澄清次数、返工率、测试结果、交付周期和验收通过率。

### 共用内核流程

```text
用户问题或需求 → Work
→ 提议并接受 GoalVersion / 验收标准
→ Agent 与开发发起 Challenge
→ 需求方补充，形成新 ContextSnapshot
→ Task 分解和 Handoff
→ 人或 Agent Run 生成方案、代码、测试 Artifact
→ Review Challenge / HumanGate
→ 合并或发布 ActionIntent
→ CI/代码库 ExecutionReceipt + Outcome
```

### 需要特别保护

- PRD 和代码库仍是外部事实来源，见微保存引用、版本和协作状态，不复制为第二真相源。
- Agent 可以提出任务、方案和 Patch，但不能自行扩大需求范围或绕过 merge/release Gate。
- 需求修改必须成为新 `GoalVersion`，不能静默覆盖原始验收标准。

## 5. 场景三：人机交互协同

### 业务包配置

- 角色：具名责任人、协调 Agent、执行 Agent、复核 Agent；两个 Agent 只是首个 fixture，不是内核上限。
- Context：人类目标、允许使用的数据、Agent 能力、预算、期限、前序 Artifact 和限制。
- Artifact：计划、子任务结果、批注、综合结论和验证报告。
- Challenge：Agent 之间结论冲突、证据不足、工具失败、越权请求或超出预算。
- HumanGate：目标接受、敏感数据使用、冲突裁决、高风险工具调用和最终提交。
- Evaluation：任务完成率、冲突发现率、重复工作、成本、时延、人类接管次数和最终质量。

### 共用内核流程

```text
Human 创建 Work 并接受 GoalVersion
→ 协调 Agent 基于 ContextSnapshot 提议 Task
→ Task 分配给 Agent A
→ Agent A 产出 Artifact 并 offer Handoff
→ Agent B 接受后复核、补充或发起 Challenge
→ 一致结果进入综合 Artifact
→ 冲突、越权或高风险动作进入 HumanGate
→ 具名责任人裁决、修改目标或授权 Action
→ Receipt + Evaluation + Replay
```

### 责任边界

- Agent 可以成为 `Task` 的执行者，但每个 `Work` 必须有具名 `accountableHumanId`。
- Handoff 只转移任务承接关系，不自动转移最终责任或权限。
- Agent B 不是默认真理裁判；其复核结果仍是 Artifact。冲突由 Policy 路由，必要时由人处理。
- 模型失败、超时、低置信或格式错误不得制造完成、批准或成功回执。

## 6. 一套共用 Command，而不是三套 API

三套业务包只能调用同一组语义命令：

```text
work.create
goal.propose / goal.accept
context.snapshot
task.create / task.assign / task.complete
run.request / run.succeed / run.fail
challenge.open / challenge.answer / challenge.resolve
artifact.publish
handoff.offer / handoff.accept / handoff.reject
gate.open / gate.resolve
action.propose / action.authorize / action.execute / action.recordReceipt
evaluation.record
```

命令由通用对象表达。场景包可以限制允许的命令、要求的 Gate 和字段 Schema，但不能增加绕过内核的行业专用写入路径。

## 7. 防止扰乱格局的四条硬规则

1. **内核无业务角色枚举。** 权限来自 `RoleBinding + AuthorityGrant + PolicyPack`。
2. **内核无业务阶段枚举。** 风控轮次、开发阶段和 Agent 协作步骤属于 Playbook；`Work` 只保留少量通用生命周期状态。
3. **内核无业务结果枚举。** pass/veto、accept/reject、merge/release 是版本化 Decision Schema。
4. **业务包无自己的存储和事件系统。** 三场景共享 Event Store、Command handler、Projection、身份、Gate、Receipt 和审计链。

## 8. P1 首批三场景验收

只有同时满足以下条件，才说明融合没有把平台重新拉回专用系统：

1. 三个 ScenarioPack 使用同一套内核对象、Command handler 和 Event envelope。
2. 删除任一业务包后，内核代码和其他业务包无需修改。
3. 新增业务包不需要增加行业专用数据库表或权威状态机。
4. 同一工作台通过配置展示不同角色、表单、Artifact、Gate 和指标。
5. 三个场景都能演示成功、补充信息、拒绝/冲突、Agent 不可用和外部结果 unknown。
6. 所有 Agent 产物绑定 ContextSnapshot；所有受保护动作绑定具名人类和 Receipt。
7. Event-only Replay 能重建三种 Work，前端刷新后不依赖 localStorage 恢复权威状态。
8. 测试证明不存在跨 Workspace、越权、旧版本、重复执行和静默 Mock success。

## 9. 当前停止点

本文件冻结前三个锚点场景的共同方向，不代表其余七个场景可以浅化或后补包装。下一步由 P1 总控分别分发真实市场研究、前端架构、轻量后端契约和纵向连调任务；任何共享内核能力都必须通过“至少三个明显不同场景真实需要”的资格线。旧 command/state machine 不直接迁移为新 runtime。
