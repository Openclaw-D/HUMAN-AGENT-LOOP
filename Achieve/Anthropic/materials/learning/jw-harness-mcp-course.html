0. 先把最重要的结论钉死

你可以说见微具备高级 Gateway（网关）的部分能力，但不能把见微只定义成 Gateway。

更准确的定位：
见微是建立在集团通用技术底座之上的、面向融资租赁真实 Case 的 vertical orchestration & control layer（垂直编排与治理层）。
Gateway 主要回答消息从哪里来，要送到哪里？
Harness 主要回答Agent 怎样思考、调用工具、运行和恢复？
见微必须回答业务能力何时进入、能做什么、谁有权决定、失败怎样回退？
最强反方意见：如果见微只有统一入口、能力卡片和路由，它就是“又一个 Gateway”或“前端聚合器”。只有真实证明 Case 状态、Human Gate、Evidence、Receipt、审计、评估和失败回退，它才拥有独立价值。

3. Session、Thread、Channel、Directory

概念它是什么最像什么
Channel（频道）消息从哪里进来微信群、Slack 频道、企业聊天入口
Thread（任务/对话线程）产品界面里的一条独立工作线Codex 侧边栏中的一个任务
Session（运行会话）运行时连续上下文和状态Agent 正在使用的会议室档案
Session ID（会话编号）找到某个 Session 的唯一编号会议室号码
Directory（工作目录）Agent 可以工作的文件位置办公桌和文件柜
codex://threads/01a... 是 Deep Link（深度链接）。其中 01a... 是 Thread ID；完整链接还包含协议和对象类型。它与 Session ID 的作用相似——都用来定位对象——但不保证是同一个系统编号。

4. Persistence、Memory、Heartbeat

Persistence（持久化）保存机制。进程重启后，重要状态仍然存在。
Memory（长期记忆）被保存的数据之一，用来跨会话带回重要信息。
Heartbeat（心跳唤醒）定期叫醒某个 Agent 或任务，让它检查是否有工作。

企业 Agent 应该持久化什么？

Session transcript对话记录
Workflow state业务走到哪一步
Human Gate / Receipt谁批准了什么，以及正式凭证
Idempotency record哪些业务请求已经处理
Audit / Evaluation执行轨迹、错误、质量和人工纠正

5. Harness、Skill、MCP、Plugin 怎样组合

组件一句话不是什么
Model（模型）负责理解和推理不是完整系统
Harness（智能体运行框架）让模型拥有循环、工具、权限、Session、持久化和审计不只是聊天框
Skill（可复用工作方法）告诉 Agent 什么时候做、怎么做、边界和验收是什么不等于远程接口
MCP（工具连接协议）让 Harness 按统一协议发现和调用外部工具不保证网络一定可达
Plugin（能力安装包）可以组合 Skill、MCP、UI、资源和配置通常不是独立 SaaS
Model + Harness + Skill + MCP/Tools + Governance = 可工作的 Agent System

6. Idempotency（幂等性）：防止重试造成重复后果

f(f(x)) = f(x)　　例如：abs(abs(-5)) = 5
天然幂等把合同状态设置为 approved，执行五次仍是 approved。
天然不幂等余额增加 100 元，执行五次会增加 500 元。

在授信四个环节里的作用

环节重复请求风险幂等保护
1. 提交材料同一附件重复入库同一材料哈希或提交 ID 只接收一次
2. 启动风险分析重复创建多个分析任务同一 Case + Context Version 只产生一个有效 Run
3. 人工审批双击导致两次状态推进同一审批请求只生成一张 Receipt
4. 同步下游系统重复创建合同或授信记录同一业务事件只消费一次
幂等性不等于一致性：
idempotency（幂等性）防止“重复做”；consistency（一致性）保证“不同系统看到的状态不互相矛盾”。它们经常一起出现，但解决的不是同一个问题。

7. Schema（结构契约）：数据必须长什么样

Schema 是“空白表格 + 填写规则”，规定字段名、类型、是否必填、允许值和限制条件。

Schema 类型规定什么审批例子
Tool Schema（工具结构契约）模型调用工具时传什么approve_case(case_id, decision)
API Schema（接口结构契约）程序请求和回复长什么样POST /cases/approve
Database Schema（数据库结构）表、字段、类型和关系decisions 表
Event Schema（事件结构契约）系统事件消息长什么样case.approved

8. 见微与 One：避开正面竞争的正确方式

Autonomy（自主性）不等于每一层都自己造。真正的自主，是租赁域资产由自己拥有，并且底层可替换、可测试、可迁移。

比赛现场必须证明的最小闭环

  1. 一个真实融资租赁 Case 到达明确阶段。
  2. 见微根据状态和规则选择一个能力，而不是用户随便点击。
  3. 能力只获得最小必要 Context，输出经过 Schema 校验。
  4. Agent 输出只能成为 Evidence 或 Candidate，不能直接成为正式结论。
  5. 具名人员通过 Human Gate 后生成唯一 Receipt。
  6. 能力超时、重复请求或被暂停时，Case 不被破坏并能回退。

10. 应用题：从“记住”走向“会用”

先自己回答，再展开参考答案。

应用题 1：评委问“集团已经有 One，为什么还要见微？”

参考答案：见微不复制 One 的通用入口、模型和 Harness。它复用集团底座，把租赁领域的 Case Schema、状态路由、具名责任、Human Gate、Evidence、Receipt、失败回退和领域评估做成可插拔治理层。One 解决共性能力，见微解决能力如何安全进入真实租赁业务。

应用题 2：人工审批按钮被连续点击两次，系统应该怎样处理？

参考答案：前端禁用按钮只能降低概率，后端仍必须用 approval request ID 或 Case + Context Version + decision intent 形成幂等约束。第一次生成 Receipt 后，第二次返回同一结果，不能再次推进状态或生成第二张正式凭证。

应用题 3：一个新的风险 Skill 要接入见微，最少检查什么？

参考答案：entry/exit 条件、input/output Schema、最小可读 Context、禁止写入的正式状态、timeout/retry/idempotency、失败 fallback、Human Gate、版本、Owner、评估集和退出机制。自然语言 description 只负责说明，runtime 必须机器校验。

应用题 4：什么时候该用 Mermaid，什么时候该用 LangGraph？

参考答案：需要让人看懂链路、状态和系统分层时用 Mermaid；需要让程序真正按节点、条件边和状态持久化运行时用 LangGraph。Mermaid 是图，LangGraph 是运行时。

建议学习顺序：先看图 → 用一句话复述 → 做测验 → 用见微场景重新解释一次。
