# JW 下一阶段：客户级授信与远程尽调｜四任务总控书

版本：规划草案 1.0；2026-09-16。用途：交给 Codex 做基线核验、契约统筹和独立验收；产品实现按仓库当前分工交 ZCode。本文不构成启动任务、修改本地代码、提交、推送、购买服务或调用收费 API 的授权。

## 一、先确认我们在做什么

产品目标：以企业客户为工作入口，把企业微信沟通、远程视频尽调、资料证据、四域分析、客户授信与逐笔支用串成一个可操作工作台。视频接通时，以真实客户现场画面为主背景，透明面板展示事实、待办、风险与操作；底部沟通区常驻；打开面板不应中断通话。

不是：四个模型投票放款；按资料数量兑换额度；把生成的工厂场景冒充真实现场；把已有静态演示改得更漂亮后宣称已实时接通。

### 用户本次提出的方向

- 客户维度统一归集所有来源的商机与融资需求。
- 拟定单一客户最高额度人民币 1,000 万元。
- 远程尽调优先，特殊情况才转现场。
- 企业微信为主要业务沟通入口，目标是授权、可追溯、可审计。
- 政策、信审、商务、资产四域协作，政策约束更刚性，信审处理复杂风险，商务与资产提供专业支持。
- 一个连续工作页面，视频、透明工作面板与聊天并存，最终必须可真实操作。

### 本任务包采用的设计建议，不冒充已经批准的公司制度

1. 客户级额度与逐笔融资交易分层：Customer → CreditFacility → FinancingRequest/LeaseContract；直租与回租在交易层保留各自必要要件。
2. 资料更充分只允许触发重新评估；有利证据可能提高可支持金额，不利证据可能降低、暂停或不支持融资。文件数量本身不加额度。
3. 1,000 万元是用户提出的产品上限，不是监管限额，不是默认批准金额；公司资本、集中度、关联关系、资产与偿债能力等仍可能施加更低限制。
4. Agent 只能生成分析、建议、提问和暂停建议；已批准、不可豁免规则由确定性 Gate 执行；正式授信/拒绝/例外/支用授权保留在人类权限体系。
5. 四域共享来源可追溯的感知与证据，不将同一份材料的四次复述当成四份独立证明。
6. 所有真实客户数据、业务规则原件、音视频、密钥、令牌、数据库和运行日志不进入公开 GitHub。

### 未决项及默认安全行为

| 项 | 未决内容 | 开发阶段默认行为 |
|---|---|---|
| 客户与关联组 | 客户的法律主体范围、集团/实控关系合并规则 | 以企业法律主体建档；关联关系独立建模，禁止仅凭同名、同电话自动合并 |
| 额度 | 额度档位、偿债模型、集中度口径、是否循环、还款后是否恢复 | 可配置；未批准规则不激活，不自动提额或释放循环额度 |
| 红线 | 每条规则的来源、适用范围、不可豁免性、复核权 | 缺失时 policy_pending；不得编造公司规则 |
| stale | 已验收依据变化后怎样复核、能否重开、何种例外 | 保留历史，阻止基于陈旧依据的新正式决定；通用 ack 不能绕过硬红线 |

| 视频方案 | 企业微信原生通话或从企微进入受控 RTC/H5/小程序 | 两路线先验证；改用 RTC 必须符合企业渠道政策，不能静默替换 |
| 数据与模型 | 存储地域、留存期限、处理依据、真实模型和费用授权 | synthetic/offline 可开发；真实服务验收未完成时必须 BLOCKED，不能模拟冒充 |
| 支用 | 资金出账系统、人工复核和付款确认接口 | 本轮不连真实资金支付；可验证业务预占和受控模拟回执 |

## 四、实施顺序与提交边界

先做任务 01 的 S0 只读核验和 S1 契约提案，再进入产品实现。执行顺序为：01 核心 → 02/03 按冻结契约推进 → 04 集成验收。禁止把本包作为无边界的长时间自动开发 Goal。

“提交边界”是 commit-ready 文件与行为边界，不是自动 git commit/push 授权。现有用户授权按具体范围适用；本任务包不扩大授权。不重置用户工作区，不擅自切分支，不建立 worktree，不修改 Achieve 历史原件。

每阶段报告必须包括：输入版本、实际修改文件、行为差异、命令与退出码、完整测试次数/失败次数、证据位置、已知失败、未测依赖、下一阶段允许范围。未通过当前关键验收门不得扩大范围。非依赖任务可继续，不能把整个项目因外部账号未就绪而空转。

## 五、统一验收等级

| 等级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| E0 契约/fixture | Schema、状态机、幂等、权限和确定性规则在合成输入下成立 | 真实视频、企微、模型、客户可用性 |
| E1 本地真实服务 | HTTP、PG、对象存储、事件、跨进程恢复实际运行 | 外部服务能力、远程网络兼容性 |
| E2 真实提供方受控测试 | 官方测试租户/RTC/获准模型与两个设备真实连通，处理经授权测试材料 | 生产业务制度已经通过、真实资金可出账 |
| E3 业务试运行验收 | 获准身份/规则/数据处理条件下的人工场景验收 | 永久无故障、模型零漏报、公司全域合规 |

产品可以阶段性交付，但仅完成 E0/E1 不得标为“真实实时尽调系统已完成”。无真实账号、费用或合规授权时，报告具体 BLOCKED 门和已经完成的本地部分。

## 六、前端契约：本轮不重做视觉，但必须为目标页面准备能力

- 工作台状态：idle、inviting、ringing、connecting、live、reconnecting、ended、replay。实时与回放必须明显区分。
- 音视频连接属于独立会话；打开透明面板、切四域、查证据不销毁连接。
- 下方聊天常驻，但 `customer` 与 `internal` 两种受众必须分别授权和显式发送；内部风控意见不可误发客户。
- 面板状态分别展示：处理进度、风险结论、数据新鲜度、正式权限与动作可用性；不能只用一条“压力值”概括。
- 原始客户视频与内部 HUD 录制分开；不得默认把内部风险叠层合流分享给客户。
- Blender/Unity 生成场景只能用作明确标注的训练/合成素材；真实尽调背景必须来自合法取得的实际媒体。
- 本轮只允许最小测试工作台验证真实操作，不借机替换 React/Vite、加入大规模 3D 引擎或进行全站 CSS 改版。
