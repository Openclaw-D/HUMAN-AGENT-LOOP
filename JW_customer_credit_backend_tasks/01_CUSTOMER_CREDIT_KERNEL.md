## 4. S1：领域契约与权限设计

### 新增/关联实体提案

- `Customer`：企业法律主体；tenantId、customerId、legalEntityRef、状态、版本。企业微信联系人不是客户法律主体的替代品。
- `CustomerRelationship`：控制、担保、供应商、关联组等关系；含证据引用、核验状态、有效期。关系不确定时保留待核验，不自动合并档案。
- `CreditAssessment`：某次评估，固定 evidence snapshot、规则版本、计算口径和输入版本；候选不直接改变额度。
- `CreditFacility`：有权人员批准的额度、币种、有效期、循环属性、产品范围、条件、审批链和依据版本。
- `FinancingRequest`：客户在额度下的一次具体融资申请；direct_lease/sale_leaseback 保留于此；关联租赁物、合同与交易链。
- `ExposureEntry`：额度状态迁移账目，与业务写同事务；不以可被客户端覆盖的余额字段作为唯一依据。
- `DecisionRecord`：人类身份、动作、职责/权限、规则与事实版本、理由、条件、时间及前后版本。

现有 Project 保留为执行/场景实例，新增 customerId 关联；旧 projectId 不被静默重用。不能把多个企业的项目仅按名称挂到同一客户。

### 额度口径

1,000 万元作为人民币客户级产品上限配置。金额内部使用整数分或精确定点数，JSON 约定一致，不用浮点货币。该上限为用户产品方向，不是法定限额。

额度总账建议采用互斥状态：`reserved`（预占）→ `committed_undisbursed`（承诺未出账）→ `outstanding`（已用未偿本金）；同一金额只能属于其中一格。取消/结算用补偿或结算事件留痕，不删除原账。

在 active、未过期、条件满足、数据有效时：可用额度 = max(0，已批准额度 − 已用本金 − 承诺未出账 − 有效预占)。冻结、到期、关键复核未决时新增支用可用额为 0。已降额低于存量敞口时，必须显示超额状态，保留实际敞口，不能篡改历史使余额“看起来合规”。

是否循环、还款何时恢复额度、利息/费用/担保等如何计入风险敞口，须由版本化政策明确；未配置不得自行猜测。公司/关联组集中度检查单独建约束，不因客户未达 1,000 万而默认可放。

### 状态与正式动作

候选评估：draft → collecting → candidate_ready → awaiting_human_review；正式人类决定独立记录。额度：proposed → approved_inactive → active → suspended/expired/closed；拒绝是评估决定，不把“拒绝额度”误置 active。

每个写命令在执行时重新验证：可信 principal、tenant/customer 权限、动作权限、expectedVersion、请求幂等、规则与证据新鲜度、条件与上限。UI 隐藏按钮不是安全边界。

`complete`、`accept`、`decide` 不改为同义词；验收某个技术产物不等于批准客户授信。不得把 jianwei 默认设为所有额度的超级审批人。

### Schema 与 API 版本

以增量 v2 契约提案为例：客户读取、评估创建/读取、额度批准/激活/暂停、融资申请、额度预占/释放/确认、客户事件。具体路由在 S1 冻结后实现，不宣称仓库已有这些路由。

旧 `/api/v1/**` 保持明确兼容期；新业务 API 通过 `/api/v2/**` 或同等版本方案发布。所有读、事件、回执和媒体元数据同样校验租户/客户范围。

修复旧 `quota|price|rate` 禁键策略的方式：新增严格的候选结果 Schema，允许合法的分析金额/条件字段，并强制 authority=none；正式状态只能由人类命令写入。禁止直接删掉旧安全校验后放任任意 JSON。

### S1 提交边界

仅领域 ADR、实体/事件/权限/错误码 Schema、迁移设计和兼容说明。明确待决政策及 safe default。不得此时改变运行态。

## 5. S2：客户归集与证据映射

新增最小数据库结构、授权边界和旧 Project 关联。迁移先在隔离库演练；记录迁移前后行数、标识映射和不可逆项。旧数据不全时只标记 legacy_unassigned，不编造客户身份。

证据模型必须区分：原始材料 EvidenceArtifact、关于业务事实的 FactAssertion、两者引用关系与冲突。发票与合同原则上并存；同一文档的更正版才按明确关系 supersede。合同不能因上传较晚就抹去发票金额或冲突信息。

任务 02 负责媒体与资料接入；本任务只提供 A 的受控登记/关联 API，不允许连接器直接插业务表。

S2 提交边界：客户结构、最小查询/关联命令、证据关系增量、迁移与相关测试；不夹带额度自动化。

## 6. S3：额度账本与并发防线

所有额度占用通过单一客户/主额度约束入口。采用事务锁或可证明等价的并发控制；关联组/客户同时加锁必须固定锁顺序，避免死锁。

幂等键须按租户、可信调用者、业务动作和资源明确作用域。校验权限应发生在返回缓存回执之前，防止用别人的 requestId 读取敏感结果。同 requestId 同有效载荷重放不新增余额；异载荷必须冲突。

预占有效期可自动清理“确定未发送/未承诺”的请求；对于外部执行状态 unknown 的请求不得超时自动释放，必须持有占用并进入对账/人工复核，防止释放后重用导致双重支用。

本轮外部出账只对受控模拟适配器测试，不调用真实银行接口。不宣称外部 exactly-once。

S3 提交边界：账本、状态迁移、预占/释放/模拟确认、并发与幂等测试；不改四 Agent 策略。

## 7. S4：人类权威与依据失效

额度批准、条件变更、暂停、例外、支用确认的角色/金额权限从服务端授权目录及已批准矩阵取得。没有矩阵就 policy_pending；任何人类测试身份都不等于生产身份。

证据 supersede、关键事实冲突、规则更新，按依赖映射将受影响评估标 stale。正式批准事务必须复查当前依据和阻断状态，避免“检查时通过，提交前发生变化”的竞态。历史已批准记录保留，不自动改成拒绝；后续动作可冻结等待复核。

现有 `staleReviewAck` 只能作为技术兼容项，不得通用放行不可豁免规则。事实纠正后重新核验与“绕过规则”是不同动作。

S4 提交边界：正式动作、权限、stale/复核和审计；须同时提供负例，不得仅交 happy path。
